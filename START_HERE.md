# Стартовое задание для Codex

Помести содержимое этого комплекта в рабочий репозиторий, сохранив существующие файлы и изменения. `AGENTS.md` должен лежать в корне проекта. Затем передай Codex текст ниже.

---

Ты реализуешь HeatRoute — веб-систему предварительной трассировки тепловых сетей. Главный приоритет — качественный backend, геоданные, реальные вычисления, тестируемость и возможность адаптации после получения данных организаторов. UI должен быть полноценным и современным, но собирается на готовой shadcn/ui, без долгого изобретения собственного дизайна.

Прочитай AGENTS.md, docs/TECH_SPEC.md и дополняющие контракты, UI, тесты и план. Используй их как единое ТЗ. Это не запрос на ещё один план: нужно последовательно реализовывать систему и проверять её работоспособность.

Сначала изучи текущий репозиторий, сохрани пользовательские изменения и создай короткий план выполнения M0–M5 в docs/implementation/progress.md. Затем начни реализацию. Выбранный стек: Python/FastAPI/PostGIS/Celery для бэкенда, React/TypeScript/Vite/shadcn/ui/MapLibre для веба. Для пустого репозитория используй этот стек без нового опроса о библиотеках.

Первый значимый результат — рабочий вертикальный срез: API/CLI принимает сценарий → worker действительно находит путь вокруг препятствия → сервер независимо проверяет коридор → сохраняет run → карта отображает полученный GeoJSON. При добавлении препятствия результат должен пересчитываться. Не подменяй это заранее нарисованной линией.

Затем доведи P0 по этапам: версионируемый импорт Raw/Staging/Canonical, безопасный mapping, CRS и topology validation, правила/кандидаты, A*/Dijkstra, альтернативы, стоимость и недостающие данные, jobs/retry/cancel, полноценный web workspace, экспорт, безопасность и сквозные тесты.

Не жди реальные данные: работай на синтетических examples и fixtures, которые явно помечены demo. Не выдумывай нормативы, цены рынка, мощности и глубины. Не реализуй пропускную способность через энтропию и не называй геометрическую проверку гидравликой. Гидравлика и 3D-инженерия остаются явно недоступными до реальной реализации и достаточных входов.

Используй стабильные совместимые версии из официальных источников, зафиксируй зависимости. Создай и запускай необходимые команды тестов/линтинга/интеграции; отдельно проверяй результат на реальном PostGIS и worker, а не только моках. Для small graphs сравни A* с Dijkstra при одинаковых ограничениях и стоимости.

Не останавливайся после scaffolding или красивой первой страницы. После каждого этапа проверь критерии приёмки, обнови progress, затем переходи к следующему. Когда сессии/ресурса недостаточно для всего P0, оставь воспроизводимый рабочий срез и точную запись следующего шага — без заявления, что система завершена.

В отчёте перечисли реально реализованное, выполненные команды и результаты, незакрытые проверки и ограничения. Скриншот интерфейса не является доказательством корректности backend.

Прочитай AGENTS.md и docs/implementation/progress.md. Воспроизведи последний smoke test, проверь состояние репозитория, затем продолжи со следующего незавершённого этапа M0–M5 по ТЗ. Не меняй стек и не переписывай завершённые модули без конкретной причины. Обнови тесты и evidence report.
