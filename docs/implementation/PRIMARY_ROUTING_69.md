## Изменение и границы

У конкретного `OfficialRouteValidator` появилась сессия одного расчёта. Окружение хранит
сессии по идентичности валидатора; используются именно его правила. Четыре geometry-вызова
planner используют эту сессию. Структурная проверка не менялась.

Повторно используется bounded `PreparedRoutingConstraints`: typed ID, фактический отступ и
точное сравнение исходной геометрии. Изменение геометрии/типа/ДУ, порядок/дубли объектов и
состав текущего окна не игнорируются. До512записей и100000резервируемых координат на сессию;
это не лимит байтов/всех временных объектов. Топология, actual geometry, собственный ввод,
нормаль, пересечения и результаты валидации вычисляются заново.

Публичный standalone `validate(nodes, edges, features)` и независимый exporter не используют
сессионную подготовку. Сессия не хранит готовые маршруты или ответы валидатора, однопоточна
и не переносится между runs. Существующий внутренний memoization подмаршрутов не изменён;
межзапускового кеша результатов не добавлено. Наследники валидатора вызываются через прежний
публичный override без подготовки: нельзя обходить более строгий hook ради ускорения.

## Профиль69: подготовка пока не устранила hot spot

30с JFR `source69-validation.jfr`,1719main samples,95,4% с `sharedSpineAlternatives` в стеке.
70,4% включают `PreparedRoutingConstraints.compile`,70,3% — `baseConstraints`.
Доли включающие; другой срез фазы не является прямым процентом ускорения/замедления.
Для анализа `jfr print` использован `--stack-depth 128`: стандартный вывод пяти frames
скрывал вызывающий код и непригоден для сравнения. Все JFR/JSON остаются ignored.

Bounded `PreparationBudgetProbe` на фактических144features обнаружил117constraints и
34889резервируемых координат дляДУ50. Повтор того жеДУ компилирует0ограничений, но
цикл50/100/150/200/250/300/400/500/50 вытесняет подготовку: после каждого переключения
заново строятся88diameter-dependent ограничений. При100000координатах одновременно
удерживаются менее трёх полных комплектов. Повтор последнегоДУ снова даёт0компиляций.
Источник — `source69-preparation-budget.log`; первоначальная диагностическая NPE для
special.blocked=null устранена в helper до получения этих чисел, production не менялся.

Измеренные фазы67→69: independent45,628→46,396с, shared63,171→65,134с,
group_spines161,666→162,868с; число поисков/пар совпадает. **Ускорение не получено.**
Свежий69 завершился за660,385с; JFR и небольшая probe делают замер не изолированным.
Следующая проверяемая идея — консервативный spatial broad phase до построения буферов,
по фактической полилинии участка; не просто увеличение лимита удержания. Обязательно
сохранить unknown-DU exceptions, порядок issues, special constraints, нормали и точность
границ/precision models. Пока только review, код фильтрации не включён.

Review уточнил безопасный следующий дизайн: нельзя молча не вычислять впервые увиденный
дальний buffer — это может скрыть прежнее исключение или неверно оценить округлённую границу.
Первую подготовку выполнять полностью. Затем удерживать меньшие metadata фактических
envelopes успешных буферов вместе с exact source snapshot, отдельно от тяжёлых геометрий.
После eviction тяжёлого buffer повторять его только для пересекающегося участка; eviction
metadata возвращает прежний полный путь. Все удерживаемые snapshots/записи/envelopes входят
в явный ограниченный бюджет, не в неограниченный второй map. Snapshot одного источника можно
разделять между ДУ, но нельзя игнорировать geometry/precision mutation или дубли ID.

Для forbidden выбирать по объединению фактического buffer envelope и outward-expanded
source envelope с полным axis clearance; для special достаточно source envelope. Касания
сохранять. Mandatory egress/normal по-прежнему получают все исходные features.
Standalone/fallback сохраняет прежний per-DU путь; session выбирает constraints по каждому
полному route envelope. До skip разрешать clearance всех релевантных непустых features:
DU проверяется для **всех forbidden типов**, не только OKS (комментарий preparation устарел).
Custom rules/geometry/precision требуют явного fallback и отдельных тестов. Это план,
не реализованная фильтрация и не доказательство speedup. Сначала RED на rotating-DU budget,
затем exact issues/касания/вводы/исключения/порядок/precision/custom/metadata-eviction.
