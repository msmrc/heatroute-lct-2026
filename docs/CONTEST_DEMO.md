# Сценарий конкурсной демонстрации HeatRoute

## Подготовка

Демонстрация выполняется на неизменённом файле `datasets/official/lct-2026.geojson`. Перед показом
нужно поднять чистый комплект по `README.md`, дождаться readiness API и открыть web-интерфейс.
Ручное редактирование маршрутов, базы и GeoJSON между шагами запрещено.

Проверяемый baseline:

- SHA-256 входа: `07921d7740c0297a63111846d4b77dfb6ccb33da65ffd7ccb14c5b2d786dd7d0`;
- 144 объекта, включая 17 точек подключения ОКС;
- 323 предупреждения compatibility-профиля и ноль блокирующих ошибок;
- текущий финальный clean-stack CI: run `35129162919`;
- финальный Java 11 topology-scale CI: run `35120995991`.

## Десять шагов показа

1. **Единый входной файл.** Нажать «Загрузить набор данных» и выбрать официальный GeoJSON.
   Интерфейс сразу показывает loader, затем карту результата без промежуточной технической формы.
   Повторная загрузка тех же байтов должна вернуть существующий import, а не дублировать 144
   объекта в PostGIS.
2. **Валидация исходных данных.** Открыть предупреждения проверки. Пояснить compatibility-профиль:
   числовые ID нормализованы, demand хранится прямо в `oks_connection_point`, а отсутствующие
   инженерные значения не выдумываются. Интерфейс группирует 323 исходных предупреждения в семь
   русскоязычных причин с количеством объектов и примерами ID, отдельно от замечаний расчёта,
   вертикального профиля и реконструкции.
3. **Один расчёт для всех ОКС.** Показать, что один immutable run обработал все 17 demand points,
   а не отдельный ручной маршрут для каждого здания.
4. **Автоматические врезки.** На карте выбрать зелёные/оранжевые узлы и показать выбранные точки
   подключения к существующей сети. Для поставленного набора формируется 204 детерминированных
   кандидата до выбора вариантов.
5. **Содержательно разные варианты.** Переключить independent, shared и diverse варианты.
   На текущем неизменённом файле показать воспроизводимые результаты: рекомендуемый independent
   подключает 17 из 17 ОКС, shared — 16 из 17, diverse — 14 из 17. Частичные варианты сохраняют
   успешно рассчитанную сеть и явные `NO_NON_CROSSING_ROUTE`, а не уничтожают весь результат.
6. **Дерево, камеры и участки.** Выбрать рассчитанный участок и узел. Показать геометрию,
   `base`/`special` секции, flow, ДУ и технические узлы. Объяснить ограничения: один upstream,
   не более трёх downstream и отсутствие циклов/пересечений вне общего узла.
7. **Расходы, ДУ и предельная длина.** В карточке/результате показать, что каждый accepted edge
   содержит `flow_tph`, `diameter`, длину и секции. Расход суммируется снизу вверх, а ДУ повышается
   как по расходу, так и при превышении непрерывной предельной длины.
8. **Ограничения и специальные проходы.** Включить слой ограничений и показать, что маршрут
   обходит запретные зоны. Для дороги/трамвая и инженерных коммуникаций показать специальные
   секции; правило конкретного перехода не отключает остальные запреты.
9. **Стоимость и ранжирование.** На contract-complete данных показать component totals,
   `calculated_cost`, `length`, `score` и deterministic rank до трёх вариантов. На поставленном
   файле прямо показать статус неполной экономики: отсутствуют baseline flow, upstream direction
   и diameter камер, поэтому финальная реконструкция и score намеренно не фабрикуются.
10. **Официальный результат и воспроизводимость.** На contract-complete варианте скачать один
    strict GeoJSON с семью выходными типами. Показать System Information, Swagger и версии
    контракта/алгоритма. Открыть публикуемую JSON Schema результата и показать, что фактический
    экспорт проходит её в CI. На supplied dataset ожидаемое поведение экспорта —
    `409 OFFICIAL_EXPORT_INCOMPLETE` с объяснением недостающих исходных полей.

## Что показывается автоматически

- исходная сеть, ограничения, ОКС/точки спроса и рассчитанные варианты на одной MapLibre-карте;
- выбор варианта и слоя без перезагрузки страницы;
- карточка выбранного объекта и компактный остров результатов;
- partial result и причина no-route;
- фактическое имя загруженного файла;
- сохранённый результат после рестарта Java API.
- продольный профиль каждого рассчитанного участка: глубины, уклоны, зоны пересечений и результат
  независимой проверки;
- XYZ-геометрию и `depth_start`/`depth_end` в строгой выгрузке.

Локальный replay-bundle строится тем же Java-инспектором из исходных байтов официального файла;
его размер, SHA-256 и 323 предупреждения защищены регрессионным тестом. Локальный API принимает
загрузку только при точном совпадении этих байтов, после чего воспроизводит тот же completed-run;
для любого другого файла возвращается явная ошибка вместо несвязанного демонстрационного
результата. Браузерный smoke на 1280×720 проверяет полный переход от file upload к карте,
кликабельность всех трёх вариантов, сгруппированную диагностику и продольный профиль без ошибок
консоли. Карта сначала поднимает локальный инженерный холст и сразу добавляет расчётный overlay;
стиль CARTO догружается как необязательный контекст. При недоступном CDN маршруты, исходная сеть,
выбор объектов и масштабирование продолжают работать, а интерфейс явно сообщает об отсутствии
фоновой карты. Этот offline-fallback проверяется unit-тестом и браузерным отказным сценарием.

## Что нельзя обещать на текущем файле

- полную реконструкцию существующей сети и камер;
- финальный официальный score и выгружаемый strict result;
- правило для `railway`, пока организатор не подтвердил его семантику;
- route throughput для неизвестной maximum-topology геометрии.

Эти ограничения относятся к отсутствующим входным данным или отдельной optional-задаче, а не
скрываются «правдоподобными» значениями. Полный список вопросов организатору находится в
`docs/implementation/OFFICIAL_ALIGNMENT_AUDIT.md`.
