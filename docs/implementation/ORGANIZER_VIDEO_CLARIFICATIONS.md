# Уточнения организаторов из видеовстречи

**Источник:** `Город 2. ДИТ.mp4`  
**Проанализировано:** 17 сентября 2026 года  
**Статус:** активная рабочая трактовка для supplied-dataset profile; противоречия с PDF/DOCX
должны быть подтверждены организатором письменно.

Этот файл фиксирует ответы организаторов, прозвучавшие на видеовстрече. Он не переписывает
официальные PDF/DOCX и не превращает устные ответы в новый контракт. Для реализации действует
следующий порядок:

1. точные таблицы, поля и формулы берутся из PDF/DOCX;
2. более поздние устные уточнения определяют текущий приоритет и трактовку supplied dataset;
3. при прямом противоречии код не должен молча выбирать одну версию — вопрос выносится ПМу для
   письменного подтверждения.

## Подтверждённая рабочая трактовка

- Весь вычислительный backend должен быть реализован на Java 11. Java-обёртка над решателем на
  другом языке не принимается. Maven, Spring Boot 2.6.3 и PostGIS допустимы.
- Расчёт должен работать полностью offline, без runtime-вызовов AI, токенов и внешних API.
  Собственный VPS используется для демонстрации; организаторы разворачивают исходный репозиторий
  на одном своём стенде.
- UI не оценивается. Обязателен сервис, который принимает исходный GeoJSON и позволяет скачать
  корректный результирующий GeoJSON. Swagger нужен для воспроизводимой проверки.
- Из-за ограничений по данным критической инфраструктуры обязательную реконструкцию существующей
  сети убрали из текущей сокращённой постановки. Реконструкцию следует сохранять как расширенный
  strict-profile, но она не должна блокировать стоимость, rank или экспорт supplied-dataset run.
- В supplied dataset объект спроса представлен непосредственно `oks_connection_point` с
  `flow_tph`; искать точку подключения внутри `oks_future` не требуется.
- Реальный городской набор может содержать тысячи точек и занимать 2–3 ГБ. Малый переданный файл
  не отменяет streaming/DB-spatial требования.
- Жёсткого таймаута одного расчёта не объявлено, но скорость является дополнительным критерием.
  Горизонтальное масштабирование и несколько серверов для обязательной оценки не нужны.
- Главный первый этап оценки — корректная 2D-геометрия, стоимость и правильное ранжирование до
  трёх вариантов. Глубина/Z проверяются позже у лучших решений.

## Уточнённые правила 2D-алгоритма

1. Угол пересечения дороги/железной дороги измеряется относительно оси препятствия. Если ось не
   задана отдельным объектом, её требуется вывести из геометрии препятствия.
2. Все переданные 17 connection points находятся внутри полигонов `restriction_type=oks`.
   Начальный участок обязан выйти из собственного здания по нормали к ближайшей границе и пройти
   за требуемую для текущего ДУ защитную зону. Нельзя просто исключить весь содержащий OKS из
   ограничений и разрешить выход в произвольном направлении.
3. Если проектная точка врезки на трубе находится не далее 10 м от допустимой существующей камеры,
   маршрут присоединяется к этой камере. Иначе создаётся новая камера врезки.
4. Каждое новое разветвление выполняется в камере.
5. Каждая новая независимая ветка, входящая в существующую камеру, считается отдельной врезкой по
   5 млн рублей. Нельзя считать несколько новых лучей одной врезкой только потому, что они имеют
   один и тот же chamber node.
6. Предпочтительные повороты — 45° и 90°. Для нестандартного отвода применяется коэффициент 1,5;
   алгоритм должен избегать лишних поворотов и сварных соединений.
7. При наложении нескольких специальных препятствий формируется один объединённый special-участок.
   Для него применяется максимальный `K_special`, а не произведение коэффициентов.
8. Объект можно намеренно оставить неподключённым, если лучший допустимый маршрут вместе с
   камерами, врезкой и остальными компонентами дороже штрафа
   `100 000 000 + 500 000 * flow_tph`. `no_route` является допустимой альтернативой оптимизации,
   а не только признаком геометрической невозможности.
9. Камера сама по себе не сбрасывает непрерывную длину одинакового ДУ. При превышении длины в
   обсуждении предлагалось повысить ДУ на один шаг каталога.

## Принятые продуктовые решения

После разбора записи владелец конкурсного набора уточнил рабочую трактовку: единственный
`restriction_type=railway` ошибочно назван в датасете и должен обрабатываться как `tram_tracks`.
Для него применяются опубликованные параметры трамвайного пересечения; отдельный вопрос по
`railway` закрыт для supplied-dataset profile.

- Непрерывная длина одинакового ДУ считается отдельно по каждому пути от корня к потребителю.
  Разветвление и камера не сбрасывают длину; новый отсчёт начинается только при смене ДУ.
- При превышении длины выбирается первый разрешённый размер, который удовлетворяет ограничению;
  повышение не ограничено ровно одним соседним шагом каталога.
- Значение `0,7 м` трактуется как минимальное покрытие над оболочкой трубы, а не как универсальный
  вертикальный просвет до препятствия. Просветы задаются отдельно по типу пересечения.
- Семь выходных типов образуют разрешённый словарь. Типы реконструкции и технические узлы не
  обязаны присутствовать, если соответствующих рассчитанных сущностей нет; выдумывать пустые
  объекты запрещено.

## Оставшиеся вопросы по дополнительной глубине

- Сохраняется ли шаг глубины 0,5 м?
- Сохраняется ли максимальный уклон 0,10 м/м и наклонные переходы, либо стоимость считает только
  горизонтальные и вертикальные длины?

До письменного ответа оставшиеся спорные правила глубины не удалять, но не считать их блокером
обязательного 2D-результата.
