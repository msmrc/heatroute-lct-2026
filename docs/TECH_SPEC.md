# HeatRoute — техническое задание на веб-систему трассировки тепловых сетей

**Версия ТЗ:** 1.0 · **Дата:** 07.09.2026 · **Рабочее название:** HeatRoute (можно заменить).

**Приоритет заказчика:** сильный, тестируемый бэкенд и возможность адаптировать систему после получения данных организаторов. Веб-интерфейс — полноценный рабочий инструмент на готовой современной библиотеке компонентов, а не отдельный дизайн-проект.

Это задание на реализацию, а не описание уже существующей системы. Комплект содержит требования, контракты, демонстрационные данные и критерии приёмки. Он не содержит готового приложения и не подтверждает инженерную пригодность демонстрационных трасс.

## 0. Как читать и исполнять задание

Сначала прочитать этот документ целиком. Затем:
- `DATA_CONTRACTS.md` — данные, импорт, API, статусы и единицы.
- `UI_SPEC.md` — экраны, компоненты, состояния и взаимодействия.
- `ACCEPTANCE.md` — обязательные проверки, отрицательные сценарии и измерения.
- `IMPLEMENTATION_PLAN.md` — последовательность этапов с проверяемым результатом.
- `ORGANIZER_DATA_PLAYBOOK.md` — как подключать реальные ресурсы.
- `SOURCES.md` — первичные технические источники и границы исходных предположений.

**Обозначения объёма:**

| Приоритет | Что означает |
|---|---|
| P0 | Обязательная законченная версия: рабочий бэкенд, реальные вычисления на демо и импортируемых данных, полноценный основной веб-сценарий |
| P1 | Доработки до устойчивой расширенной версии: дополнительные форматы, локальный оптимизатор, развитая эксплуатация и представление данных |
| P2 | Инженерные и интеграционные возможности, реализация которых зависит от данных и согласованной методики |

P0 не означает «всё замокать». Синтетическими могут быть исходные объекты, но импорт, поиск, проверки, расчёт показателей, сохранение и экспорт должны реально выполняться. P1/P2 нельзя выдавать за готовые через декоративные кнопки.

## 1. Назначение и границы продукта

### 1.1. Назначение

Система помогает предварительно выбирать варианты прокладки нового коридора теплосети от перспективного здания до допустимых точек подключения к существующей или планируемой инфраструктуре.

Основной сценарий:

`проект → данные → проверка качества → сценарий подключения → расчёт → сравнение трасс → ручные ограничения → пересчёт → сохранение и экспорт`.

Выход — до трёх существенно различающихся вариантов с геометрией, выбранной точкой подключения, расчётными показателями, ограничениями, неопределённостями и воспроизводимым паспортом расчёта. Количество вариантов не гарантируется: один корректный вариант лучше трёх выдуманных.

### 1.2. Что считается результатом P0

Пользователь запускает систему, открывает демо-проект или импортирует поддерживаемый набор, выбирает здание и вход сети, задаёт сценарий, получает реально рассчитанные линии, изучает причины выбора, редактирует ограничения, пересчитывает и выгружает результат. После перезапуска сервера проект и расчёты сохраняются.

Любое вычисление доступно через API и через CLI/тест без браузера. Фронтенд не является местом хранения единственной копии расчётных правил или бизнес-логики.

### 1.3. Не обещать лишнего

P0 не является автоматизированной выдачей технических условий, заменой проектировщика, согласованием земляных работ, полноценной сметной системой или подтверждением пропускной способности сети.

Разделять четыре независимые группы выводов:
1. Геометрия соответствует выбранной модели и предоставленным ограничениям либо не соответствует.
2. Стоимость оценена полностью по выбранному каталогу, частично или не оценена.
3. Исходные сведения о возможности подключения достаточны, недостаточны или противоречат сценарию.
4. Гидравлическая/тепловая проверка выполнена, не выполнена или завершилась ошибкой.

Нельзя объединять их одним зелёным «всё проверено». Формулировка P0: **«предварительный вариант трассы по версии данных … и профилю правил …»**.

### 1.4. Решения по присланным материалам

Сохранить идею графовой модели, типовых локальных элементов, сравнения вариантов и модульного улучшения участка.

Не переносить в основное ядро:
- зависимость «больше энтропия формы — больше пропускная способность трубы»;
- расчёт инженерной мощности в битах или бит/с;
- представление любой сети только деревом;
- набор из 12 пентамино как обязательное описание реальной инфраструктуры;
- регрессию по рангу уже отсортированных значений как доказательство оптимальности;
- обещания O(1) для расчёта произвольного маршрута.

Полный граф попарных расстояний между точками не равен физическому графу соединённых труб. Поворот геометрии, перестановка идентификаторов и изменение фактических соединений — разные операции.

Экспериментальная энтропийная метрика допустима только в изолированном `research/`, выключенном по умолчанию. Она не определяет мощность, допустимость или ранжирование P0. Исходный код программ со скриншотов отсутствует; переносить из них нечего без отдельного получения и проверки лицензии.

## 2. Принципы архитектуры

### 2.1. Бэкенд как самостоятельный продукт

Бэкенд — модульный монолит с отдельными процессами API и вычислительных workers. Не начинать с микросервисов, Kubernetes, Kafka или распределённого графового движка. Границы модулей и контракты должны позволить выделить тяжёлый компонент позже без смены публичного API.

```text
React / Vite / shadcn/ui / MapLibre
                │ HTTPS, REST, SSE
                ▼
      FastAPI: доступ, контракты, оркестрация
                │
        application use cases
                │
     domain: сценарии, правила, графы, оценки
          │                         │
          ▼                         ▼
  PostgreSQL + PostGIS        Celery workers
  версии, объекты, задачи     импорт / поиск / экспорт
          │                         │
          └────────┬────────────────┘
                   ▼
          ArtifactStorage interface
          local files → S3-compatible
```

Redis используется как брокер/оперативный кэш, но не как единственное хранилище результатов и статусов. Долговечное состояние задач — PostgreSQL.

Разделение тяжёлых вычислений и API соответствует рекомендованному FastAPI подходу для задач такого класса [S03]; семантика повторной доставки и идемпотентность должны учитываться отдельно [S04].

### 2.2. Направление зависимостей

`transport → application → domain`.

Инфраструктурные реализации подключаются через явные интерфейсы. Domain не импортирует FastAPI, Celery и ORM-модели. Геометрические вычисления могут использовать Shapely/NumPy, но код маршрутизации не читает файлы организаторов, не делает HTTP-запросы и не запускает SQL изнутри каждой релаксации ребра.

Роутер API валидирует запрос, проверяет доступ, вызывает use case и возвращает DTO. Не размещать в роутере построение графа, GDAL-импорт или расчёт стоимости.

### 2.3. Фиксированный базовый стек

| Слой | Решение |
|---|---|
| Backend runtime | Python 3.12 как консервативная стартовая цель; смена через ADR после проверки геозависимостей |
| API и валидация | FastAPI, Pydantic 2, Uvicorn |
| База | PostgreSQL + PostGIS; стартовая совместимая целевая ветка PostgreSQL 17, конкретный PostGIS выбирается и фиксируется при bootstrap |
| Доступ к БД | SQLAlchemy 2, GeoAlchemy2, Alembic, psycopg 3 |
| Геометрия и проекции | Shapely 2, pyproj, NumPy; Pyogrio/GDAL для файловых адаптеров |
| Поиск | Собственный небольшой A*/Dijkstra над единым GraphProvider; NetworkX как эталон на малых тестовых графах |
| Долгие задачи | Celery + совместимый Redis, отдельные очереди ingest/compute/export |
| Объектные файлы | LocalArtifactStorage в P0; S3ArtifactStorage в P1 без изменения домена |
| Frontend | React + TypeScript strict + Vite; React Router |
| UI | shadcn/ui из официального источника, Tailwind CSS 4, Lucide, Sonner |
| Состояние UI | TanStack Query для серверных данных, Zustand только для локального состояния карты/панелей |
| Формы и таблицы | React Hook Form + Zod, TanStack Table |
| Карта | MapLibre GL JS; GeoJSON в P0, MVT для крупных слоёв в P1 |
| Тестирование | pytest, Hypothesis, integration tests с PostGIS; Vitest и Playwright |
| Сборка и запуск | uv, pnpm, Docker Compose; CI |

React/Vite/shadcn — выбранный стек, а не приглашение сравнивать десять библиотек. Официальные инструкции подтверждают поддержку Vite и Tailwind 4 [S01–S02]. MapLibre отвечает за визуализацию, не за окончательное инженерное решение [S05].

При bootstrap проверить совместимость конкретных стабильных версий, зафиксировать lockfiles и версии образов. Не использовать неприкреплённый `latest` в поставляемом Compose. Не утверждать, что приведённая целевая матрица уже проверена реальной сборкой.

Синхронный SQLAlchemy допустим и предпочтителен для первоначальной простоты: API использует обычные sync handlers с ограниченными запросами, workers — собственные sessions. Не блокировать event loop синхронным GDAL/SQL. Не смешивать async и sync sessions случайным образом.

## 3. Предметная модель и версии

Полные поля и API — в `DATA_CONTRACTS.md`.

Обязательные агрегаты: Workspace, User, Project, Dataset, DatasetVersion, LayerVersion, Feature, CoverageArea, MappingProfile, RuleProfileVersion, CostCatalogVersion, Scenario, ScenarioRevision, CalculationRun, RouteAlternative, RouteSegment, Finding, JobEvent, ExportArtifact, AuditEvent.

Сеть дополнительно содержит NetworkNode, NetworkEdge, ConnectionCandidate и, при наличии данных, сведения о контурах подачи/обратки, источниках и параметрах мощности.

### 3.1. Неизменяемые срезы

Опубликованная версия данных, правил и цен не редактируется на месте. Правка создаёт новую версию. Сценарий также имеет revisions. CalculationRun ссылается на точные идентификаторы версий, а не на `latest`.

Паспорт расчёта включает версии данных, mappings, правил и цен, ревизию сценария, целевую дату, CRS и преобразование, алгоритм и версию кода, seed, конфигурацию точности, лимиты, перечень предположений, содержательные hashes и время расчёта.

Изменение текущих данных не перезаписывает старую трассу. UI обозначает старый результат как «рассчитан по предыдущей версии» и предлагает отдельный новый run.

### 3.2. Временная модель

Различать `observed_at` — когда получены/зафиксированы сведения, `valid_from`/`valid_to` — период применимости, `lifecycle_status` — существующий, планируемый, выведенный, неизвестный.

Сценарий имеет `planning_date`. Планируемый объект не становится действующим автоматически. Включение его в будущую модель требует явного temporal policy и, если дата доступности неизвестна, сохраняемого предположения. Нельзя объединить срезы из разных лет и молча назвать их текущими.

### 3.3. Отсутствующие и противоречивые сведения

`null` не означает 0; отсутствующий диаметр не означает стандартный диаметр; неизвестная мощность не означает неограниченную.

Числовое значение при необходимости сопровождается происхождением: `provided`, `derived`, `assumed`, `unknown`, `conflicting`. Последние два не превращаются в положительную проверку.

Не вычислять «достоверность 97%» без определённой и проверенной статистической модели. Показывать конкретные пробелы, участки неопределённости и состав выполненных проверок.

### 3.4. Единицы

Внутренние геометрические вычисления — в метрах в проектной CRS. Нагрузки — kW, диаметры/глубины — m, давление — Pa, температуры API — °C с явным переводом в K для моделей, которые этого требуют. Денежные расчёты — Decimal с заданной валютой, базой цен и политикой налогов. В JSON деньги передавать строкой.

Преобразования единиц задаются mapping-профилем. Для неоднозначных единиц (например, разновидностей calorie) требуется подтверждённый коэффициент и ссылка на его основание. Не гадать по названию столбца.

## 4. Интеграция данных — ключевой backend-модуль

### 4.1. Три слоя хранения

**Raw:** неизменённые загруженные файлы, hash, имя, MIME, размер, источник, права использования, timestamp. Raw не является веб-публичной директорией.

**Staging:** разобранные слои, предварительное сопоставление, диагностика CRS, geometry issues, ошибки типов, непринятые строки. Не участвует в расчётах до публикации.

**Canonical:** опубликованные нормализованные версии, пригодные для доменных сервисов. Содержит трассируемую связь каждого объекта с raw/staging-источником.

### 4.2. Pipeline P0

`upload → inspect → map → validate → preview/report → confirm publish → canonical snapshot → indexes → available for scenarios`.

Каждый этап возобновляемый и идемпотентный. Публикация атомарная: либо доступна целая версия, либо она остаётся staging. Карантин плохих объектов не означает автоматическое объявление отсутствующих ограничений безопасными.

### 4.3. Форматы

P0: GeoJSON FeatureCollection и GeoPackage, выбор слоя, CSV с явно указанными coordinate columns или WKT для справочников/точек. Поддерживаемая геометрия строго перечисляется в capabilities.

P1: zipped Shapefile с проверкой обязательных частей, GeoParquet, дополнительные CSV-справочники и повторное применение mappings.

P2: согласованные CAD/BIM/3D форматы, WFS/OGC API/институциональные API и прямые источники БД через отдельные адаптеры. Не обещать импорт DWG, IFC, CityGML и произвольной 3D-модели только потому, что существует GDAL.

Pyogrio/GDAL используются для перечисленных векторных форматов [S11–S12], но доменная валидация остаётся задачей приложения.

### 4.4. Mapping profile

Профиль задаёт слой-источник, целевой тип, ID, связь концов сети, поля, типы, допустимые значения, единицы, source CRS, missing policy и безопасные transforms.

Разрешённый язык transformations — ограниченный перечень операций (`rename`, `trim`, `parse_decimal`, `enum_map`, `unit_convert`, `date_parse`, `constant`). Никаких `eval`, пользовательского Python, SQL, импортов кода и shell-команд.

Профиль версионируется, проверяется на sample, затем на всех объектах. Повторное применение к новой поставке строит отчёт added/changed/deleted/unmapped и не перезаписывает старый snapshot.

### 4.5. Геометрические проверки

Проверить CRS, диапазоны координат, finite numbers, пустые геометрии, типы, самопересечения, кольца, дубликаты source_id, длины, точки входа и ссылки на network nodes.

Исправление через MakeValid допускается только как явно выбранная операция с оригиналом, исправленной геометрией и отчётом изменений. Не применять `buffer(0)` ко всему массиву молча. Преобразование Polygon в MultiPolygon или распад объекта требуют отражения в отчёте.

Сложную геометрию можно упрощать для отображения; расчётная геометрия отдельно хранится и не подменяется визуальной.

### 4.6. Покрытие территории

Хранить coverage polygons по типам данных и периоду: `known_complete`, `partial`, `unknown`, `synthetic` — утверждения в рамках источника, а не объективная гарантия отсутствия коммуникаций.

Ноль найденных объектов в bbox не означает, что территория обследована и свободна. Отсутствие слоя или его coverage — отдельный Finding. Выход трассы за допустимую исследуемую область запрещается либо явно фиксируется в exploratory-режиме согласно профилю.

### 4.7. Контракт адаптера

```python
class DatasetAdapter(Protocol):
    def inspect(self, source: RawArtifactRef) -> InspectionReport: ...
    def read_batches(self, source: RawArtifactRef, mapping: MappingProfile,
                     batch_size: int) -> Iterator[CanonicalFeatureBatch]: ...

class ArtifactStorage(Protocol):
    def put(self, stream: BinaryIO, metadata: ArtifactMetadata) -> ArtifactRef: ...
    def open(self, ref: ArtifactRef) -> ContextManager[BinaryIO]: ...
```

Это проектные интерфейсы, а не готовая реализация. При приходе новых файлов изменяется адаптер/mapping и тесты. Если появляются новые предметные сущности или физические правила, дорабатывается соответствующий модуль через ADR; универсальное обещание «изменится только импорт» запрещено.

## 5. Пространственная основа и существующая сеть

### 5.1. CRS

Raw CRS хранить вместе с исходными данными. Для опубликованных объектов хранить canonical geometry в EPSG:4326 для API/карты и проектную metric representation либо воспроизводимый metric cache для вычислений.

На одном расчёте все вычислительные геометрии имеют одну подтверждённую метрическую CRS. Один проект не смешивает несколько SRID в расчётной таблице без явной стратегии. Для нестандартной местной системы допустим WKT/PROJJSON с подтверждёнными параметрами и локальной регистрацией в PostGIS.

GeoJSON API следует RFC 7946: longitude, latitude; не выдавать внутренние метровые координаты за GeoJSON [S09]. Если старый «GeoJSON» содержит произвольную CRS, это legacy adapter с явным назначением source CRS, а не стандартный endpoint.

EPSG:3857 используется для отображения/тайлов, не как универсальная метрическая инженерная плоскость. Для преобразований задавать порядок осей явно и сохранять выбранный operation и точность; не подменять отсутствующие transformation grids тихим приблизительным преобразованием [S08].

В демо используется EPSG:32637 и полностью синтетическая геометрия. Это не рекомендация CRS для будущего массива Москвы.

### 5.2. Два различных графа

**NetworkGraph:** фактические/проектные соединения труб и узлов, их параметры и происхождение топологии.

**RoutingGraph:** допустимые перемещения нового коридора в пространстве с учётом препятствий, направления, способа прокладки и правил.

Теплосеть может содержать циклы и параллельные участки. Не хранить её как дерево по умолчанию. Топология не выводится из картинки карты.

### 5.3. Связность сети

Приоритет — предоставленные `from_node_id`/`to_node_id` и подтверждённые точки соединения. Геометрическая близость может создать предложение по исправлению, но не скрытое инженерное соединение.

Пересечение двух линий в 2D не создаёт junction. Совпавшие XY с разными отметками/контурами также не объединяются автоматически. Все операции snapping имеют tolerance, причину, provenance и отчёт.

Проверить dangling edges, дубли, нулевые длины, endpoints, изолированные компоненты, ошибочно смешанные supply/return, неоднозначные пересечения. Наличие цикла само по себе не ошибка.

### 5.4. Подача и обратка

Результат геометрического P0 — **ось строительного коридора**, а не обязательно одна физическая труба. У сценария есть `circuit_layout`: `paired`, `single`, `unknown`.

`route_length_m` — длина коридора. `supply_pipe_length_m` и `return_pipe_length_m` — отдельные количества, если задано основание их расчёта. Длина пары может оцениваться как 2L только как явно указанный упрощённый quantity model; земляные работы и переходы нельзя автоматически удваивать вместе с ней.

Гидравлическая модель позже представляет подачу и обратку отдельными связными контурами с теплообменом в соответствующих точках, а не одной линией неопределённого смысла.

## 6. Профили правил и независимая валидация

### 6.1. Структура правил

Каждое правило имеет ID, версию, название, тип, область действия, параметры, единицы, severity, missing-data policy, provenance, approval_status и machine-readable reason_code.

Типы P0: `hard_exclusion`, `clearance`, `coverage_required`, `crossing_allowed_only_via_portal`, `candidate_eligibility`, `temporal_availability`, `soft_exposure`.

Правила — данные, а evaluators — типизированный исполняемый код. Нельзя загрузить произвольный код вместе с профилем. Некорректный/неподдерживаемый тип правила не игнорируется.

Профили: `demo` (синтетический), `draft` (не подтверждён), `reviewed` (согласован уполномоченным специалистом в продукте). `reviewed` не означает государственную экспертизу.

### 6.2. Коридор, а не тонкая линия

Проверять swept corridor всей трассы и каждого специального перехода. Для простого участка — буфер оси на половину полной ширины коридора. Если препятствие уже расширено на минимальный отступ, не прибавлять тот же отступ второй раз без основания.

Формально для обычного участка: `corridor = buffer(centerline, corridor_width/2)`; запрещённое множество — `buffer(obstacle, required_clearance)`. Проверяется их пересечение с явно заданной политикой касания и tolerance.

Край исследуемой области, вогнутые препятствия, узкие проходы и диагональные переходы тоже проверяются по полной геометрии. ST_Buffer — 2D-операция и не подтверждает вертикальное расхождение [S06].

### 6.3. Точка входа в целевое здание

Поиск ведётся до назначенного entry point на разрешённой границе здания. Специальный короткий entry connector может пересекать отступ только у целевого здания в указанной entry gate area; сам footprint посторонних зданий не исключается из запретов.

Не выключать всё здание из препятствий, иначе путь может пройти через него насквозь. У connector есть проверенное направление подхода, длина, геометрия, ссылка на entry, и он включён в длину/стоимость результата.

### 6.4. Неизвестные данные

`strict` — критически неизвестный параметр/coverage блокирует соответствующую проверку или маршрут согласно профилю; статус `insufficient_data`, не «нет препятствий».

`exploratory` — разрешены только перечисленные assumptions, каждый записан, показан на карте и в отчёте. Жёсткий подтверждённый запрет не превращается в штраф ни в одном режиме. Exploratory не снимает административное ограничение автоматически.

### 6.5. Findings

Finding содержит `code`, `severity`, `check_status`, связанные features/rules, geometry location, измеренное и допустимое значение с единицами, причину, missing fields, remedy и источник.

Примеры: `BUILDING_CORRIDOR_INTERSECTION`, `ROAD_CROSSING_WITHOUT_PORTAL`, `UTILITY_DEPTH_UNKNOWN`, `CRS_UNCONFIRMED`, `CANDIDATE_PERMISSION_UNKNOWN`, `CAPACITY_NOT_PROVIDED`, `OUTSIDE_DATA_COVERAGE`, `MODEL_RESOLUTION_LIMIT`.

### 6.6. Независимый RouteValidator

Финальную трассу проверяет отдельный сервис по canonical geometry и выбранному RuleProfile, а не по закэшированному флагу «ребро проходимо». Одна и та же библиотека предикатов может использоваться повторно, но validation pass независим от маршрута поиска.

Проверять исходную трассу, сглаженную, локально оптимизированную и вручную изменённую версии. Не сохранять отредактированную линию как успешно проверенную со старым validation report.

## 7. Точки подключения и исходные условия

### 7.1. Формирование кандидатов

Источники кандидатов: подтверждённые узлы подключения, предоставленные разрешённые зоны/сегменты подключения или явно указанные пользователем точки с отмеченным статусом.

Не считать все точки существующей линии разрешёнными для врезки. Для вычисления сначала фильтровать по жизненному циклу, пространственной области, permissions, доступным ограничениям мощности и применимости контура, затем строить connector.

Каждый отброшенный кандидат сохраняет причину. Ограничение числа кандидатов или радиуса — часть паспорта расчёта; оно ограничивает область поиска, поэтому результат не называется глобально оптимальным по всей сети.

### 7.2. Нагрузка и мощность

Для геометрического режима тепловая нагрузка может быть неизвестна; это отключает capacity screening и гидравлическую проверку, а не устанавливает нагрузку в 0.

`requested_load_kw` должен сопровождаться источником. `available_capacity_kw` у кандидата — предоставленное значение с датой, областью применимости и пояснением, учтены ли резервы. Если reserves представлены отдельно, не вычитать их второй раз из уже net-значения.

Сравнение нагрузки с предоставленным резервом — предварительный фильтр, не полноценная гидравлическая проверка. Не суммировать автоматически резервы разных несвязанных источников.

Пакетное присоединение нескольких зданий с общими ограничениями мощности — P2; нельзя выдавать независимо рассчитанные подключения за совместно допустимый план.

### 7.3. Способы прокладки и пересечения

Сценарий задаёт разрешённые construction methods. Дорога не является просто «очень дорогой травой»: для управляемого пересечения нужен разрешённый crossing portal/macro edge с входом, выходом, footprint, методом, стоимостью и условиями.

В P0 дороги, требующие специальных переходов, блокируют обычные шаги графа. Разрешение действует только на именованный объект дороги и конкретный проверяемый портал. Оно не разрешает одновременно пересечь здание или другую сеть внутри того же footprint.

Глубина/отметки при отсутствии данных остаются неизвестными. Отрисовка трубы ниже земли не является инженерной проверкой.

## 8. Расчётное ядро

### 8.1. Pipeline одного CalculationRun

1. Создать immutable snapshot запроса и всех ссылок на версии.
2. Проверить доступность данных, правил, CRS и required capabilities.
3. Построить AOI из исходной точки, кандидатов и ограниченного буфера.
4. Получить metric geometry, spatial indexes и coverage.
5. Отфильтровать connection candidates и проверить connector geometries.
6. Подготовить constraints и graph provider.
7. Выполнить поиск по выбранным objective profiles в рамках budget.
8. Построить дополнительные существенно отличающиеся варианты.
9. Независимо проверить геометрию и допущения каждой альтернативы.
10. Выполнить безопасное упрощение/локальные замены и повторить проверки.
11. Пересчитать quantities, стоимости, exposures и candidate screening.
12. Удалить дубли/доминируемые альтернативы согласно критериям и сохранить outcomes.
13. Записать findings, паспорт, statistics, завершить job и выпустить события.

У каждого этапа — прогресс по известной единице работы или честный неопределённый progress, timing и diagnostic code.

### 8.2. GraphProvider

P0 — адаптивно ограниченный пространственный граф на сетке с неявным раскрытием соседей. Не материализовать полный NetworkX-граф всей территории города.

Базовое состояние:

```text
(cell_x, cell_y, heading, construction_mode, waypoint_index)
```

Возможные значения heading — 8 направлений плюс специальное стартовое состояние. Набор допустимых поворотов и способы прокладки задаются профилем. Учитывать требуемое продолжение после портала/элемента. Направление не декоративно: оно нужно для стоимости и допустимости поворотов.

Длинные переходы, entry/connectors и crossings — отдельные типизированные edges с полной проверкой геометрии. Для обычных 8-соседних переходов исключить corner cutting. Если форма элемента имеет footprint, проверять его, а не только соединяющий отрезок.

Spatial index/STRtree используется для выбора потенциальных препятствий, после чего выполняется точный предикат. Попадание bbox само по себе не конфликт [S07].

Граф должен поддерживать ordered waypoints без склеивания независимо найденных отрезков, теряющего направление на стыке. В P0 максимум 10 пользовательских waypoints; лимит конфигурируется.

### 8.3. Точность и пределы

Resolution, геометрическая tolerance, snap tolerance и допустимый AOI задаются явно и сохраняются. Параметры не подбираются молча, чтобы обязательно получить зелёную линию.

Если coarse search не нашёл путь, возможен ограниченный уточняющий поиск с меньшим шагом в той же области. Уточнение и затраченный budget отражаются в metadata. Отсутствие пути в дискретной модели не доказывает невозможность прокладки в реальном непрерывном пространстве.

Сообщения различаются: `NO_ROUTE_IN_MODEL`, `INSUFFICIENT_DATA`, `NO_ELIGIBLE_CANDIDATES`, `COMPUTATION_BUDGET_EXCEEDED`, `INVALID_INPUT`. Timeout не превращается в «маршрута нет».

### 8.4. Алгоритмы

Dijkstra — обязательный baseline. A* — ускоренный поиск с admissible heuristic и возможностью перехода к h=0. На одинаковом малом графе A* и Dijkstra должны давать одинаковую минимальную стоимость с учётом tolerance [S10].

Для длины допустима евклидова нижняя оценка до ближайшей допустимой цели. Для стоимости — расстояние × доказанная минимальная стоимость метра; если такую границу нельзя гарантировать, h=0. Для лексикографической политики неопределённости в P0 использовать корректный Dijkstra/эквивалентный label-setting, не придумывать эвристику.

Все edge costs неотрицательны. Любые бонусы «предпочтительного коридора» реализуются снижением до неотрицательной базовой стоимости или отдельным критерием, но не отрицательными рёбрами.

Нельзя заявлять оптимальность после approximate search, penalties для разнообразия, ограничения кандидатов, времени или coarse-to-fine без доказательства применимости. Сохранять `optimality_scope` и `search_completion`.

### 8.5. Целевые профили P0

**shortest:** минимизация полной длины коридора; при равенстве — фиксированное детерминированное разрешение ничьей. Стоимость и findings всё равно рассчитываются отдельно.

**estimated_cost:** минимизация моделируемой строительной стоимости. Доступен как экономическое сравнение только при полноте обязательных ставок и выбранной методики quantities; отсутствующие ставки не равны нулю.

**least_unverified:** лексикографически минимизировать допускаемую в exploratory-режиме длину в областях неподтверждённых данных, затем моделируемые события, требующие проверки, затем длину. Это не вероятность аварии. Известные hard restrictions остаются запрещёнными.

В P1 можно добавить weighted profile:

`J = wL·L/Lref + wC·C/Cref + wU·U/Uref + wB·B/Bref`.

Нормировочные величины фиксируются до расчёта в версии профиля. Они положительные, не зависят от уже получившегося списка альтернатив; разные единицы не складываются напрямую. UI не даёт пользователю отключить hard restrictions весами.

### 8.6. Связь search cost и финальной оценки

Стоимость перехода должна соответствовать quantities выбранной конструкции. Постоянная стоимость пересечения начисляется на macro edge один раз на физическое событие, а не на каждый пиксель внутри дороги. Смена покрытия делит участок на неперекрывающиеся интервалы.

Если дополнительный финальный показатель не является аддитивным и не учтён в search state, он может использоваться только для reranking найденных кандидатов. Тогда результат явно имеет `candidate_reranking`, а не гарантию оптимума по этому показателю.

После сглаживания, изменения числа элементов или локальной оптимизации пересчитать стоимость с нуля. Объяснения строить из финальных quantities, не из старых edge costs.

### 8.7. Альтернативы

Сначала получить решения разных объективов/кандидатов. При необходимости сформировать дополнительный bounded pool через штрафы за повторное использование выбранных коридоров или ограниченный k-shortest на небольшом графе. Penalty входит только во вспомогательный поиск, а не в показываемую строительную стоимость.

Дедупликация — по симметричному overlap buffered centerlines с фиксированным tolerance и по connection candidate. Например, в демо считать почти одинаковыми коридоры с overlap > 0.90; порог — параметр, не универсальная норма.

При сравнении разных длин использовать пересечение / минимум площади двух буферов и дополнительную проверку endpoints; короткий полностью вложенный фрагмент не должен ошибочно считаться полноценной альтернативой для другого подключения. Метрика и её ограничения документируются.

Не представлять совпавшие результаты разных целей как три разные трассы. UI может показать одну трассу с несколькими objective badges.

### 8.8. Постобработка

P0: удаление избыточных коллинеарных точек и проверенный line-of-sight shortcut с учётом допустимых углов и corridor footprint. Нельзя применять визуальное spline-сглаживание и сохранять его как расчётную трассу без проверки.

P1: библиотека straight/bend/detour/crossing primitives. Локальная замена сохраняет вход, выход, направления и обязательные соединения, не создаёт новые ответвления. Затем повторная геометрическая, количественная и при наличии инженерная проверка. Сохранить before/after и измеримый эффект.

Реализация не привязана к пяти квадратам. Отдельный T-/X-узел допустим только при реально заданном ответвлении и подходящих условиях, а не ради структурного показателя.

### 8.9. Воспроизводимость

Детерминированный порядок features/candidates/neighbors, stable tie-break, фиксированный seed генераторов и параметры точности. На одном наборе версий и одинаковом завершённом search budget результат должен совпадать в пределах документированной tolerance.

Ранний останов по wall clock может изменить найденный partial pool: это указывается отдельно. Не обещать побитовое совпадение на разных GDAL/GEOS/CPU без специального контракта. В паспорт включить версии геобиблиотек.

## 9. Количества и стоимость

### 9.1. Quantities отдельно от цен

Quantity engine формирует ведомость: длина коридора, длина каждого трубопровода по принятой модели, длины способов прокладки/покрытий, площадь восстановления при заданной ширине, количество переходов, узлов, поворотов и иных моделируемых элементов.

Каждая позиция имеет quantity, unit, geometry/segment reference, measurement_method, assumptions. Пустое значение не заменяется нулём.

Ценовой каталог имеет currency, price_date, region_scope, tax_policy, estimate_status, rates и exclusions. Ставки только из версии каталога. Демо-ставки вымышленные и помечаются на экране и во всех отчётах.

### 9.2. Арифметика

`subtotal = Σ(quantity_i × rate_i)` по неперекрывающимся работам. Коэффициенты/надбавки применяются с явно заданной базой, без скрытого повторного наложения. Округление до минимальной денежной единицы по определённой политике; расчёт Decimal, не float.

Недостающая цена даёт `cost_status=partial` и список `unpriced_items`, а не 0 рублей. Интервал min/max допускается только при заданных нижних/верхних ставках или сценарных допущениях; это не «доверительный интервал» без статистического основания.

Показывать стоимость отдельной трубы, пары и земляных работ раздельно. Не удваивать crossing lump sum вместе с двумя трубами, если он уже оценён за парный коридор.

### 9.3. Экономия

Сравнение допускается для одной задачи, с одним набором правил, версии цен, нагрузкой, набором учитываемых работ и временным сценарием. Базовый вариант должен быть допустимым в той же модели.

`delta = baseline_cost − alternative_cost`; процент только при baseline_cost > 0 и сопоставимой полноте оценки. Подписывать «разница предварительных оценок», не обещать фактическую экономию строительства.

## 10. Инженерный модуль — расширение, а не имитация

P0: зарегистрированная capability с корректным `not_performed`/`insufficient_data`; интерфейс обязательных входов и отчёт missing fields. Возвращать фальшивый результат расчёта запрещено.

P2: адаптер `EngineeringValidator`, например к pandapipes, после согласования методики и получения входов. Библиотека предусматривает гидравлическую и тепловую процедуру [S13–S14], но её подключение само по себе не подтверждает корректность предметной модели.

Входы могут включать реальные соединения сети, подачу/обратку, диаметры и длины, шероховатость/материал, местные сопротивления, нагрузки, свойства теплоносителя, источники/насосы, давления и температуры, граничные условия, отметки и теплопотери. Точный required set определяется версией выбранной модели.

Результат: convergence_status, mass/energy balance diagnostics, значения на узлах/рёбрах, превышения согласованных порогов, версия solver, исходные assumptions. Отсутствие сходимости — не `passed` и не инженерное доказательство невозможности подключения.

Не выводить диаметр из энтропии; не считать единственное сравнение requested/available capacity полной гидравликой. Не выдумывать физические параметры для получения красивого результата.

## 11. Задачи, очереди и надёжность

P0: импорт, построение графа/маршрутов и экспорт выполняются в workers, API возвращает 202 и job/run ID. HTTP-запрос не удерживается до окончания расчёта.

### 11.1. Состояния

`queued → running → succeeded | partial | failed | cancelled`; дополнительно `cancel_requested` перед остановкой. Job transport state отдельно от run outcome (`routes_found`, `no_route_in_model`, `insufficient_data`, `budget_exceeded`, `invalid_input`). Задача может успешно вычислить отсутствие пути в текущей модели.

Хранить phase, progress_current/total с единицей, timings, heartbeat, attempt, error_code, retryable и sanitized error context. Stacktrace доступен только разработчику в логах, не пользователю.

### 11.2. Идемпотентность и доставка

POST расчёта поддерживает `Idempotency-Key`. Повтор одинакового запроса с тем же ключом возвращает прежнюю операцию; другой body с тем же ключом — 409. Ключ ограничен workspace/user и TTL, documented.

Создание run и outbox event — одна DB transaction. Publisher публикует pending outbox в брокер с retry. Worker получает ID, атомарно захватывает lease и проверяет, не завершён ли run. Повторная доставка не создаёт дубликаты alternatives/exports.

Настроить Celery acknowledgement, retries и Redis visibility timeout согласованно с максимальным временем задач; не считать `acks_late` достаточным механизмом exactly-once [S04]. Желаемая семантика — at-least-once с идемпотентными эффектами.

### 11.3. Отмена и лимиты

Кооперативная отмена проверяется между этапами и регулярно при поиске. Частота проверки настраиваемая и измеряется. Force kill не является основным пользовательским механизмом.

Budget содержит max_wall_time_s, max_expanded_states, max_memory_mb, max_candidates, max_alternatives. На превышении сохранить диагностируемый partial outcome, только если есть независимо валидированные варианты. Не выставлять optimality complete.

Progress события имеют sequence ID и сохранённую историю. SSE поддерживает reconnect/Last-Event-ID; polling fallback обязателен. Полные GeoJSON не передаются в каждом progress event.

### 11.4. Кэш

Ключ derived graph/cache включает project/workspace, dataset/layer versions, AOI, CRS/transformation, rule profile, width, construction modes, temporal policy, precision и algorithm version. Cached run result дополнительно включает scenario revision, objectives, costs и все влияющие assumptions.

Изменение входов не возвращает старый результат по случайно совпавшему bbox. Межпроектное раскрытие geodata через общий ключ кэша запрещено.

## 12. API, доступ и хранение

REST `/api/v1`, OpenAPI — единственный контракт для генерируемого TypeScript-клиента. Versioned request/response DTO, единообразные ошибки, pagination и пространственные фильтры обязательны. Основные endpoints приведены в `DATA_CONTRACTS.md`.

### 12.1. Доступ

P0: один или несколько workspace, локальная аутентификация, роли viewer/editor/admin; project membership проверяется на каждом ресурсе. Development demo login разрешён только при explicit env flag и localhost/dev deployment; production не должен запускаться с фиксированными общедоступными credentials.

Для web — серверная сессия в HttpOnly cookie, secure в production, SameSite и CSRF-защита для изменений. Не хранить долгоживущие административные токены в localStorage. CLI service tokens при необходимости ограничены scope и хранятся сервером в хэшированном виде.

P1: интеграция OIDC через адаптер без изменения domain use cases. Не реализовывать самодельный OAuth-сервер.

### 12.2. Файлы и инъекции

Allowlist форматов, проверка content и размеров, ограничения распакованного архива/числа файлов/сложности геометрии, защита от zip slip/symlinks, изолированные worker temp directories [S15].

Для GDAL не принимать пользовательские SQL, connection strings, VSI paths и произвольные remote URLs. Upload pipeline работает с локальными raw artifacts. Network egress парсера по умолчанию отключён; загрузка SQLite extensions запрещена. Потенциально опасные библиотечные драйверы не включать «все сразу».

Содержимое атрибутов отображается как текст; без raw HTML и выполнения Markdown/JavaScript. Выгрузка CSV нейтрализует spreadsheet formula injection. Имена колонок mapping — данные, не SQL identifiers без безопасного контроля.

### 12.3. Конфиденциальность

Реальные инженерные геоданные не отправляются в LLM, аналитику, сторонние tile APIs или error trackers без отдельного разрешения. P0 не требует LLM/API-ключей вообще.

Подложка карты — заменяемый provider. Демо работает без внешней сети на нейтральном фоне с собственными синтетическими объектами. Внешние карты подключаются отдельно с выполнением лицензии и attribution; камера/viewport сами по себе могут раскрывать район работы, это нужно учитывать.

3D, fonts, icons и стили не должны зависеть от внешнего CDN в offline-demo. MapLibre renderer не означает наличие прав на сторонние тайлы.

## 13. Веб-версия и UI

Подробная спецификация — `UI_SPEC.md`. Основной экран — desktop GIS workspace, не лендинг.

Обязательные экраны P0: список проектов, мастер загрузки, данные/качество, карта-сценарий, сравнение вариантов, паспорт расчёта, каталог правил/цен в режиме просмотра и безопасного редактирования, задачи и история.

Готовая UI-база: shadcn/ui; локальный `packages/ui` с токенами, обёртками и согласованными variant. Не переписывать Button/Dialog/Table ради уникальности. Дизайн должен быть пригоден «как есть» и допускать замену токенов/компонентов без изменений domain/API.

Карта занимает основную площадь. Слева сценарий/слои, справа properties/findings, снизу alternatives/jobs. Панели изменяемого размера и сворачиваемые. Доступность keyboard/labels/focus, таблица результатов как альтернатива исключительно визуальному выбору обязательны.

Фронтенд показывает фактические backend capabilities и статусы. Отсутствующая гидравлика отображается «не выполнялась», не фальшивым датчиком. Запрос пересчёта всегда создаёт новую ревизию/run, если изменились значимые входы.

## 14. Экспорт и обмен

P0: GeoJSON трасс/коридоров/findings, CSV ведомости/показателей, JSON паспорта расчёта, самодостаточный HTML-отчёт с print stylesheet. Формирование — server-side по immutable run. Пользователь может печатать HTML, но это не обещание серверного PDF в P0.

P1: GeoPackage с отдельными слоями; серверный PDF по готовому HTML после внедрения и тестов рендеринга; импорт scenario package для воспроизведения на доступных версиях данных.

Отчёт содержит исходную задачу, идентификаторы версий, правила/цены и статус их согласования, картографическую схему, выбранного кандидата, таблицу вариантов, quantities, стоимость/пропуски, findings, непроведённые проверки, assumptions, пределы поиска, timestamp и автора.

Синтетическое происхождение сохраняется во всех форматах. Экспорт не должен превращать «предварительно» в «согласовано». Raw исходники в пакет не включаются без explicit choice и проверки права экспорта.

## 15. Производительность и эксплуатация

Приведённые цифры — целевые бюджеты для проверки, не результаты уже проведённых замеров. После этапа M3/M4 выпустить benchmark report, затем скорректировать лимиты через ADR.

Reference host: 4 vCPU, 16 GB RAM, SSD; один compute worker, ограниченный 4 GB; API и БД в том же Compose. Замеры включают описание данных, resolution, cold/warm cache и versions.

- Малый демо-район 600×400 m, шаг 5 m, до 100 препятствий, 2–5 кандидатов: целиться в ≤ 10 s для законченного run с несколькими objectives при warm cache.
- Средний тест 1 km², шаг 4 m, до 1 000 препятствий: первоначальный run budget 120 s; max states/memory ограничены, partial outcomes честно показаны.
- Обычные metadata API: ориентир p95 ≤ 500 ms локально без тяжёлого импорта; job enqueue не ждёт вычислений.
- Отображать большие слои через bbox/limits, в P1 — MVT [S16]. Не отдавать мегабайты невидимых объектов при каждом перемещении карты.

Отдельно измерять ingest, indexing, graph preparation, search, validation, cost, export, peak memory. Не оптимизировать вслепую на фиктивных цифрах.

P0 операции: health/live, health/ready, structured JSON logs, request_id/run_id, базовые metrics, migrations, persistent volumes, readiness checks, ограничение очередей и graceful shutdown.

P1: автоматические backups Postgres+raw artifacts с проверкой восстановления, retention policy, Prometheus/OpenTelemetry integration и нагрузочные профили. Для production эти эксплуатационные требования должны быть закрыты до хранения значимых реальных данных.

## 16. Тестирование и критерий готовности

Детали в `ACCEPTANCE.md`. Обязательные группы:
- unit/property tests геометрии, единиц, costs, objective policies и topology;
- сравнение A*/Dijkstra на одинаковых малых графах;
- реальные integration tests с PostGIS, worker, брокером и storage;
- contract tests API и generated client;
- E2E: импорт → расчёт → изменение ограничения → пересчёт → экспорт → reload;
- security/access tests и импорт некорректных файлов;
- deterministic fixtures, no-route/unknown-data/budget outcomes;
- regression suite для смены mapping/rules/data versions.

Нельзя считать этап завершённым на основании screenshot интерфейса или успешной сборки без расчётных тестов. P0 принимается только при прохождении backend и сквозных критериев, а не по количеству готовых страниц.

## 17. Поставляемый результат реализации

Репозиторий с исходниками, рабочий Docker Compose, `.env.example` без секретов, зафиксированные зависимости, migrations, seed demo, generated API client, тесты, benchmark report, инструкции запуска и восстановления, OpenAPI, ADR и описание ограничения возможностей.

Обязательные команды/эквиваленты, которые Codex должен реализовать и проверить:

```bash
make bootstrap
make up
make migrate
make seed-demo
make test
make test-integration
make test-e2e
make benchmark-demo

```

Команды в этом ТЗ — контракт будущей реализации; они не существуют только от наличия документа.

Первый вертикальный срез должен появиться раньше расширенного интерфейса: HTTP/CLI запуск → worker → реальный поиск вокруг препятствия → сохранённый результат → GeoJSON → отображение в браузере. Следующие этапы наращивают тот же код, а не выбрасывают демо и пишут всё заново.

## 18. Принятие решений при недостатке информации

Не блокировать P0 ожиданием организаторов. Использовать явно синтетические inputs и профили. Не выдумывать нормативные отступы, стоимость, мощность, глубины, формат неизвестных файлов и критерии хакатона.

Неизвестный формат решается через adapter spike и mapping. Неизвестная методика — через draft/reviewed profile и missing capability. Неизвестные правила использования заранее написанного кода — организационный вопрос, не техническое свойство системы.

Все существенные допущения — `docs/adr` и assumptions в run. Новая гипотеза должна сопровождаться тестом или экспериментом, а не сразу попадать в главное ранжирование.

**Итоговая формула продукта:** устойчивый геоданный backend + проверяемая маршрутизация + объяснимые ограничения/оценки + готовый профессиональный web UI. Декоративная 3D-сцена и энтропийный калькулятор не заменяют эти четыре части.
