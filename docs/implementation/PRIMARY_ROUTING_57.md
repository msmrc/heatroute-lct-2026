## Оценки кандидатов

`draftScore` выполняет настоящий sizing и экономику. Ранее admission вычислял его, затем
comparator многократно повторял тот же расчёт. `AssessedRouteDraft` теперь переносит уже
вычисленные score/length/bend count внутри одного этапа отбора неизменного draft.
В переносе камер baseline engineering evaluation вычисляется один раз на проход; оценка
каждого кандидата переносится из admission. После изменения сети создаётся новая оценка.

Сохранены stable ordering при равных score (включая разные scale BigDecimal), порядок двух
top-3, лимит до dedup, исходный geometry-signature для удаления дублей и каждый полный finish.
Оценки разных drafts не объединяются по geometry signature; это остаётся только прежним
правилом выбора представителей. Metric record не является проверенным результатом и не
может заменить sizing/geometry/depth/economics после перестройки сети.

## Подготовка препятствий

`Constraint` использует существующий prepared fallback для неподдерживаемой, слишком большой,
пустой или невалидной геометрии без второй owned-копии. Пригодность проверяется до копирования;
отрицательное решение публикуется один раз. При отмене инициализация не считается законченной.
Поддерживаемый индекс по-прежнему владеет копией, строится до volatile-публикации, не меняет
исходный userData; standalone-конструктор сохраняет прежний owned-fallback контракт.

Retention budget включает `source + blocked + 3×blocked` координат для потенциального индекса:
дополнительная owned-копия N и верхняя граница2N координат концов рёбер. Резерв определяется
без построения индекса и без eager validity scan, по всем кольцам/компонентам и замыканиям.
Порог16 384 включителен. Слишком большой элемент всё равно возвращается для расчёта,
но не удерживается в preparation map. LRU eviction не удаляет ограничения из текущего запроса.

Это **не лимит байтов heap**: внутренние объекты JTS/временные массивы и ещё используемые
потребителем записи после eviction в него не входят. Невалидный полигон может получить
консервативно завышенный резерв. Более ранний eviction может изменить время подготовки.

Ресурсный regression:8 падений до исправления (`primary57-constraint-resources-red.log`);
после —69/69 isolated PASS,2,08 с (`primary57-constraint-resources-green.log`), включая
cap/eviction, отсутствие копии/повторного validity, cancellation/retry,4 concurrent cold
queries, ownership, старые differential и реальные official-constraints проверки.
Команда: `sh .tooling/primary57-constraint-resources-run.sh`.

## Ограниченный перенос ответвления: проверен, не включён

Второй отдельный probe динамически выбирает трёхлучевую камеру A с листом-потребителем,
переподключает этот лист к другой трёхлучевой камере B и удаляет ставшую узлом степени2 A,
соединяя два оставшихся пути. Корни, полная геометрия корневых рёбер и прежние лучи B сохраняются.
Из90 вариантов /70 различных пар A/B проверены первые6 пар по геометрической добавке длины,
включая одну несоседнюю; до3 путей на пару,16 настоящих finish,8 прошедших допуск/экспорт.
Лимит не доказывает исчерпание всех обменов или топологий.

Лучший допустимый:1906,953 м /12 камер /17 поворотов /275817240,07 ₽ /score13,443741722.
Относительно preferred:−1 камера,−643664,56 ₽, но+19,731 м,+1 поворот и худший score
на0,041170392. Все17 подключений, rooted forest без циклов, степень≤4, sizing, включённая
глубина и независимый экспорт сохранены. Не интегрировано: выигрыш по камерам/цене сам по себе
не улучшает итоговый целевой показатель и форму.

Дополнительная пятиградусная ортогональная эвристика порта отдельно пропускает2 кандидата;
лучшая mandatory-valid сеть ей не соответствует, но прежние три подхода B тоже ей не
соответствовали. Это **не новый нормативный запрет**, и эти8 результатов нельзя называть
нарушающими обязательный допуск. Авторитетная классификация — `summary.log`, не первоначальный
`accepted` в `result.log`, который дополнительно учитывал эту эвристику.

Evidence: `.tooling/leaf-exchange57-probe/findings.md`, `summary.log`, `result.log`;
кандидат `.tooling/leaf-exchange57-run.aWe9vg/leaf-p1-v0.json`. Использован изолированный

Следующая гипотеза — согласованная перестройка нескольких ответвлений/общего ствола:
одно локальное удаление камеры здесь не улучшает score. Начинать с ограниченного probe и
полного допуска, а не с неограниченного увеличения бюджета или ослабления валидатора.
Общая цель формы/камер/скорости остаётся открытой.

### Конкретный следующий шаг геометрии

`.tooling/primary57-geometry-quality.json` и просмотренная `routing-comparison-57-preferred`
сохраняют исходные полилинии, тот же масштаб и проверенный SHA исходной разметки. Это depth-on
fixture, не новый native2D run. У preferred11 тройников и2 четырёхлучевых узла; у Евгения7 и4.
Cheapest fixture уже имеет7 и4, но24 поворота против15 в разметке: одного счётчика камер мало.

Следующий bounded probe: перенос листа **вместе** с переносом принимающей камеры и перестройкой
всех её подходов, используя существующие `CorridorChamberRelocations`/approach helpers.
В57 эта составная операция не реализована. Старый leaf probe фиксировал камеру B и её лучи;
это ограничение эксперимента, не требование ТЗ. Сохранять корни, все подключения и независимый
допуск; отдельно измерять длину/score/камеры/повороты. Не переносить кандидата в pipeline без
подтверждённого выигрыша и нового full gate. Если составной шаг не даёт выигрыша, следующий
уровень — смена общего ствола, а не увеличение всех существующих лимитов.
