# Единый поиск и портфель вариантов маршрута

**Статус:** частично реализовано в `global-tree-33`, требуется дальнейшее расширение портфеля.  
**Дата:** 22 сентября 2026 года.  
Текущая реализация сохраняет независимый, общий и экономический финалисты, переиспользует общий
контекст поиска и выбирает представителей трёх стратегий. Полный Pareto/beam-поиск на каждом шаге
ещё не реализован.

## 1. Продуктовое решение

Один calculation run должен выполнять один общий поиск и формировать портфель допустимых
кандидатов, из которого затем выбираются три содержательно разных результата:

1. **Инженерная геометрия** — регулярная трасса с длинными общими стволами, небольшим числом
   изломов и конструктивными углами.
2. **Самый короткий** — допустимый кандидат с минимальной суммарной длиной.
3. **Самый дешёвый** — допустимый кандидат с минимальной официальной стоимостью.

Правила присвоения `rank`, рекомендуемого варианта и окончательные пользовательские названия
будут определены отдельно. Выбор стратегии и официальный rank не должны смешиваться.

## 2. Что означает один прогон

Один прогон не означает построить одну жадную трассу, а затем косметически изменить её три раза.
Если во время поиска оставить только один лучший промежуточный результат, варианты с другой
точкой врезки, группировкой ОКС или общим стволом будут необратимо потеряны.

Один прогон означает:

- один раз подготовить topology, ограничения, spatial indexes, demand points и tie-in candidates;
- переиспользовать найденные допустимые локальные пути и результаты дорогих visibility-проверок;
- во время построения сети сохранять ограниченный набор недоминируемых деревьев;
- применять операции построения и перестройки к общему портфелю кандидатов;
- один раз доводить выбранных финалистов через sizing, economics и final validation;
- выбирать из финального портфеля представителя каждой стратегии.

## 3. Предлагаемый pipeline

### 3.1. Общий неизменяемый контекст

В начале run один раз создаются:

- модель существующей сети и кандидаты врезок;
- метрические геометрии в EPSG:32637;
- индексы препятствий и разрешённых специальных пересечений;
- точки нормального выхода из каждого ОКС;
- справочники ДУ, стоимости и обязательные параметры run.

### 3.2. Общий пул локальных маршрутов

Для существенной пары точек сохраняется не только один путь, а небольшой набор содержательно
разных допустимых путей: кратчайший, регулярный по геометрии и альтернативный обход. Переиспользовать
можно только результаты с одинаковым контекстом ограничений. Проверки против уже принятых рёбер
дерева остаются динамическими и не должны ошибочно кешироваться как независимые от состояния.

### 3.3. Портфель деревьев

Поиск хранит bounded portfolio промежуточных деревьев. Кандидат описывается не одним scalar score,
а набором показателей:

- число подключённых ОКС;
- валидность и виды нарушений;
- официальная стоимость;
- суммарная длина;
- число врезок и камер;
- число изломов и отклонений от конструктивных направлений;
- сигнатура топологии и геометрии для исключения дублей.

Кандидат удаляется, если другой кандидат не хуже по всем существенным показателям и лучше хотя бы
по одному. Размер портфеля ограничивается beam width и квотами разнообразия, чтобы поиск оставался
ограниченным по памяти и времени.

### 3.4. Общие операции поиска

Один раз генерируются и оцениваются операции:

- прямое подключение к существующей сети;
- общий ствол для группы ОКС;
- graft к существующему ребру дерева;
- смена точки врезки;
- перенос или объединение камер;
- перестройка нескольких связанных ветвей;
- corridor-first перестройка для инженерной геометрии;
- допустимый обход препятствия альтернативной стороной.

Операция может улучшать одного представителя портфеля и ухудшать другого. Она не отбрасывается
только потому, что не улучшает текущий cheapest или shortest draft.

### 3.5. Финализация

Перед выбором результатов каждый финалист проходит один и тот же обязательный контур:

1. нормализация топологии и геометрии;
2. bottom-up flow aggregation и sizing;
3. проверка непрерывной длины одного ДУ;
4. точный расчёт участков, камер, врезок и специальных проходов;
5. независимая final validation;
6. дедупликация по топологической и геометрической сигнатуре.

Из валидного портфеля выбираются представители трёх стратегий. Если один кандидат одновременно
лучший по нескольким стратегиям, для следующего варианта выбирается ближайший содержательно другой
кандидат, а не небольшое смещение той же линии.

## 4. Цели трёх стратегий

Все стратегии сначала требуют максимально возможного покрытия и полной валидности.

### Инженерная геометрия

Предпочитает в указанном порядке:

- длинные общие прямолинейные стволы;
- минимальное число изломов;
- направления по доминирующим осям территории и углы 45°/90° относительно них;
- минимальное число камер при соблюдении ограничения степени;
- отсутствие необоснованных коротких зигзагов;
- меньшую длину и стоимость при равной регулярности.

Допустимые ограничения на проигрыш cheapest/shortest по стоимости и длине будут определены позже.

### Самый короткий

Минимизирует фактическую итоговую длину новой сети после sizing и финальной геометрии. Стоимость,
число камер и регулярность используются только как детерминированные tie-breakers.

### Самый дешёвый

Минимизирует официальный `calculated_cost`, включая трубы назначенных ДУ, камеры, врезки,
специальные проходы и штрафы. Длина и регулярность используются как tie-breakers.

## 5. Производительность

Единый поиск должен уменьшить повторную работу, но ускорение не считается гарантированным заранее.
Портфельный поиск рассматривает больше состояний, чем один scalar objective, поэтому выигрыш от
общих индексов и кеша может частично компенсироваться расширенным frontier.

При реализации сравниваются на одном и том же наборе:

- wall-clock run time;
- число visibility-search и проверенных пар;
- cache hit/miss для локальных путей;
- количество созданных, отброшенных и финализированных drafts;
- peak heap и объём временных данных;
- длина, стоимость, число камер, врезок и изломов каждого результата.

Цель изменения — не формальное сокращение трёх вызовов до одного метода, а устранение повторного
поиска одинаковых локальных путей без потери качества и разнообразия вариантов.

## 6. Границы будущей реализации

- Не менять официальный контракт, sizing, economics и final validator ради ускорения поиска.
- Не выводить три варианта из одной уже выбранной топологии только геометрическим post-processing.
- Не кешировать результат, зависящий от уже принятых рёбер, без ключа состояния дерева.
- Не считать вариант точным только потому, что у него меньше координат.
- Не использовать дороги или линии подложки, отсутствующие во входном GeoJSON.
- Не смешивать реализацию портфеля с решением о rank и UI-рекомендации.

## 7. Текущее состояние и следующий шаг

Текущий planner уже переиспользует общий routing environment, topology и tie-in candidates, но
строит как минимум независимый и shared drafts отдельными ветками, а затем получает shortest и
cheapest через дополнительные локальные перестройки. Это частичное переиспользование, но ещё не
единый портфельный поиск.

К реализации этого решения следует возвращаться после завершения текущей работы над настоящими
shortest и cheapest вариантами. Первый технический шаг — отделить состояние draft, генераторы
операций и оценки кандидата от orchestration `OfficialRoutePlanner`, не меняя поведение готовых
стратегий.
