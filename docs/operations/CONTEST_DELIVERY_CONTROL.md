# Контроль соответствия ТЗ и готовности конкурсной сдачи

**Статус:** `RED — к передаче жюри не готово`

**Последняя актуализация:** 21 сентября 2026 года

**База аудита:** commit `54e85808064232356e3576eedf1388ebe00960d8`

**Назначение:** единая оперативная точка правды для разработчиков до финальной сдачи.

Этот файл защищает команду от ситуации, когда решение развивается быстро, но обязательный контракт,
поставка или демонстрация остаются неподготовленными. Здесь фиксируются только требования, влияющие
на приёмку. Подробные технические заметки и история разработки не заменяют этот документ.

## 1. Как пользоваться этим документом

1. Перед началом работы выбрать не более одного незакрытого P0 на разработчика.
2. Поставить ему статус `IN PROGRESS`, указать владельца и ожидаемую проверку.
3. Вместе с кодом добавить или обновить автоматический тест.
4. После проверки записать команду, результат и commit SHA в колонку `Evidence`.
5. Перевести пункт в `VERIFIED` только после проверки из чистого checkout.
6. При получении нового документа организаторов сначала обновить раздел 2 и журнал решений,
   затем менять код.

Допустимые статусы:

- `OPEN` — работа не начата;
- `IN PROGRESS` — есть один ответственный и активное изменение;
- `BLOCKED` — зафиксирована конкретная внешняя причина;
- `VERIFIED` — есть воспроизводимая проверка на текущем commit;
- `DEFERRED` — не входит в обязательную сдачу и осознанно отложено.

Слова «готово», «работает» и «соответствует» без команды проверки и commit SHA доказательством не
считаются.

## 2. Приоритет источников

При противоречии используется следующий порядок:

1. актуальное письменное техническое приложение;
2. письменные разъяснения по вопросам участников;
3. основное описание кейса;
4. материалы встреч и внутренние конспекты — только если они не противоречат письменным документам;
5. текущие README, схемы, тесты и код — они должны быть приведены к требованиям выше.

## 6. Требования к поставке

Письменное ТЗ требует работающий сервис, а не одиночный исполняемый файл:

| Область | Требование |
|---|---|
| ОС | Ubuntu Server 22 |
| Ресурсы | 16 ГБ ОЗУ; иных аппаратных требований не задано |
| Backend | Java 11, Spring Boot 2.6.3 |
| Данные | PostgreSQL до 18 включительно либо OpenSearch до 2.18 включительно |
| API | springdoc-openapi-ui 1.7.0 / Swagger UI |
| Развёртывание | `docker-compose 1.29.2`; приложение и БД поднимаются через Compose |
| Файлы | вход до 3 ГБ, результат до 500 МБ, потоковая обработка |
| Нагрузка | до 50 пользователей |
| Финальная сдача | работающий сервис, презентация, документация, GeoJSON результата |

Одиночный backend JAR сейчас не является автономной поставкой: ему нужны PostgreSQL/PostGIS, схема
Liquibase и отдельно собранный web. Не следует создавать второй упрощённый алгоритм только для
демо — он может разойтись с основным расчётным ядром.

### Обязательный офлайн-комплект

Офлайн-релиз должен собираться как отдельный release artifact, а не хранить тяжёлые image tar в Git:

```text
heatroute-release/
  README_START_RU.md
  compose.yaml
  compose.offline.yaml
  images/
    heatroute-api.tar
    heatroute-web.tar
    postgis.tar
  bin/
    start.sh
    stop.sh
    smoke.sh
  examples/
    input.geojson
    expected-output.geojson
  SHA256SUMS
```

`start.sh` должен без доступа к сети загрузить образы, поднять Compose, дождаться readiness и
напечатать адреса UI и Swagger. `smoke.sh` должен загрузить пример, дождаться завершения расчёта,
скачать результат и проверить его по актуальной схеме.

Текущий `scripts/local-demo-server.mjs` не является поставкой алгоритма: он воспроизводит заранее
рассчитанный ответ только для файла с точным размером и SHA-256. Его можно оставить как резервный
показ, но нельзя использовать как доказательство обработки нового или скрытого набора.

## 7. Минимальный процесс до финала

Чтобы решение и сдача двигались одновременно, работа идёт в трёх дорожках:

| Дорожка | Лимит | Результат каждого дня |
|---|---:|---|
| Алгоритм | 1 активный P0 на разработчика | Код + тест + измеримый результат |
| Поставка | 1 активная задача на команду | Воспроизводимый шаг clean/offline запуска |
| Документация | только вслед за проверенным кодом | Обновлённый контракт или инструкция без обещаний вперёд кода |

Ежедневный ритуал занимает 15 минут:

1. обновить статусы P0 и владельцев;
2. проверить, появился ли новый источник требований;
3. запустить быстрые проверки затронутой части;
4. записать evidence для закрытых пунктов;
5. выбрать один следующий блокер сдачи, а не новую необязательную функцию.

Рекомендуемое распределение оставшегося времени: 70% — обязательный расчёт и контракт, 20% —
поставка и E2E, 10% — документация и презентация. Дополнительная глубина, косметика и расширенные
профили не берутся в работу, пока есть незакрытый P0 обязательного 2D-контура.

## 8. Definition of Done для любого P0

Пункт закрыт, только если одновременно выполнено следующее:

- поведение реализовано в основном коде без отдельного демонстрационного обхода;
- есть позитивный, граничный и негативный тест, где они применимы;
- тест проверяет требование, а не только факт отсутствия исключения;
- изменённые публичные контракты и документация синхронизированы;
- проверка выполнена на требуемой версии Java/Node/Compose;
- рабочее дерево чистое;
- commit отправлен в Git;
- в таблице P0 записаны команда, итог и SHA.

## 9. Быстрый контроль перед каждым push

```bash
git status --short
git diff --check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

Для изменений backend или контракта дополнительно:

```bash
docker build --target test -f infra/docker/backend.Dockerfile -t heatroute-api:test .
docker-compose -f compose.yaml config --quiet
docker-compose -f compose.yaml up --build -d
```

Перед релизом команды должны выполняться из чистого checkout на Ubuntu Server 22. Локальная успешная
проверка на другой ОС полезна, но не заменяет release gate.

## 10. Запреты до закрытия обязательного контура

- Не добавлять новую бонусную функциональность при незакрытом P0.
- Не возвращать реконструкцию в обязательную стоимость или экспорт.
- Не объявлять глубинный режим соответствующим, пока не убраны шаг 0,5 м и отдельный максимум.
- Не использовать старый dataset hash как критерий допустимости произвольного входа.
- Не считать replay-демо проверкой алгоритма.
- Не менять одновременно алгоритм, контракт и UI без раздельных тестов для каждого слоя.
- Не обновлять README обещанием функции раньше, чем готов проверяемый код.
- Не закрывать пункт ссылкой на старый evidence, выполненный до текущих изменений.

## 11. Финальный release gate

- [ ] Все P0 имеют статус `VERIFIED` на одном commit.
- [ ] Скорректированный набор находится в репозитории, его SHA записан в тесте и документации.
- [ ] Скрытоподобный набор с другой геометрией проходит без изменения кода.
- [ ] Базовый 2D-результат содержит только четыре разрешённых типа.
- [ ] Результат проходит актуальную JSON Schema и независимую семантическую проверку.
- [ ] Полный расчёт и экспорт проходят на Ubuntu Server 22 / Java 11.
- [ ] Офлайн-комплект запускается на чистой машине одной командой.
- [ ] После перезапуска сохраняются импорт, задание и результат.
- [ ] README, Swagger, пример и презентация описывают одинаковое поведение.
- [ ] В публичных материалах нет внутренних handoff, старого стека и устаревших трактовок.
- [ ] Зафиксированы время расчёта, память, размер входа/выхода, commit и SHA артефактов.
- [ ] Создан Git tag и неизменяемый release artifact.
