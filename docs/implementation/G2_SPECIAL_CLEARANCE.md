## Основание и воспроизведение

Техническое приложение §3.1: GeoJSON-линия — ось пары; расстояния считаются до внешнего
габарита. §4: минимальный горизонтальный отступ обязателен при прохождении рядом, исключение
локально внутри разрешённого special. Road/tram: R=1,5м,угол≥45°,прямой проход через полигон
с3м по трассе с обеих сторон. Приоритет — документ организатора, не эвристика СП.
Текст повторно прочитан в локальной выписке `tmp/source-review/technical/source.txt:174,190,244`;
SHA исходного DOCX записан в [реестре](EXPERT_ROUTING_2026_09_25.md).

Синтетика в EPSG:32637, локальные координаты ниже прибавляются к(500000,6170000):

```text
road или tram_tracks = POLYGON ((0 0,100 0,100 6,0 6,0 0))
route = LINESTRING (-10 7.700,110 7.700)
ДУ100: W=0,510м; требуется от оси 1,5+0,510/2=1,755м.
Фактическое расстояние оси=1,700м; просвет=1,445м — нарушение.
```

Изолированный Java11 тест на compiled71 реально дал **2PASS/4FAIL**:
для обоих типов `lineAllowed=true` вместо false и финальный `OfficialRouteValidator`
возвращает пустые issues вместо отказа. Обычный перпендикулярный контроль

Тест не включён в full71: `.tooling/intake-20260925/RoadParallelClearanceRedTest.java`,

## Затронутая цепочка

`OfficialRouteGeometryRules.baseConstraints/preparationClearanceM`: buffer/clearance сейчас
есть только у forbidden. `segmentAllowed`/`validate` проверяют special только при пересечении
source. `ConstraintIndex` индексирует special по исходному envelope, как и новая bounded
подготовка validation. Отступ нельзя исправить одним условием после такого отбора — дорога
уже могла быть исключена. Ключ подготовки должен учитывать ДУ и clearance special-объекта.

Текущий exporter проверяет сохранённую геометрию/углы/смету, но не пересчитывает эти отступы
от ограничений. Export-контрпример ещё не запускался; это вывод из чтения пути
`OfficialGeoJsonExporter`→`SavedChamberAssessment`, не новый acceptance test.
SQL/in-memory окно для этой синтетики уже включает дорогу: дефект возникает после загрузки.

## Минимальный согласованный fix

1. Численный осевой clearance road/tram из существующего `OfficialAxisClearance`;
   расширенный conservative envelope в обоих spatial отборах и ДУ-зависимая подготовка.
   Не превращать special в безусловно запрещённый объект.
2. Проверять полную полилинию. Исключение — только конкретный прямой special-интервал
   конкретного объекта с допустимым входным углом и защитными3м. Нельзя одним пересечением
   разрешить дальнейшее движение вдоль дороги. Коллинеарные дополнительные вершины не
   должны ломать допустимый проход; min/max всех пересечений не заменяет отдельные интервалы.
3. Согласовать поиск/порталы/sections/финальный допуск. Сейчас порталы вынесены лишь на0,25м;
   для перпендикулярного прохода нужен вынос как минимум max(3,axisClearance)+searchMargin.
   Само обрезание special по концам полилинии не доказывает полные защитные длины.
4. Повторный допуск перед export по исходным ограничениям, конечным ДУ и фактически выдаваемой
   геометрии. Затем PostGIS/in-memory equivalence, оба датасета и HTTP/native.

Проверить неоднозначные/краевые случаи отдельно: root или потребитель внутри road;
касание без прохода; углы polygon corners; повторное/многокомпонентное пересечение;
special длиннее исходного edge и коллинеарная граница топологии. Не добавлять молчаливую
льготу всему root footprint. Остальные special-типы/собственные габариты остаются G2 scope.
