# Алгоритм обязательного 2D-расчёта

Активная трактовка supplied dataset зафиксирована в
`implementation/ORGANIZER_VIDEO_CLARIFICATIONS.md`. Реконструкция и глубина остаются расширенными
режимами и не блокируют обязательный 2D-результат.

## Поток обработки

1. Java API потоково инспектирует один GeoJSON, одновременно считает SHA-256 и применяет strict
   либо явно названный compatibility-профиль.
2. Объекты сохраняются в PostgreSQL/PostGIS в WGS84 и EPSG:32637. Повтор contract+SHA возвращает
   существующий import.
3. Валидатор строит существующую топологию и формирует кандидаты врезок. Точка на трубе в пределах
   10 м от допустимой существующей камеры заменяется кандидатом в эту камеру; иначе врезка требует
   новой камеры.
4. Для каждой demand point определяется собственный полигон OKS. Первая часть пути выходит из
   здания по нормали к ближайшей границе и заканчивается за защитной зоной текущего ДУ.
5. Для всех demand points одним запуском строятся independent, shared и diverse стратегии.
   Visibility search использует prepared geometry и adaptive STRtree; каждый кандидат после
   упрощения повторно проходит независимую проверку.
6. Функция поиска предпочитает прямые участки и углы 45°/90°. Нестандартный поворот получает
   коэффициент 1,5, поэтому лишние повороты и сварные соединения ухудшают вариант.
7. Принятые линии нормализуются в дерево/деревья. Разветвления и врезки становятся камерами,
   изменения инженерных параметров — technical nodes.
8. Расходы суммируются снизу вверх. Официальный каталог назначает минимальный ДУ, удовлетворяющий
   расходу и непрерывной предельной длине. Камера не сбрасывает длину неизменного ДУ.
9. Ограничения применяются и во время поиска, и финальным валидатором. Перекрывающиеся разрешённые
   пересечения объединяются в один `special` span с максимальным `K_special`, без перемножения.
10. Для каждого demand сравнивается marginal cost подключения со штрафом
    `100 000 000 + 500 000 * flow_tph`. Дорогой, но геометрически возможный маршрут разрешено
    заменить явным `no_route`.
11. Стоимость включает новые участки, камеры, отдельные новые лучи-врезки, special/depth/bend
    коэффициенты и penalties. До трёх разных вариантов получают deterministic score и rank.
12. Adapter и независимый validator проверяют whitelist полей, типы, ссылки, уникальность IDs и
    WGS84, после чего Jackson пишет FeatureCollection потоково. Для supplied profile отсутствие
    реконструкции не блокирует экспорт.

## Отказоустойчивость

Run и job неизменяемо сохраняются в PostgreSQL. Workers забирают задания через `SKIP LOCKED`,
имеют bounded concurrency и lease heartbeat. Отмена кооперативная; истёкший lease можно безопасно
перехватить после остановки процесса. Ошибка одного ОКС создаёт partial result с ID и причиной,
а не удаляет успешные маршруты остальных объектов.

## Границы применимости

- расчётные расстояния и площади выполняются в EPSG:32637, API/export — WGS84;
- обязательная модель остаётся самостоятельным 2D-результатом; optional R8 запускается отдельным
  этапом и не меняет успешность, стоимость и доступность экспорта обязательного 2D-варианта;
- реконструкция существующей сети выполняется только в strict-profile с полными baseline/direction
  полями и не является обязательной для supplied-dataset profile;
- supplied dataset compatibility не заменяет отсутствующие flow/upstream/diameter значения;
- routing не должен материализовать весь городской импорт одним Java `List`; геометрия читается
  порциями или пространственными окнами из PostGIS;
- exact 3 GiB input, ≥500 MiB output и 50 concurrent API sessions измерены отдельно от
  geometry-representative maximum-topology throughput;
- `railway` обрабатывается консервативно до официального уточнения.
