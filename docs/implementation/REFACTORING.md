# Правила кода и план рефакторинга HeatRoute

**Создан:** 2026-09-21. **База аудита:** `0096da4`.
**Статус:** правила зафиксированы; рефакторинг и исправления по этому документу не начаты.
**Основной фокус:** Java backend в `apps/api`.

## 1. Как работаем до завершения разработки

Не откладываем качество целиком до «конца разработки» и не начинаем переписывание всей системы.
Новые функции и существенно изменяемый код следуют правилам ниже уже сейчас. Существующий код
приводим к ним небольшими законченными изменениями, когда затрагиваем соответствующий участок.
Большие перемещения классов и разделение планировщика выполняем после стабилизации активного
функционального scope и создания проверяемой базы поведения.

Разделяем три вида работы:

- **Исправление ошибки:** меняет неправильное поведение. Сначала воспроизводящий тест и ожидаемый
  результат по контракту; затем исправление. Ошибки расчётов, экспорта и сохранения состояния
  имеют приоритет перед косметикой и не ждут окончания всей разработки.
- **Рефакторинг:** меняет устройство кода с сохранением принятого поведения. Эквивалентность
  подтверждается тестами и сравнением результатов до/после.
- **Новая функция или изменение правила:** отдельные требования и проверки; не прячем это
  внутри рефакторинга. Изменения инженерных правил требуют источника и версии алгоритма.

Не расширяем текущую функциональную задачу до переработки всего backend. Если безопасное
локальное исправление невозможно, записываем зависимость в backlog и выбираем отдельную задачу.
Технический долг фиксируем предметно: место, нарушенное правило, последствия, проверка закрытия.

Организаторские документы и [активный roadmap](OFFICIAL_TZ_ROADMAP.md) сохраняют приоритет.
Этот документ не меняет конкурсный scope, не разрешает спорные инженерные трактовки и не является
подтверждением готовности R-этапов. Продолжаем разработку по [handoff](TOMORROW_HANDOFF.md).

## 2. Обязательные правила для нового и изменяемого кода

### Архитектура и ответственность

- **ARC-01.** Сохраняем модульный монолит, Java 11, Spring Boot 2.6.3, JDBC, PostgreSQL/PostGIS и
  единственный backend `apps/api`. Не вводим микросервисы, новый брокер, ORM или другой язык
  ради рефакторинга. Не используем Java API/синтаксис новее Java 11.
- **ARC-02.** API отвечает за HTTP и преобразование DTO; application-слой — за сценарии,
  транзакции и координацию; domain — за алгоритмы и инварианты; infrastructure — за SQL,
  хранение и сериализацию. SQL принадлежит репозиториям, а инженерные формулы — domain.
- **ARC-03.** Алгоритмы не зависят от Spring MVC, JDBC, `MultipartFile` и JSON-структуры
  транспортного контракта. Spring-конфигурация собирает компоненты через конструкторы.
  Убираем существующие framework-зависимости поэтапно, не массовым переименованием пакетов.
- **ARC-04.** Класс имеет одну связную ответственность. Поиск маршрута, оценка варианта,
  ранжирование и экспорт должны изменяться независимо. Новую стратегию не добавляем очередной
  веткой в большой метод, если она может быть самостоятельным компонентом.
- **ARC-05.** Интерфейсы вводим для реальных границ и альтернативных реализаций. Запрещённые
  по умолчанию приёмы: универсальный `BaseService`, `Utils` для несвязанных правил,
  интерфейс на каждый класс и фабрика без причины. Размер файла — сигнал для ревью, не метрика
  качества. Объединяем параметры в объект только при наличии общего предметного смысла.

### Модель данных и контракты

- **MOD-01.** JSON разбирается в типизированную модель до вычисления. `JsonNode` допустим
  в адаптере контракта, сериализаторе и изолированном хранилище дополнительных атрибутов;
  маршрутизатор не извлекает обязательные значения через `path("...").as...()`.
- **MOD-02.** Состояния, профили, типы объектов и статусы соединений представлены типами/enum
  внутри Java. Их wire-имена остаются совместимыми; преобразование выполняется на границе.
- **MOD-03.** Отсутствующее обязательное значение не заменяется нулём, пустой строкой или
  минимальным диаметром. Различаем неизвестное, неприменимое и известное значение. Значения
  по умолчанию должны следовать контракту. Ошибка разрешения ссылки обнаруживается до расчёта.
- **MOD-04.** Конструкторы/factory-методы проверяют инварианты. Обязательная зависимость не может
  быть `null`; отсутствие зависимости не отключает проверку. Ожидаемое отсутствие результата
  выражается последовательно: `Optional` на границе поиска или явный исход предметной операции.
- **MOD-05.** Черновик и проверенный результат не смешиваются. Единственная процедура допуска
  объединяет все блокирующие проверки активного профиля. Экспорт не доверяет одному сохранённому
  флагу `valid`. Десериализация не должна обходить инварианты проверенной модели.
- **MOD-06.** Не обещаем неизменяемость только из-за `final` и unmodifiable-списка: учитываем
  изменяемые `Geometry`, `JsonNode` и вложенные объекты. Устанавливаем явное владение ими;
  копируем на границе владения, если нужно, без бесконтрольного копирования больших геометрий.
- **MOD-07.** Сохраняем HTTP/JSON, БД и совместимость чтения ранее сохранённых запусков.
  Изменение DTO, enum wire-name или сериализации сопровождается contract-тестом; изменение
  persisted JSON — версией формата/адаптером чтения, если совместимость иначе нарушается.

### Инженерная корректность

- **CALC-01.** WGS84 — граница API; метрическая геометрия — EPSG:32637. Единицы отражаем
  в именах (`lengthM`, `flowTph`, `costRub`); не передаём безымянные числа между системами координат.
- **CALC-02.** Для геометрии допустим `double` с обоснованным допуском. Для денег и табличных
  десятичных величин используем `BigDecimal`; не создаём его через `new BigDecimal(double)`.
  Точки и режимы округления задаются явно и проверяются на границах.
- **CALC-03.** Формулы, коэффициенты, каталог и правила округления имеют одного владельца.
  Экспорт не содержит вторую несогласованную реализацию экономики. Независимые проверки
  пересчитывают инварианты и сверяют суммы, а не только наличие и JSON-типы полей.
- **CALC-04.** Изменение геометрии после sizing требует повторной проверки длин, диаметров,
  отступов и стоимости. Пространственные ограничения для финальной проверки покрывают всю
  фактическую полилинию с необходимыми буферами, а не только её конечные точки.
- **CALC-05.** Геометрия, агрегированные расходы, допустимость ДУ, непрерывные длины, арифметика
  и включённая глубина входят в итоговое решение о допустимости. Требования реконструкции и
  глубины определяются профилем. Ошибки обязательного этапа нельзя потерять в отдельном списке.
- **CALC-06.** Функции сравнения штрафа/подключения и ранжирования должны вызываться реальным
  pipeline и иметь сквозной тест. Порядок обхода и разрешение равенств детерминированы.
  Действующие требования к objective сверяем с организаторскими источниками перед изменением.

### Ошибки, БД и фоновые задачи

- **OPS-01.** Тип исключения и стабильный код отделены от сообщения. Не ветвимся по
  `getMessage().startsWith(...)`. Ожидаемый `no_route`, неверный ввод, конфликт состояния
  и технический сбой — разные исходы. HTTP-преобразование централизовано.
- **OPS-02.** Неверный UUID/JSON/параметр получает клиентскую ошибку, превышение размера — 413,
  неприемлемое состояние — согласованный 409; непредвиденный сбой — 500 с безопасным сообщением.
  Не выдаём SQL, stack trace и внутренние пути клиенту; request/job/run ID позволяют найти лог.
- **OPS-03.** Транзакция покрывает весь атомарный бизнес-переход, но не длительный CPU-расчёт.
  Согласованность коротких чтений опирается на неизменяемую версию импорта. Транзакционный
  метод вызывается через Spring proxy; self-invocation не считается новой транзакцией.
- **OPS-04.** Изменения job и run согласованы в одной транзакции. Терминальный UPDATE защищён
  текущим состоянием, владельцем lease и номером попытки; проверяется число обновлённых строк.
  Потерявший владение worker не публикует результат. Гонка завершения и отмены имеет определённый
  исход, а не зависит от порядка двух несвязанных UPDATE.
- **OPS-05.** Явно задаём восстановление после падения, повторные попытки и классификацию ошибок.
  Дедупликация не должна навсегда блокировать повторный импорт после временного сбоя.
  Идемпотентность подтверждается конкурентным тестом с реальной БД.
- **OPS-06.** Владение permit, stream, connection и временным ресурсом явно. Освобождение
  обеспечено при успешном завершении, исключении, отмене и отказе executor. Interrupted status
  обрабатывается осознанно. Heartbeat не продлевает уже потерянную попытку.

### Память, производительность и наблюдаемость

- **PERF-01.** Большие входы/выходы обрабатываются ограниченными порциями на всём пути.
  Пагинация с последующим общим `ArrayList` не считается streaming. Полное чтение допустимо
  только для явно ограниченного набора с обоснованным бюджетом памяти.
- **PERF-02.** CPU-конкурентность, пул БД, экспорт и admission в очередь имеют согласованные
  пределы. Ускорение не должно выводить ограничения из финального валидатора. Индексы и запросы
  проверяем на PostGIS, алгоритмы — на плотных окнах и большой топологии, не только на размере файла.
- **PERF-03.** Логи содержат ID, фазу, длительность и ограниченные счётчики; не полный GeoJSON,
  секреты или гигантские списки объектов. Прогресс отражает реальные этапы. Состояние worker и
  потеря lease должны диагностироваться отдельно от доступности PostgreSQL.

### Тесты и стиль

- **TEST-01.** Unit-тесты алгоритмов проверяют результат и инварианты; Mockito не подменяет
  проверяемую предметную логику. SQL, транзакции, миграции, claim и восстановление проверяются
  на PostgreSQL/PostGIS, а не только на mock `JdbcTemplate`.
- **TEST-02.** Для каждой ошибки сначала создаём падающий regression-тест. Обязательны
  табличные границы, составные цепочки/деревья, отрицательные случаи и оба активных профиля.
  Небольшие синтетические случаи строим в тестах; официальный файл не модифицируем.
- **TEST-03.** Characterization-тесты фиксируют принятое поведение, но не узаконивают дефекты.
  Неправильный baseline помечаем и исправляем отдельно. Не измеряем качество числом mock-вызовов
  или произвольным процентом покрытия; проверяем риски.
- **TEST-04.** Нужны сквозные import → run → export проверки и отказные сценарии. Restart-тест
  прерывает активную работу; чтение уже завершённого результата после рестарта проверяет только
  сохранность результата. Scale-проверка проходит через настоящий service/API-путь.
- **STYLE-01.** Один форматтер Java, согласованные imports и статический анализ. ArchUnit
  закрепляет зависимости слоёв. Подключение инструментов — отдельное изменение без массовых
  suppressions и без смешивания форматирования с исправлением алгоритма.
- **STYLE-02.** Имена объясняют предметный смысл; комментарии — причину, допуск и источник правила.
  Предпочитаем простую управляющую логику, небольшой scope переменных и явные зависимости.
  Не навязываем streams, Lombok, builder или паттерн там, где обычный Java-код понятнее.
- **DOC-01.** Для жюри и новых разработчиков пишем краткие русские JavaDoc у основных классов,
  точек входа сценариев, предметных алгоритмов и методов с неочевидным контрактом. Для TypeScript
  действует тот же принцип с JSDoc. Идентификаторы остаются английскими; wire-коды, API-поля
  и сообщения логов не переводим в рамках документирования.
- **DOC-02.** Обычный объём — 1–3 коротких предложения: назначение и, где существенно, условие
  применения, единицы или смысл результата/отказа. Не пересказываем тело метода построчно.
  `@param`, `@return`, `@throws` добавляем, когда они уточняют контракт, а не повторяют имя и тип.
- **DOC-03.** Внутри метода поясняем только нетривиальное решение: почему нужен допуск,
  повторный sizing, исключение для профиля или защита от гонки. Формулы и длинные обоснования
  выносим в документацию; рядом оставляем краткую причину и ссылку на источник/раздел.
- **DOC-04.** Очевидные геттеры, сеттеры, конструкторы простых DTO и тривиальные helpers
  не требуют формальных комментариев. В описании класса указываем его роль в pipeline;
  в описании метода — то, чего недостаточно понять из сигнатуры.
- **DOC-05.** Комментарий описывает действующие гарантии. Не пишем «потоковый», «атомарный»,
  «независимая полная проверка» или «восстанавливается после сбоя» без подтверждения реализацией
  и проверками. При изменении поведения обновляем комментарий в том же изменении.

### Примеры кратких русских описаний

Для `OfficialNetworkSizer.size()` — назначение и способ сообщить о нарушениях:

```java
/**
 * Суммирует расходы от потребителей к корню и подбирает ДУ по каталогу.
 * Выявленные нарушения возвращает в issues результата.
 */
```

Для `OfficialJobRepository.claimNext()` — неочевидный конкурентный контракт:

```java
/**
 * Атомарно забирает задачу из очереди или с истёкшей арендой.
 * Задачи, заблокированные другим исполнителем, пропускаются; отсутствие задачи даёт Optional.empty().
 */
```

Локальный комментарий перед повторной проверкой после sizing:

```java
// Увеличение ДУ меняет отступ от здания — проверяем выход из ОКС повторно.
```

Не нужны комментарии вида `// Получаем список`, `// Запускаем цикл` или «Метод calculate
выполняет расчёт». Читатель должен быстро понять предметную причину и условия, не только
увидеть перевод Java-кода на русский.

## 3. Примеры направления изменений

Эскизы ниже не являются реализованными API. При переносе сохраняем Java 11 и проверяем контракт.

### Разделить построение, оценку и ранжирование

На момент аудита прежний монолит объединял эти роли в одном классе. Целевая оркестрация:

```java
RoutingContext context = contextFactory.create(input);
List<VariantDraft> drafts = candidatePlanner.plan(context);
List<VariantEvaluation> evaluations = drafts.stream()
        .map(draft -> variantEvaluator.evaluate(draft, context))
        .collect(Collectors.toList());
return variantRanker.rank(evaluations);
```

`VariantEvaluator` сохраняет необходимый порядок повторных sizing/geometry-проверок. Извлечение
не должно упрощать pipeline ценой пропуска этапов. Сначала выделяем одну ответственность и
проверяем эквивалентность; не делаем всё одним изменением.

### Не превращать неизвестный расход в ноль

На момент аудита в историческом `demands()`:

```java
BigDecimal resolvedFlow = flow == null ? BigDecimal.ZERO : flow;
```

Целевой адаптер разрешает ссылку на ОКС, проверяет расход и возвращает типизированный `Demand`:

```java
BigDecimal flow = connection.getFlowTph()
        .or(() -> linkedOks.flatMap(FutureOks::getFlowTph))
        .orElseThrow(() -> new MissingDemandFlowException(connection.getId()));
return new Demand(connection.getId(), flow, location);
```

Это требует загрузки связанных `oks_future`, а не только замены одной строки.

### Допуск результата — явная проверка всех обязательных условий

Сейчас `RouteVariant.isValid()` проверяет только `validationIssues.isEmpty()`.
Целевой переход:

```java
ValidationReport report = finalValidator.validate(candidate, profile);
if (report.hasBlockingIssues()) {
    return VariantEvaluation.rejected(candidate, report);
}
return VariantEvaluation.accepted(ValidatedVariant.from(candidate, report));
```

Создание проверенного типа ограничено; exporter не может принять произвольный черновик.
Если отдельный тип не оправдан, те же гарантии обеспечивает обязательная процедура допуска.

### Тип ошибки вместо протокола в сообщении

Сейчас контроллер распознаёт `IllegalStateException` по префиксу `OFFICIAL_EXPORT_INCOMPLETE`.
Цель: `ExportNotReadyException` с кодом и причинами, один `@ExceptionHandler` для преобразования
в согласованный ответ 409. Сообщение можно менять без изменения поведения API.

### Атомарное завершение с защитой владельца

Сейчас worker последовательно вызывает `runRepository.markCompleted(...)` и
`repository.markCompleted(...)`. Целевой сервис переходов для calculation job:

```java
@Transactional
public void complete(ClaimedJob job, CalculationResult result) {
    if (!jobs.completeIfOwned(job.getId(), job.getWorkerId(), job.getAttempt(), result)) {
        throw new JobOwnershipLostException(job.getId());
    }
    runs.complete(job.getRunId(), result);
}
```

Условный SQL проверяет состояние/отмену/владельца/попытку; оба UPDATE входят в одну транзакцию.
Для topology job переход определён отдельно, без фиктивного run. Это эскиз, не замена интеграционным
тестам гонок, rollback и повторного выполнения.

## 5. Поэтапный backlog рефакторинга

Этапы RF — внутренние этапы качества, не конкурсные R-этапы. Чекбоксы отмечаем только с evidence.
Исправления B-xx можно и нужно выполнять до масштабного структурного рефакторинга, в частности
если они затрагивают разрабатываемую функцию или блокируют корректный результат.

- [ ] **RF-00 — воспроизводимая база.** Зафиксировать актуальный SHA, входы, профили, версии,
  состояние тестов, принятые результаты, время и память. Исправить устаревшие CI-ожидания.
  Добавить недостающие regression-тесты B-xx; не выдавать известные ошибки за golden results.
- [ ] **RF-01 — корректность и отказоустойчивость.** Подтвердить и исправить B-01–B-07,
  B-09–B-11 либо документировать опровержение/решение по требованиям. Каждый пункт — отдельное
  проверяемое изменение с тестом. Структурную уборку не смешивать с изменением результатов.
- [ ] **RF-02 — типизированные границы и инварианты.** Ввести предметные input/profile/status-модели,
  единый допуск результата и типизированные ошибки; убрать необязательные обязательные зависимости.
  HTTP и сохранённые run читаются совместимо, что подтверждено contract/regression-тестами.
- [ ] **RF-03 — разделение планировщика.** По одной ответственности извлечь построение кандидатов,
  оценку варианта и ранжирование. Убрать JSON-доступ из алгоритмов. Проверить геометрию, связи,
  расходы, ДУ, стоимости, rank и диагностику до/после; объяснить любое допустимое отличие.
- [ ] **RF-04 — ресурсы и экспорт.** Закрыть B-08, ограничить память чтения/экспорта, сократить
  транзакции и согласовать concurrency с пулом БД. Проверить cancellation/recovery и плотное
  spatial window; synthetic writer benchmark не заменяет API-проверку.
- [ ] **RF-05 — автоматическое удержание качества.** Подключить единый форматтер, ArchUnit,
  выбранный статический анализ и проверку Java-зависимостей. Зафиксировать совместимые toolchain
  версии. Не подавлять найденные проблемы массово; исключения имеют причину и отдельный долг.
- [ ] **RF-06 — итоговая проверка и передача.** Выполнить Java 11/web/Compose gates, реальный
  официальный import → run → export, extended-профиль, отказные и релевантные scale-проверки.
  Проверить краткие русские описания ключевых классов/методов по DOC-01–DOC-05: жюри должно
  проследить import → job → расчёт → проверку → export по точкам входа и их контрактам.
  Обновить roadmap, progress и handoff с SHA/evidence; закрыть только подтверждённые пункты.

Базовые команды проекта: `pwsh -File scripts/dev.ps1 test`, затем `lint` и `typecheck` через
тот же скрипт; для API-изменений — live Compose smoke. Дополнительно RF-этап требует собственные
focused/интеграционные/scale-проверки по риску. Эквивалентный запуск на другой ОС должен использовать
те же версии и тесты; отсутствие инструмента записывается как «не проверено», а не как успех.

## 6. Чеклист одного изменения

- [ ] Указаны тип работы (bugfix/refactor/feature), B/RF-ID, scope и затронутые правила.
- [ ] Есть тест поведения/инварианта; для bugfix подтверждено падение до исправления.
- [ ] Форматирование/перемещение не скрывает смысловое изменение в большом diff.
- [ ] Проверены профиль, единицы, округления, детерминизм и совместимость контрактов.
- [ ] Проверены отказные пути, владение ресурсами и границы транзакции, если затронуты.
- [ ] Ключевые классы/методы имеют актуальные краткие русские JavaDoc/JSDoc; сложные решения
  объяснены, очевидный код не загромождён пересказом.
- [ ] Выполнены необходимые gates; записаны непроведённые проверки и причины.
- [ ] Измерены время/память, если изменился горячий путь, выборки или большие данные.
- [ ] Обновлены этот backlog и progress; при закрытии gate — roadmap и handoff.

Запись закрытия: `ID → commit → что изменилось → тесты/команды и результат → evidence → ограничения`.
После завершения разработки начинаем с актуализации RF-00, а не с массового переноса файлов.
В каждой следующей сессии читаем этот документ, roadmap, handoff и `git status`; выбираем один
незакрытый пункт и доводим его до проверяемого результата.
