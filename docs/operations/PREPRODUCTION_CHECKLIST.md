# Предпродакшен-чек-лист HeatRoute

Этот документ используется после завершения активной разработки и перед передачей проекта жюри,
публикацией релиза или развёртыванием production-версии.

Текущие блокеры, владельцы и доказательства готовности ведутся в
[контроле конкурсной сдачи](CONTEST_DELIVERY_CONTROL.md). Этот чек-лист применяется после закрытия
обязательных P0 из него и не заменяет оперативный контроль соответствия ТЗ.

Цель этапа — привести репозиторий, документацию, конфигурацию и демонстрационный стенд к единому
проверенному состоянию. Пункт считается выполненным только после проверки результата в чистом
checkout.

## 1. Зафиксировать состав релиза

- [ ] Определить commit, который становится кандидатом в релиз.
- [ ] Остановить добавление новых функций; после этого принимать только исправления.
- [ ] Зафиксировать версии приложения, алгоритма, контрактов данных и инженерных справочников.
- [ ] Проверить, что версия отображается одинаково в API, интерфейсе и документации.
- [ ] Сформировать краткий список реализованных возможностей и известных ограничений.

## 2. Очистить верхний уровень репозитория

- [ ] Переписать START_HERE.md как нейтральную инструкцию для нового разработчика.
- [ ] Актуализировать AGENTS.md: убрать историю смены технологий, временные указания и привязку к
  конкретному компьютеру.
- [ ] Удалить или перенести design-qa.md; не оставлять ссылки на временные локальные изображения,
  старые commit hash и адреса промежуточных стендов.
- [ ] Проверить checks/package_review.txt и checks/validation_report.txt: удалить устаревшие
  проверки и формулировки, не относящиеся к текущей реализации.
- [ ] Убедиться, что в корне остаются только файлы, полезные участнику, проверяющему или процессу
  сборки.

## 3. Удалить следы внутренней истории разработки

- [ ] Найти упоминания предыдущего стека, прототипов, миграций, cutover и legacy-компонентов.
- [ ] Удалить из публичных материалов формулировки вида «не возвращать», «раньше использовалось» и
  сравнения с удалённой архитектурой.
- [ ] Убрать из публичных документов имена исполнителей, handoff-заметки, задачи «на завтра» и
  указания для отдельных смен разработки.
- [ ] Убрать внутренние обозначения этапов там, где читателю нужны возможности продукта и критерии
  проверки.
- [ ] Заменить комментарии в исходном коде про прежнюю реализацию на объяснение текущего
  инварианта или алгоритмического решения.

Контрольный поиск:

~~~bash
rg -n -i "python|fastapi|celery|alembic|redis|legacy|prototype|cutover|handoff|tomorrow|former" .
~~~

Каждое найденное совпадение должно быть удалено, переписано или осознанно оставлено с понятным
обоснованием.

## 4. Разделить публичную и внутреннюю документацию

- [ ] Сформировать компактный набор документов для жюри: README, описание решения, алгоритм,
  архитектура, контракты, демонстрация и критерии проверки.
- [ ] Переписать docs/CONTEST_SUBMISSION.md как краткое описание ценности и инженерных решений.
- [ ] Привести docs/TECH_SPEC.md, docs/ALGORITHM.md, docs/DATA_CONTRACTS.md и
  docs/UI_SPEC.md к единой русской терминологии.
- [ ] Переписать docs/ACCEPTANCE.md как набор проверяемых критериев без устаревших статусов.
- [ ] Переписать docs/CONTEST_DEMO.md как уверенный воспроизводимый сценарий показа.
- [ ] Создать docs/README.md с навигацией по актуальной документации.
- [ ] Перенести исторические evidence, аудиты и handoff-файлы из docs/implementation/ в архив
  либо удалить их из конкурсной ветки.
- [ ] Проверить ADR: оставить только решения, которые объясняют актуальную архитектуру.
- [ ] Удалить ссылки из публичных документов на внутренние журналы разработки.
- [ ] Проверить все локальные Markdown-ссылки.

## 5. Устранить противоречия

- [ ] Зафиксировать фактическое поведение базового и расширенного профилей входных данных.
- [ ] Единообразно описать доступность расчёта стоимости, score, rank и экспорта.
- [ ] Единообразно описать роль реконструкции и продольного профиля.
- [ ] Сверить заявленные возможности README с API, интерфейсом и автоматическими тестами.
- [ ] Удалить устаревшие pending, not deployed, проценты готовности и временные статусы.
- [ ] Не публиковать неподтверждённые показатели производительности или полноты реализации.
- [ ] Для каждого публичного численного показателя указать воспроизводимую проверку.

## 6. Сделать конфигурацию переносимой

- [ ] Удалить абсолютные пути и настройки конкретной рабочей станции из .npmrc,
  .env.example, скриптов и документации.
- [ ] Проверить запуск на Windows, macOS и Linux либо явно указать поддерживаемые платформы.
- [ ] Проверить работу с путём checkout, содержащим пробелы и не-ASCII символы.
- [ ] Оставить в .env.example только безопасные локальные значения и понятные комментарии.
- [ ] Убедиться, что production-конфигурация требует явного задания секретов.
- [ ] Проверить, что Docker-образы и версии инструментов закреплены воспроизводимым образом.

Контрольный поиск абсолютных и служебных путей:

~~~bash
rg -n "([A-Z]:[/\\]|/Users/|/home/|AppData|Temp/|\\Temp\\)" .
~~~

## 7. Проверить безопасность публикации

- [ ] Убедиться, что в Git нет .env, .env.vps, токенов, паролей, приватных ключей и дампов.
- [ ] Проверить историю изменений на случайно опубликованные секреты.
- [ ] Удалить ненужные IP-адреса, временные домены и внутренние URL.
- [ ] Проверить настройки CORS, публичные порты и доступность PostgreSQL только во внутренней сети.
- [ ] Убедиться, что API не возвращает stack trace, локальные пути и детали инфраструктуры.
- [ ] Проверить ограничения размера загрузки, тип содержимого и обработку некорректного GeoJSON.
- [ ] Проверить лицензии production-зависимостей и обязательные attribution-уведомления карты.

## 8. Выполнить полный набор автоматических проверок

- [ ] Собрать и протестировать backend на Java 11.
- [ ] Запустить frontend unit-тесты.
- [ ] Запустить ESLint и TypeScript typecheck.
- [ ] Собрать production-версию интерфейса.
- [ ] Проверить OpenAPI-контракт и JSON Schema.
- [ ] Проверить миграции на новой пустой базе.
- [ ] Поднять полный Compose-стек из чистого checkout.
- [ ] Убедиться, что после тестов рабочее дерево остаётся чистым.

~~~bash
docker build --target test -f infra/docker/backend.Dockerfile -t heatroute-api:test .
pnpm install --frozen-lockfile
pnpm test
pnpm lint
pnpm typecheck
pnpm build
docker compose config
docker compose up --build -d --wait
~~~

## 9. Проверить полный пользовательский сценарий

- [ ] Открыть интерфейс в чистом браузерном профиле.
- [ ] Загрузить конкурсный GeoJSON.
- [ ] Проверить отчёт валидации и понятность сообщений.
- [ ] Запустить расчёт и дождаться его завершения.
- [ ] Проверить все рассчитанные варианты на карте.
- [ ] Проверить карточки участков, камер, врезок и сводные показатели.
- [ ] Проверить отображение частичного результата и причины неподключения.
- [ ] Скачать итоговый GeoJSON и проверить его JSON Schema.
- [ ] Перезапустить API и убедиться, что импорт, задание и результат сохранились.
- [ ] Проверить поведение без доступа к внешнему картографическому CDN.
- [ ] Проверить отсутствие ошибок и предупреждений приложения в консоли браузера.

## 10. Проверить эксплуатационные характеристики

- [ ] Повторить утверждённый тест большого входного файла.
- [ ] Повторить утверждённый тест большого выходного файла.
- [ ] Повторить тест одновременных API-запросов.
- [ ] Зафиксировать время полного расчёта, пиковую память и конфигурацию стенда.
- [ ] Проверить отмену задания, повторную попытку и восстановление после рестарта.
- [ ] Проверить очистку временных файлов и ограничение дискового пространства.
- [ ] Сопоставить опубликованные показатели с результатами финального commit.

## 11. Подготовить конкурсный показ

- [ ] Проверить, что README корректно отображается на GitHub, включая Mermaid-схему.
- [ ] Подготовить один основной сценарий демонстрации и резервный локальный сценарий.
- [ ] Проверить доступность стенда по HTTPS.
- [ ] Заранее загрузить только те данные, которые допустимы правилами конкурса.
- [ ] Убедиться, что демонстрация не зависит от локальных путей и файлов разработчика.
- [ ] Подготовить краткое объяснение архитектуры, алгоритма и проверяемости результата.
- [ ] Подготовить ответы по ограничениям исходных данных без обсуждения внутренней истории проекта.

## 12. Финальная приёмка

- [ ] Все предыдущие пункты закрыты или имеют письменно принятое исключение.
- [ ] В публичной документации нет противоречий и внутренних служебных формулировок.
- [ ] Рабочее дерево чистое, CI успешно завершён.
- [ ] Финальный Compose-стек поднят из чистого checkout и прошёл smoke-тест.
- [ ] Commit кандидата в релиз отмечен Git tag.
- [ ] Создана резервная копия production-базы перед обновлением.
- [ ] После развёртывания проверены главная страница, readiness API, расчёт и экспорт.
- [ ] Зафиксированы дата, commit, версия и ответственный за финальное решение о публикации.

## Результат этапа

Предпродакшен завершён, когда новый проверяющий может открыть репозиторий, понять назначение
HeatRoute, запустить систему по README и воспроизвести основной расчёт без доступа к внутренней
истории разработки или рабочей станции команды.
