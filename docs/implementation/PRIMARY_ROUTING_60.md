Это вызовы, не сумма уникальных сетей: политики и гипотезы повторяют часть вариантов.
Каждый исследовательский бюджет ограничен заранее. Радиус локальных переносов40 м;
разделение осей на5° — способ разнообразить поиск, не норма. Сравниваются обе политики
`TerminalApproachPolicy` на отдельных копиях с повторной полной финализацией.

Усиленный probe-допуск сверх production-validator включает сохранение **целых корневых
полилиний** и совместимость направлений принимающей камеры. Поэтому `accepted=false`
или `mandatory` в диагностическом логе нельзя переводить как «нарушение СП». Например,
часть экспортируемых вариантов отклонена именно по направлениям камеры. В цепочке и
обмене листьями реальные пересечения выявлены финальным валидатором и блокируют экспорт.

В первом запуске повторного обмена обнаружена коллизия ID ребра, унаследованного от seed
предыдущего probe. Исправлен только исследовательский генератор ID, проверяющий занятые
имена. Авторитетен повторный `leaf-pass-fixed.log`; исходный лог оставлен как evidence.
Это не исправление production-дефекта и не основание складывать оба запуска как gate.

Время успешных процессов: оси34,630/28,877 с, shortlist60,83 с, повторный обмен9,519 с,
перенос камеры10,173 с, цепочка10,447 с, обмен листьями9,811 с. Это время replay после
готового seed, **не время пользовательского расчёта и не доказанное ускорение**.

## Что исключил независимый аудит shortlist

Проверены все104 raw draft, восстановлен стабильный top-3-before-dedup, стоимость
пересчитана теми же sizing/economics, равенство draftScore подтверждено для каждого.
В пуле нет raw-кандидата без регрессии длины, цены, камер, bends, irregular pairs,
углов/расстояний и суммарных отклонений. Дополнительно нужен строгий выигрыш bends или ports.

Близкие дубли действительно занимают бюджет: диагностическое удаление почти коллинеарных
отсчётов с2-мм допуском сводит шесть baseline-позиций shortlist к трём семействам формы.
Эта нормализация **не используется** генератором, оценкой или допуском. Она не обнаружила
пропущенного известного raw-выигрыша. Невыбранные draft не финализированы все; finalizer
немонотонен, поэтому вывод ограничен обследованным пулом, а не глобальной невозможностью.
Лучший finished score воспроизводит59:1899,696 м/12 камер/17 поворотов/11 irregular pairs,
274329342,38 ₽, score13,380309587. Это компромисс, не улучшение по всем метрикам.

## Почему теперь нужно менять дерево раньше

Сравнение топологии по исходным данным с проверкой SHA/всех геометрий разметки показывает:

- У preferred58 одиннадцать трёхлучевых и две четырёхлучевые новые камеры.
- У кандидата11 и ручной разметки одинаковое распределение: семь трёхлучевых и четыре
  четырёхлучевые. Но остаются четыре отличающихся внутренних разбиения потребителей.
- Изменилось не только положение камер: отличается, какие здания имеют общее ответвление.
  Например, прямые группы листьев reference1/2 и13/14/15 не совпадают с baseline2/4,
  1/11 и9/14/15. Это диагностические ID, не правила генерации.
- Один узел разметки находится примерно в74,5 м от ближайшей текущей камеры. Это
  свидетельство ограничения текущего дерева/40-м локального поиска, **не** основание
  механически увеличивать радиус и бюджет.

На чертеже кандидата есть почти параллельный обратный участок ответвления рядом со
стволом: около43 м при поперечном смещении около2 м. Он объясняет, почему одно уменьшение
числа камер не даёт желаемой формы. Существующий допуск пройден; отдельное нарушение СП
этим наблюдением не установлено. Удалять участок только ради картинки нельзя.

По исходникам `OrthogonalCorridorNetworkBuilder` выбирает одну общую ориентацию через
`CorridorOrientation.angle`. `OrthogonalCorridorGrid` вычисляет её ещё раз, уже по anchors;
при сильном фасадном семействе значения должны совпадать, но fallback использует иной
набор терминалов. Расхождение fallback пока **гипотеза, не воспроизведённый баг**.
Сейчас нет ограниченного сравнения целых деревьев в нескольких согласованных системах осей.

### Следующий шаг

1. Снять инвентарь направления фасадов/допустимых нормальных вводов без reference-targeting.
   Проверить, даёт ли альтернативное представительное направление действительно другую
   сетку, привязки и дерево. Не запускать ещё серию эквивалентных локальных переносов.
2. Изолированный probe: передать одну явно выбранную ориентацию одновременно grid и spur
   router; сравнить incumbent с альтернативным целым corridor tree. Сначала малый bounded
   бюджет; не умножать дорогой global pipeline вслепую. Скорость пока гипотеза.
3. При реальном выигрыше — focused Java tests, свежий полный план без сохранённого seed,
   независимый geometry/sizing/depth/arithmetic/export gate; затем обязательные проверки
   проекта и настоящий UI→API→БД→экспорт. До них production не менять.
4. Не ослаблять валидатор/selector для продвижения понравившегося кандидата. Пользователю
   предложен выбор приоритета для «Сбалансированного»: меньше камер/цены с небольшим ростом
   bends или строгий запрет роста bends. Ответа на checkpoint нет; предвыбранный вариант
   вопроса не является согласием. Текущие ограничения сохранены, это не блокирует исследование.
