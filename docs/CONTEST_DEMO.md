## Показ на 6-8 минут

### 1. Результат сразу, 40 секунд

Открыть карту готового run и сказать:

> Перед вами единая сеть подключения 17 перспективных объектов. Алгоритм сам выбрал общие стволы,
> ответвления, камеры, расходы и диаметры. Все 17 объектов подключены, итоговый вариант прошёл
> три независимых группы проверок.

Показать общий вид, затем приблизить общий ствол и два ответвления.

### 2. Не «17 кратчайших путей», 50 секунд

Выбрать общий участок и показать его `flow_tph`, ДУ и длину.

> Здесь несколько потребителей используют одну физическую трубу. Мы не накладываем независимые
> линии друг на друга: участок существует в модели и стоимости один раз, а его ДУ рассчитан по
> суммарному downstream-расходу.

Это главный продуктовый и технический тезис.

### 3. Полный запуск, 60-90 секунд

Загрузить `datasets/official/lct-2026.geojson` или использовать demo-import, затем создать run.
Пока он выполняется, показать статус job. После завершения проверить:

- `state = completed`;
- `algorithm_version` начинается с `heatroute-network-`;
- `connected_demand_count = 17`;
- все issue-массивы пусты.

Не обещать ровно 15,918 с в каждом повторе. Сказать:

> Повторный контрольный запуск на этом VPS занял 15,918 секунды, cold run — 19,017 секунды.
> Время зависит от нагрузки и
> геометрии, поэтому мы показываем фактические timestamps самого run.

### 4. Как работает алгоритм HeatRoute, 90 секунд

Показать одну схему:

```text
GeoJSON
  → obstacle-aware каталог трасс
  → объединение совпадающих физических участков
  → CP-SAT выбирает топологию всей сети
  → frozen evaluator считает расходы, ДУ и стоимость
  → строгий GeoJSON
```

Короткое объяснение:

> Геометрический слой отвечает на вопрос «где физически можно пройти». CP-SAT отвечает на вопрос
> «какую совместимую сеть собрать». Финальный evaluator не доверяет оптимизатору на слово и заново
> проверяет готовую сеть. Если обнаружен локальный конфликт, HeatRoute расширяет только проблемную
> часть каталога и повторяет синтез.

### 5. Проверяемость, 60 секунд

Открыть Swagger и `GET /api/v1/official/runs/{runId}`. Показать:

- immutable `input_sha256`;
- `algorithm_version`;
- параметры run;
- counts и issues;
- endpoint экспорта.

Затем открыть JSON Schema результата.

> Жюри не обязано верить картинке. Версия алгоритма, вход и результат доступны через API, а
> GeoJSON проверяется опубликованной схемой и серверным валидатором.

### 6. Внедрение, 40 секунд

> Первый сценарий - предпроектный анализ района. Дальше система может получать актуальные слои
> дорог, метро, железной дороги, газа и кабелей из городских систем и возвращать варианты в
> GIS/BIM-контур проектировщика. Архитектура уже отделяет входной контракт, расчёт и экспорт.

### 7. Финал, 20 секунд

> HeatRoute превращает ручной перебор маршрутов в воспроизводимый расчёт общей сети. Наш результат
> можно увидеть, проверить через API и выгрузить. На конкурсном наборе это 17 из 17 подключений за
> 15,918 секунды без ошибок инженерного допуска.

```bash
BASE=https://130-49-150-217.sslip.io

curl --fail --silent "$BASE/api/v1/health/ready"
curl --fail --silent "$BASE/api/v1/official/runs/latest"
curl --fail --silent \
  "$BASE/api/v1/official/runs/32df0407-22a4-42b2-8426-2bb88be8d46e"
curl --fail --silent -o heatroute-result.geojson \
  "$BASE/api/v1/official/runs/32df0407-22a4-42b2-8426-2bb88be8d46e/export?variant_id=balanced"
```

## Что не говорить на защите

- «Мы доказали глобальный оптимум». Корректно: bounded-каталог + CP-SAT + точный допуск.
- «Всегда будет три варианта». Корректно: до трёх materially different вариантов.
- «Любой набор считается за 15 секунд». Корректно: повторный контрольный run на этом VPS —
  15,918 с, cold run — 19,017 с.
- «Score определяет победителя конкурса». Он ранжирует варианты внутри run.
- «Depth обязателен». Это дополнительный режим; основной результат является 2D.
- «Railway считаем как tram». Железная дорога является запрещённым пересечением.
