Основные цели: радикально сократить время полного расчёта, сохранить обязательные инженерные требования и получить воспроизводимую демонстрацию на неизвестных заранее данных. ## 2. Решение и почему оно отличается от нынешнего

Сейчас `OfficialRoutePlanner` генерирует independent/shared/spine-кандидаты и многократно выполняет финализацию, sizing, repair камер, relocation и повторный допуск. A* обслуживает локальный поиск пути, но не решает совместно всю задачу сети.

В новом движке выбираются одновременно:

- допустимые точки присоединения к существующей сети;
- общие физические ветви и подключения потребителей;
- конкретные геометрические варианты участков;
- положения и целые конфигурации камер;
- согласованные с нормативным sizing диаметры.

Глубина рассчитывается для связанной сети существующим специализированным решателем. Из точных конфликтов получается повторно используемое логическое ограничение. Это позволяет не ремонтировать заново каждое сочетание, содержащее уже доказанную ошибку.

```text
Неизменяемый снимок входа и правил
  → пространственный каталог направленных путей и камер
  → CP-SAT выбирает связанную сеть
  → FrozenNetworkEvaluator: ДУ, геометрия, общая глубина, стоимость
      ├─ допустимо → архив проверенных решений
      ├─ доказанный конфликт → корректный cut → следующий выбор
      └─ недостаточно данных/вариантов → адресное расширение каталога
  → существующий selector + независимый допуск
  → обычный result, карта, сохранение, строгий export
```

Нельзя называть это полным точным решением непрерывной городской задачи: положения камер и трассы представлены конечным каталогом. Гарантия допустимости готового результата отделена от доказательства оптимальности внутри конкретной модели.

## 3. Выбор готового решателя

### Основной выбор: OR-Tools CP-SAT через Java API

Стартовая фиксируемая версия: `com.google.ortools:ortools-java:9.15.6755`. Наличие этой Maven-версии проверено при подготовке ТЗ; официальный release — [v9.15](https://github.com/google/or-tools/releases/tag/v9.15). Перед добавлением проверить фактический POM, transitive dependencies и security advisories; не использовать плавающий `LATEST`. Лицензия OR-Tools — [Apache-2.0](https://github.com/google/or-tools/blob/v9.15/LICENSE). Зафиксировать также лицензии/версии поставляемых native зависимостей, а не только верхнего JAR.

Причины выбора: булевы решения, целочисленные ограничения, готовый поиск по ограничениям, Java API и отсутствие обязательного платного облачного сервиса. Геометрический движок не заменяется: JTS и существующие инженерные компоненты остаются. Поддержка конкретной комбинации Java 11, protobuf, JNA, архитектуры CPU, libc и Spring Boot должна быть доказана загрузкой и solve в целевом образе, а не только успешной компиляцией.

CP-SAT работает с целочисленными ограничениями; различает `OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `MODEL_INVALID`, `UNKNOWN`. Их смысл ограничен переданной моделью. [Официальный контракт](https://developers.google.com/optimization/cp/cp_solver). Механизм наших внешних конфликтов — цикл solve/check/add-cut; не предполагать наличие произвольных lazy constraints внутри callback.

### Рассмотренные альтернативы

| Подход | Решение |
|---|---|
| SCIP-Jack | Полезен для задачи Штейнера, но не готовый Java-движок с нашими камерами/ДУ/depth. Сайт указывает отдельные условия коммерческого лицензирования. Не делать обязательным компонентом поставки: [источник](https://scipjack.zib.de/) |
| topotherm / MILP-модели теплосетей | Полезный открытый reference, но Python/Pyomo и иная модель проектирования; перенос всего сервиса нарушил бы текущую архитектуру. Использовать для сравнения постановок, не как второй backend: [репозиторий](https://github.com/jylambert/topotherm) |
| Density-based / adjoint topology optimization | Перспективный иной класс методов, но восстановление дискретных труб, камер и наших строгих углов требует отдельного решения. Не включать обязательную научную разработку в критический путь этой поставки: [исследование](https://pub.vito.be/openaccess/benchmarkDHN_postscript.pdf) |
| Новый shortest-path алгоритм вместо A* | Не устраняет совместный выбор ветвей, камер и повторные ремонты. Не является основной архитектурой нового движка |
| Собственный SAT/MIP solver | Не писать: эту инфраструктуру закрывает CP-SAT. Собственный код нужен для инженерной модели, каталога, доказанных конфликтов и интеграции |

Используется идея [logic-based Benders / branch-and-check](https://johnhooker.tepper.cmu.edu/encyLBBD.pdf): сложная задача разделяется на выбор решений и специализированную проверку. Называть конкретную реализацию точным LBBD можно только после доказательства корректности её cuts и bounds; до этого корректное название — constrained search с проверкой и внешними конфликтами.

## 5. Неприкосновенные инженерные правила

Детальные таблицы не дублировать в новом solver вручную: получать из действующих каталогов с fingerprint. Обязательная матрица:

| Область | Сохранить |
|---|---|
| География | WGS84 на API-границе, EPSG:32637 для метров; та же миллиметровая граница `RouteCoordinate`; нельзя проверять до округления, а публиковать после без повторного допуска |
| Углы | Фактический внутренний угол 90–120°, правила коллинеарности и нормальных выходов ОКС; technical vertex не сбрасывает расстояние между поворотами |
| Spacing | Таблица 2–6 м по всем 18 ДУ, оба конца камера→камера; минимум 10 м между последовательными новыми камерами |
| Камеры | До четырёх разных лучей по взаимно перпендикулярным осям; существующая проходящая труба занимает два луча; подходы проверяются по фактическим конечным сегментам |
| Корни | Подтверждённая опора на существующую геометрию; использование пригодной существующей камеры в пределах 10 м; локальность исключения врезки |
| Коммуникации | Полные горизонтальные отступы по окончательному ДУ; специальные интервалы и crossing angles из актуальных правил; bbox — только broad phase |
| DU/flow | Потоки суммируются на общем стволе; каталог по расходу и непрерывной длине; одинаковый ДУ на связанном неизменном расходе, без уменьшения к источнику |
| Depth | Полный связанный профиль, общие отметки узлов, уклоны/crossings/floors по действующему решателю и независимому validator; depth=true нельзя незаметно отключить |
| Экономика | Действующие цены, секции, глубинные множители, округления, камеры и отдельные новые лучи существующей камеры; без новых выдуманных штрафов за повороты |
| Coverage | Не отключать технически доступного потребителя ради стоимости; не выдавать исчерпание поиска за доказанную невозможность |
| Выход | Существующие JSON DTO и четыре строгих типа export: `heatNetwork`, `heatChamber`, `technicalNode`, `variantSummary`; реконструкция существующих активов не возвращается |

Не увеличивать допуски, не урезать препятствия, не подставлять корни/камеры из ручной схемы. Depth defaults остаются прежними, но конкурсные speed/quality gates выполняются с явно включённой глубиной.

| `job/OfficialJobWorker`, `OfficialJobRepository`, `run/OfficialRunService` | Native cancellation, fencing попыток, согласованное сохранение и версия queued job |
| `export/OfficialGeoJsonExporter`, Saved*-assessment | Независимая проверка результата перед экспортом; не обходить solver-флагом |

Новые компоненты разместить первоначально в `domain.routing`, так как многие текущие building blocks package-private. Не делать весь пакет public ради интеграции. Изоляция зависимостей: native API виден только в adapter, внутренняя модель не содержит protobuf/JNI объектов. Java 11: обычные `final class`, не `record`/`sealed`.

| Новый компонент | Единственная основная ответственность |
|---|---|
| `RoutingProblemSnapshot` / `RoutingProblemFactory` | Неизменяемый вход, источники, demands, roots, версии правил и параметры |
| `RoutingCatalogCompiler` / `RoutingCatalogSnapshot` | Создание и версии конечного каталога |
| `DirectedPathOptionCompiler` | Фиксированная направленная геометрия и её проверенные условия допуска |
| `PhysicalAssetCompiler` | Общие физические участки, accounting/topology splits и цепи |
| `ChamberConfigurationCompiler` | Целые совместимые наборы лучей и подходов камеры |
| `SpatialConflictCompiler` | Пространственные кандидаты конфликтов и точные доказательства |
| `NetworkConstraintModel` / `CpSatNetworkSolver` | Точная конечная constraint-модель и единственный OR-Tools adapter |
| `FrozenNetworkEvaluator` | Оценка выбранной сети без изменения XY/topology |
| `ConflictExplanation` / `ConflictStore` | Проверяемые, версионированные внешние cuts |
| `AdaptiveCatalogExpander` | Адресное добавление отсутствующих обходов/корней/камер |
| `AcceptedSolutionArchive` | Неизменяемые полностью допущенные варианты, exact metrics и distinct |
| `NextGenerationRoutePlanner` | Общий deadline, solve/check/refine, диагностика и result assembly |
| `RoutingExecutionDescriptor`, `RoutingCancellation` | Версия выполнения, deadline и остановка Java/native |

Не создавать все классы пустыми заранее. Вводить по этапам с тестами; малые value objects можно объединять, если сохраняется ясная ответственность. Не плодить универсальные `Utils` и не передавать весь старый planner как service locator.

## 7. Неизменяемый вход и каталог вариантов

### 7.1. `RoutingProblemSnapshot`

Фиксировать `importId` и source hash, input profile, CRS, code/rules/catalog versions, parameters включая depth, demands с действительным расходом, разрешённые roots с существующими направлениями, feature-source snapshot. Snapshot должен обеспечивать согласованность window reads: один расчёт не видит меняющийся импорт.

Не переносить дефект core input: `OfficialFeatureRepository.findCore...` не включает `oks_future`, а нынешний resolver может использовать нулевой flow fallback. Перед новым solver отдельно исправить/проверить extended case, где расход расположен у связанного ОКС. Отсутствующий обязательный расход — диагностируемая ошибка ввода, а не придуманное нулевое значение. При допустимом нулевом расходе потребитель всё равно участвует в задаче связности.

Feature data не загружается целиком ради snapshot: большие obstacles читаются страницами/окнами. Неизменяемость означает стабильную версию источника, а не обязательно копирование гигабайтного импорта в heap.

### 7.2. `PathOption`

Обязательные данные: стабильный option ID, from/to port IDs, направление, immutable ordered coordinates, physical asset references, sections, длины, крайние касательные, расстояния до ближайших фактических поворотов, provenance, условия endpoint/root contact и множество **проверенных** ДУ. Разная геометрия/направление/проверочный контекст — разные варианты.

Не давать наружу изменяемые `Coordinate`, `Geometry`, `JsonNode`. `List.copyOf` не замораживает их содержимое. Fingerprint используется для быстрого поиска, equality проверяет полный контракт; hash collision не означает совпадение трасс.

Два уровня сертификата: `SEGMENT_LOCAL` и `COMPLETE_PHYSICAL_PATH`. Даже второй подтверждает путь при перечисленных предпосылках, не всю сеть. В сертификате: rule hash, source snapshot, ДУ, направление, endpoint context, sections и состав выполненных проверок.

Для каждой комбинации direction/context + ДУ хранить отдельный статус `VERIFIED_ALLOWED`, `PROVEN_FORBIDDEN` или `UNCHECKED`. Непроверенный ДУ не равен запрещённому: нужен admission/refinement, а не ложный proof cut. Не предполагать монотонность допустимости по ДУ — особенно у специальных проходов и DU-зависимой геометрии.

Критические ловушки нынешних builders:

- `OrthogonalCorridorGrid.link` может сохранить связь, допустимую хотя бы в одном направлении. Для solver отдельно проверить каждую направленную дугу.
- `OrthogonalCorridorNetworkBuilder.buildWithAnchors` использует ДУ общего расхода при построении сетки. Нельзя этим ДУ отфильтровать все узкие ветви нового каталога: нужны индивидуальные допустимые DU domains.
- `PreparedCorridor.completeCheckedAssembly` не заменяет полноценный forbidden/utility clearance.
- Техническая вершина внутри road special не делит специальный проход на независимые разрешения и не сбрасывает bend/length/depth-station контекст.
- Текущие ограничения отдельных helper на 64 terminal нельзя превратить в контракт нового сервиса или молча отбрасывать demands после 64-го.

### 7.3. Общие физические участки

Каталог различает выбор пути и выбор **физического актива**. Общий ствол нескольких подключений должен получить один суммарный flow, один нормативный ДУ и одну стоимость.

Частичные совпадающие интервалы разбивать на атомарные учётные участки; соединять ветви только в явно разрешённых ports/junctions. Обычное XY-пересечение не создаёт камеру автоматически. Обратное направление имеет тот же physical ID только при совпадении реального актива и контекста, но отдельный directed admission. Разные уровни/исполнение не объединять по одному XY.

Должна быть отдельная сборка физических цепей для sizing, depth и economics. Атомизация не создаёт фиктивные камеры и не меняет округление стоимости из-за большего числа рёбер. Тест technical-split invariance обязателен. Если незаконность наложения доказана, варианты несовместимы. Если пока не хватает представления/проверки общего актива — это `UNKNOWN` и запрос atomization/refinement; возможное временное ограничение неполного каталога не является инженерным proof cut. Не «склеивать» непроверенные участки для экономии стоимости.

### 7.4. Конфигурации камер и техузлов

Генерировать целую конфигурацию: положение, тип, оси, выбранные incident options, неизменяемые существующие лучи, допустимые сочетания ДУ и подходов. Pairwise compatibility не доказывает общую вместимость. Degree-2 техузел не становится бесплатной камерой; его переход также проверяет продолжение полилинии и историю spacing.

Позиции предлагать из нормалей ОКС, пригодных существующих камер, пересечений коридорных осей и существующих relocation helpers. Не использовать координаты/ID контрольного результата как генератор. Камеры с альтернативными положениями представлять разными физическими конфигурациями с mutually-exclusive choice, а не перемещать после solve без смены решения.

### 7.5. Полнота каталога и расширение

`CatalogBuildResult` содержит snapshot, counters, coverage генераторов, remaining work и причины truncation. Пустой результат при исчерпанном бюджете — `CATALOG_INCOMPLETE`, а не географическая невозможность.

Начальная подготовка должна быть компактной и сохранять несколько геометрически разных доступных обходов/roots; не только один ближайший root или один shortest path. Расширение адресное: проблемный terminal, congestion камеры, другой DU, объезд, продолжение road special, другое положение камеры, межоконный коридор. Использовать пространственную индексацию и существующие caches, а не all-pairs геометрию всех объектов.

Каталог расширяется монотонно в пределах одного snapshot; ранее допустимый incumbent не теряется. Бюджеты по memory/nodes/options/constraints/time относятся к поиску, а не к инженерным допускам. Масштабирование на большой импорт не означает независимую оптимизацию районов с потерянными межрайонными соединениями: нужны boundary ports и общий согласующий граф.

Монотонность относится к сохранению ранее представимых физических решений, а не к неизменному разбиению рёбер. Новый junction может разрезать asset: нельзя менять geometry/состав под старым ID. Создать новые IDs/catalog version, согласованно отобразить incumbent/hints и повторно проверить certificates, cut scopes и sizing implications. Старое решение должно оставаться воспроизводимым через явное отображение, иначе expansion считается некорректным.

## 8. Математическая модель CP-SAT

### 8.1. Объекты и переменные

Пусть `G=(V,A)` — конечный граф, `A=A_phys ∪ A_book`: `A_phys` содержит фиксированные направленные физические варианты, `A_book` — только разрешённые bookkeeping-связи учёта; `T` — потребители; `R` — допустимые корни. Один реальный участок с альтернативными geometry/направлением не должен выбираться как две наложенные трубы без явного инженерного разрешения.

| Переменная | Смысл |
|---|---|
| `x_a ∈ {0,1}` | Выбрана дуга из `A_phys` или разрешённая bookkeeping-дуга из `A_book` |
| `z_v ∈ {0,1}` | Узел используется |
| `r_v ∈ {0,1}` | Узел является активным разрешённым корнем |
| `q_t ∈ {0,1}` | Потребитель подключён |
| `c_vk ∈ {0,1}` | Выбрана конфигурация узла/камеры |
| `y_ad ∈ {0,1}` | Выбран ДУ варианта из официального каталога |
| `h_v` | Целочисленный топологический порядок |
| `K_a` | Число подключённых потребителей ниже дуги |
| `F_a` | Суммарный расход ниже дуги в точных целочисленных единицах |

Все множества имеют детерминированные canonical IDs и порядок. Snapshot solver-модели не содержит текущие случайные UUID run. Если высокая детализация требует отдельной path-selection variable, связать её с **всеми** входящими атомарными assets; не позволять выбирать половину пути, игнорируя его специальные участки и условия концов.

### 8.2. Связность, корни и отсутствие циклов

Для каждого узла:

```text
sum(x_a для входящих дуг из A_phys ∪ A_book) = z_v - r_v
r_v <= z_v; r_v = 0 для v вне R
x_(u,v) <= z_u; x_(u,v) <= z_v
x_(u,v) = 1 => h_v >= h_u + 1
0 <= h_v <= |V|-1
```

Для demand leaf `z_t=q_t`, любые исходящие дуги запрещены. Если несколько demands имеют одну точку, представить отдельные виртуальные leaves, не сливать их IDs/расходы. Bookkeeping-дуга соединяет только свой виртуальный leaf с уже определённым физическим attachment в той же точке; не соединяет произвольные места и не заменяет обязательный реальный ввод/нормаль ОКС. Все реальные подключения и занятые ими лучи представлены физическими options/configurations.

Parent constraints, ацикличность, `K` и `F` учитывают **оба** множества дуг. Геометрические пересечения, строительная стоимость, physical ray capacity и ДУ относятся только к `A_phys`; `A_book` не создаёт трубу или камеру. Это не должно давать виртуальный обход obstacles/spacing. Источник `σ` ниже служит только балансу и не входит в ограничения родителя физических/виртуальных узлов.

Единственный родитель + ацикличность гарантируют лес, укоренённый в разрешённых врезках. Несколько корней допустимы; нельзя принудительно свести всё к одной врезке. Не добавлять ёмкость/резерв существующего источника, отсутствующие в действующем входном контракте.

Для запрета бесполезных ветвей ввести виртуальный источник `σ` и счётчик consumers:

```text
x_a <= K_a <= |T| * x_a
r_v <= K_(σ,v) <= |T| * r_v
sum(K_in) + K_(σ,v) = sum(K_out) + sum(q_t для consumers узла)
```

`K_(σ,v)=0` вне roots. Это требуется и при нулевом тепловом расходе. Отдельно закон сохранения реального расхода:

```text
0 <= F_a <= Q_total * x_a
0 <= F_(σ,v) <= Q_total * r_v
sum(F_in) + F_(σ,v) = sum(F_out) + sum(demandFlow_t * q_t)
```

Общие physical assets имеют одну выбранную ориентацию/конфигурацию; противоположные направления и взаимоисключающие реализации связать ограничениями суммы ≤1. Никакого списания стоимости по commodity и повторного сооружения общего участка для каждого demand.

### 8.3. Узлы, лучи и конфликты

Для выбираемого узла `sum_k c_vk=z_v`. Конфигурация задаёт **точный** набор выбранных incident options; для каждого инцидентного `a`:

```text
x_a = sum(c_vk для конфигураций k, включающих a)
```

Аналогичная проверяемая связь нужна для technical transition, если правила пути требуют контекста соседних участков. Нельзя проверять только degree≤4: нужны лучи, существующие направления, нормали, DU-зависимые отступы и spacing через промежуточные техточки.

Доказанно несовместимые фиксированные options: `x_a + x_b <= 1`. Условный конфликт зависит от конкретной конфигурации/ДУ/корневого контакта и получает соответствующие literals. Допустимый контакт в общей камере требует выбранной совместимой конфигурации, а не просто близких координат. Общий physical asset — reuse, не pair collision.

STRtree используется только для отбора кандидатов конфликтов; точный геометрический oracle устанавливает сам конфликт. Clique constraint `sum(x)<=1` допустима только для множества с доказанным конфликтом каждой пары. Связная компонента conflict graph не является clique. Для конфликтов трёх и более решений использовать hyperedge/no-good с достаточным контекстом.

### 8.4. DU: релаксация master и нормативный расчёт

```text
sum_d y_ad = x_a
y_ad = 1 => F_a <= catalogueMaxFlow(d)
y_ad = 0, если данный directed option доказанно недопустим при d
```

Это **не полный sizing**. Непрерывные same-flow цепи, минимальность ДУ и ограничения длины остаются в `OfficialNetworkSizer` / `SameFlowDiameterAssignment` до доказанного эквивалентного переноса.

Протокол согласования: для выбранных topology/geometry/connections вычислить канонический нормативный sizing. Если master выбрал другие ДУ, не запрещать всю топологию. Определить отдельный `SizingScope B`: выбранные **и невыбранные** topology/geometry/root/configuration/consumer decisions и версии demand/input/catalog. В `B` **не входят текущие `y`**, топологические номера `h`, производные flow и depth. При допустимом нормативном sizing вернуть `CANONICAL_SIZING_REQUIREMENT` и добавить для каждой выбранной физической дуги `B ⇒ y_(a,canonicalDiameter(a))=1`; решить модель снова. Так исключаются все неправильные комбинации ДУ этой сети, а не только одна.

Если canonical DU ещё `UNCHECKED` для PathOption, запросить его проверку/расширение domain, а не объявлять сеть невозможной. Если нормативный sizing сам вернул issues, ответ — обоснованный отказ фиксированного назначения либо UNKNOWN при неполном контексте, не набор якобы правильных ДУ. При смене длины, descendants, geometry или версии каталога `SizingScope` другой.

При сборке общих атомарных участков установить соответствие variables ↔ физические same-flow цепи, чтобы невозможно было искусственно уменьшить непрерывную длину. Последующий допуск выполняется только с окончательными ДУ. Геометрия, допустимая при одном ДУ, не получает автоматически допуск при остальных.

### 8.5. Числа и стоимость

Расходы и коэффициенты переносить в integer domain без потери предусмотренной контрактом точности. Масштаб выводить из проверенных данных/правил, а не округлять все расходы до произвольных целых. Проверить bounds каждого выражения и int64 overflow до solve. Модель с переполнением/неподдержанным scale даёт явную техническую ошибку, не молчаливое упрощение.

Стоимость участка учитывается один раз на physical asset/цепь с сохранением официального порядка округлений. Камера — один раз по максимальному действительному инцидентному ДУ. **В существующей камере 5 млн ₽ начисляются на каждый новый исходящий луч, а не один раз на активный root**; новая камера уже включает присоединение. Источник истины — `OfficialVariantEconomicsCalculator.tieInCount` и `OfficialEconomics`.

Точный score вычисляется нынешним `OfficialEconomics.score`: 0,7 нормированной стоимости + 0,3 нормированной длины с его промежуточными и конечным округлениями. Не заменять его «похожей» целочисленной функцией при окончательном выборе.

Master может использовать доказанную нижнюю границу стоимости и guiding objective. Для lower bound необходимо доказательство отсутствия завышения с учётом rounding, shared assets, chambers, special sections и depth. Если доказательства нет — оценка только направляет поиск, не служит cut, gap или основанием отсечения. Консервативный нулевой bound допустим для начала разработки, но не освобождает от performance gate.

### 8.6. Coverage-first и три роли

Сначала искать полное подключение (`q_t=1` для всех). Если оно не найдено, расширять каталог и различать timeout/неполноту/доказанную infeasibility конечной модели. Для частичного результата сначала максимизировать coverage, затем применять действующий выбор стоимости/длины/качества; не жертвовать coverage ради дешёвого score.

Каждый proof descriptor хранит `coverageConstraint/requiredCoverage`, input/rules/catalog hash, depth profile и дополнительные role-ограничения. «Нет полного решения» не означает «нет частичного». При необязательных `q` пустой лес математически допустим, но не является готовой полезной сетью; для поиска непустого решения задавать `sum(q)>=1`. Максимальность найденного частичного покрытия заявлять только после доказательства невозможности большего coverage в том же scope. Cuts этапа полного подключения не переносятся в частичный без проверки предпосылок.

Поддержать портфель `cheapest`, `shortest`, `balanced` через общую модель и общий архив допущенных решений, разделяя глобальный time budget. Повторно использовать каталог, cuts и hints; не запускать три полных legacy pipeline. Последний выбор выполняет `FinishedRouteVariantSelector`, включая не накапливаемые quality budgets source102. Нельзя считать CP-SAT surrogate objective заменой этого selector.

Для каждой роли фиксировать `objectiveId`, последовательность критериев и область определения anchors. Selector над найденным архивом не доказывает optimum всего каталога: поздний кандидат может поменять minimum-length/cost anchor и quality corridor. Для `balanced` по умолчанию публиковать `FEASIBLE_VALIDATED`; `OPTIMAL_IN_CATALOG` разрешён только при отдельно доказанных необходимых anchors и точной целевой функции. Proof/gap другой роли не наследуется всей тройкой вариантов.

До трёх различающихся сетей получать по canonical physical identity. Чтобы искать альтернативу, временно исключать уже **оценённое** назначение в отдельном enumerator; это не доказательство его недопустимости. Такие exclusions не должны загрязнять proof-model и менять значение `INFEASIBLE` на «в природе нет сети».

## 9. `FrozenNetworkEvaluator`: главный контракт корректности

Вход: immutable выбранная topology/XY, roots, chamber configurations, connections, согласованные ДУ, rules/input snapshot и cancellation/deadline.

Порядок:

1. Проверить целостность выбранного графа и собрать физические цепи, сохранив provenance.
2. Выполнить нормативные flow/sizing; согласовать master DU по протоколу выше.
3. Проверить готовую геометрию с этим ДУ: нормали, obstacles, special sections, камеры, bends и spacing.
4. При depth=true рассчитать **общую** depth network; проверить её независимым валидатором.
5. Рассчитать точную экономику/score и независимую арифметику.
6. Создать `AcceptedSolution` только после всех обязательных проверок; окончательная публикация дополнительно проходит текущий selector и Saved*-export assessment.

**Evaluator не перемещает камеры, не reroute, не simplify и не меняет XY/topology.** Назначение производных flow/ДУ/depth не является перемещением геометрии, но обязано согласоваться с выбранными literals. Входные объекты не мутируются. Hash геометрии/связности до/после должен совпадать.

Нынешний `OfficialRoutePlanner.finish` меняет геометрию: его нельзя просто вызвать и выдать результат B за оценку выбранной сети A. Старый repair/finish можно использовать как generator нового предложения B; тогда B заново компилируется в каталог, получает собственные certificates и полную оценку. Никакие bounds/optimality A не присваиваются B.

Ответ evaluator — один из:

- `ACCEPTED(solution, exactMetrics, validationReceipt)`;
- `CANONICAL_SIZING_REQUIREMENT(assignmentScope, requiredDiameters)`;
- `PROVEN_REJECTED(conflictExplanation)`;
- `UNKNOWN(reason, refinementRequests)`;
- `ERROR(typedFailure)` — техническая неисправность, отдельно от инженерной невозможности.

`AcceptedSolution` — Java 11 final class с закрытым/ограниченным конструктором и immutable данными. Callback CP-SAT не может создать его напрямую. Нативный `FEASIBLE` означает только решение master, пока evaluator не завершил допуск.

## 10. Доказанные конфликты, bounds и статусы

### 10.1. Структура `ConflictExplanation`

Обязательные поля: тип, rule ID/version, source/catalog snapshot, достаточные decision literals, зависимые DU/flow/root/terminal условия, ссылки на геометрию/события, причина, версия checker, proof scope. Внутренний proof artifact не должен содержать секреты и гигабайтные копии входа.

Если все literals `l_i` одновременно истинны и это доказанно невозможно, добавляется `sum(l_i)<=n-1`. Для отрицательного literal использовать `1-x`, а не забывать невыбранные варианты. Переменные `h`, случайные flow representations и временные индексы не должны создавать разные physical identities одного решения.

Для полного no-good обязательна достаточность контекста. Набор только выбранных дуг часто недостаточен: добавление разрешённого junction/другой конфигурации может устранить конфликт. Когда минимальный конфликт не доказан, использовать полное relevant физическое назначение с выбранными **и невыбранными** решениями конечного каталога.

### 10.2. Примеры корректного и некорректного обучения

| Наблюдение | Корректное действие | Запрещено |
|---|---|---|
| Фиксированные пути A и B незаконно пересекаются | Запретить A+B при указанном junction/context | Запретить A целиком, если A+C допустимо |
| Выбранные лучи не помещаются в камеру | Запретить несовместимую конфигурацию | Запретить весь географический район |
| Путь не проходит при DU=400 | Cut с literal DU=400 и нужным context | Запретить тот же XY для всех диаметров |
| Общая depth-задача доказанно несовместима | Cut по всем предпосылкам сертификата сети | Назначить виновным случайное ребро |
| Bounded router не нашёл обход | UNKNOWN + запрос расширения | INFEASIBLE/cut для всей топологии |
| Solver истёк по времени | Сохранить accepted incumbent либо честный timeout | Считать UNKNOWN доказанным no_route |
| Fixed assignment оценён точно | Сохранить cost/result; допустим scoped exact-cost implication | Перенести exact cost на другую сеть с той же длиной |

При расширении каталога проверить, остаётся ли cut истинным. Геометрический конфликт фиксированной пары обычно сохраняется; полный no-good старого каталога нельзя трактовать как запрет этой пары при добавлении устраняющего конфликт решения. Versioned full-assignment scopes должны быть перебазированы/переобъяснены либо отключены. Неизменность input/rules тоже обязательна.

`ConflictStore` хранит доменные доказательства между solve-вызовами. **Не предполагать**, что внутренние SAT learned clauses сохраняются при новом `CpSolver.solve`; модель может пересобираться, reusable state — собственные проверенные cuts и hints. Не модифицировать модель из callback во время native solve. Callback только копирует ограниченный assignment/telemetry и при необходимости запрашивает остановку.

### 10.3. Оптимальность и полнота

Различать:

- `FEASIBLE_VALIDATED` — готовая сеть прошла инженерный допуск;
- `OPTIMAL_IN_CATALOG` — доказан optimum для указанного catalog hash, точной objective и политики evaluation;
- `INFEASIBLE_IN_CATALOG` — конечная модель не имеет решения при указанном coverage/objective/role scope; это не утверждение об иных scopes;
- `SEARCH_LIMIT_REACHED` / `CATALOG_INCOMPLETE` — поиск не завершён;
- `ERROR` / `CANCELLED` — технический исход/отмена.

`CP-SAT OPTIMAL` для lower-bound surrogate не означает `OPTIMAL_IN_CATALOG` точной экономики. Нельзя показывать gap, вычисленный между разными objectives, разными coverage или разными catalog versions. Оптимальность на всём городе не заявляется даже при точном решении конечного каталога. На ограничениях времени рабочий результат — лучший полностью проверенный incumbent с честным статусом поиска.

Не отдавать пользователю инженерную причину «присоединение невозможно», если доказано лишь отсутствие решения среди перебранных портов. Для partial variants UI показывает фактическое покрытие и различает доказанную причину и незавершённый поиск; строгая экспортная схема при этом не расширяется произвольно.

## 11. Полный цикл и контроль времени

Все этапы используют общий монотонный deadline. Стартовые ориентиры распределения 300 с: input/context до 10%, каталог до 25%, совместный поиск/подзадачи до 50%, финальный допуск/сохранение/export резерв не менее 15%. Это начальные настройки, не основание обрывать обязательную проверку. Невыбранный бюджет передаётся следующему этапу; telemetry фиксирует фактический расход.

```text
problem = loadImmutableProblem(executionDescriptor)
catalog = compileInitialCatalog(problem, sharedBudget)
archive = emptyAcceptedArchive()
conflicts = emptyVersionedConflictStore()

while budget leaves time for mandatory final admission:
    assert not cancelled and lease still owned
    master = buildModel(catalog, conflicts, currentRole, hints)
    answer = solveBounded(master, remainingBudget)
    if answer has a candidate:
        assessment = evaluateFrozen(candidate)
        ACCEPTED: archive exact solution; schedule other roles/alternatives
        SIZING_REQUIREMENT: add scoped canonical-diameter implication
        PROVEN_REJECTED: check certificate; add sound scoped cut
        UNKNOWN: record reason; request targeted catalog expansion
        ERROR: handle typed failure; never manufacture infeasibility
    else:
        distinguish model infeasibility / timeout / invalid model
        expand relevant catalog if useful and allowed by budget
    retain archive; version cuts correctly after expansion

if cancelled or lease lost: stop native work; never publish completed
if archive empty: return typed no-validated-result outcome
select and independently recheck accepted results
persist atomically under current attempt ownership; strict export
```

`UNKNOWN` нельзя «обработать» бесконечным повтором того же assignment. Координатор хранит pending/visited assignments и меняет refinement context или план работы; временное исключение pending assignment — scheduling state, не feasibility proof. После снятия UNKNOWN такой assignment доступен снова.

Durable outcome должен быть явным: пустой archive после search limit / incomplete catalog / error → `failed` с типизированным кодом, а не обычный `OfficialCalculationResult` с пустыми variants, который worker ошибочно пометит completed. Полностью проверенный непустой incumbent по deadline → `completed` с честным внутренним статусом поиска и фактическим coverage. Принятая отмена → `cancelled`. Потерявший lease worker вообще не записывает terminal state чужой/новой попытки. Доказанная infeasibility заданного каталога без результата сохраняется как отдельный предметный код неуспешного run, не как фиктивная готовая сеть.

Для быстрого первого решения использовать ограниченные существующие generators или CP-SAT hints, но **не запускать перед каждым новым расчётом полный старый 42–73-минутный planner**. Время seed-generation входит в лимит. Старые сохранённые ответы допустимы только как явно проверенные hints для точно совпадающих input/rules/parameters; конкурсные cold gates не используют готовый ответ.

Сначала один solver worker на job, фиксированный seed и стабильный порядок модели. Повторяемость проверять при deterministic work budget; wall cutoff может оборвать поиск в разный момент — это явно отражать. Многопоточный solver включать только отдельным измеренным change с повторяемостью качества и ресурсным gate; не распараллеливать общий mutable environment через `parallelStream`.

## 12. Интеграция, устойчивость и native runtime

### 12.1. Единственный production-профиль

`RoutingAlgorithmRegistry` сейчас допускает ровно один `STABLE`; `expert_experimental` — legacy alias того же алгоритма. Во время разработки новый planner вызывается из тестов/внутреннего adapter, не регистрируется вторым `RoutingAlgorithm @Component`. После приёмки единственный `StableRoutingAlgorithm` делегирует новому planner; старое wire-name поведение сохраняется.

Назначить новую уникальную algorithm version, связанную с кодом/model/rules/solver manifest. Не записывать новый результат под `global-tree-102`. `OfficialRunService` сохраняет version при постановке, но нынешний worker выбирает реализацию позже по parameters: это разрыв. Добавить immutable execution descriptor; worker проверяет/разрешает сохранённую версию до расчёта. Не выполнять молча старый queued job новым engine. Разрешён явный отказ `ENGINE_VERSION_UNAVAILABLE` с возможностью создать новый run; completed legacy результаты читаются без пересчёта.

### 12.2. Сохраняемые endpoints

| Действие | Контракт |
|---|---|
| Импорт multipart `file` | `POST /api/v1/official/imports` |
| Новый run | `POST /api/v1/official/imports/{importId}/runs` |
| Run/result | `GET /api/v1/official/runs/{runId}` |
| Последний завершённый | `GET /api/v1/official/runs/latest` |
| Job | `GET /api/v1/official/jobs/{jobId}` |
| Отмена | `DELETE /api/v1/official/jobs/{jobId}` |
| Строгая выгрузка | `GET /api/v1/official/runs/{runId}/export?variant_id=...` |

Для конкурсного замера body run: `{"depth_enabled":true,"algorithm_profile":"stable"}`. Preserve SNAKE_CASE и старые defaults. Solver metadata/доказательства хранить в отдельном внутреннем диагностическом артефакте/manifest, не добавлять полей в strict GeoJSON. Если для UI нужны новые поля прогресса, делать additive versioned API change с schema/controller/frontend тестами, не случайные Jackson getters.

UI должен показывать корректные этапы, elapsed time, реальное покрытие, длину/стоимость/ДУ/глубину и причины частичного результата. Не показывать fabricated проценты прогресса и слово «оптимальный» без допустимого proof scope. Изменение UI ограничить этими данными, без общего редизайна.

### 12.3. Native cancellation и владение попыткой

Java interrupt недостаточен для native solve. Создать per-attempt handle `(jobId, attempt, leaseOwner)` и связать cancellation с `CpSolver.stopSearch()`, предусмотренным [Java API выбранной версии](https://raw.githubusercontent.com/google/or-tools/v9.15/ortools/java/com/google/ortools/sat/CpSolver.java). Проверить токен до регистрации, после неё, после native return и перед публикацией. Предусмотреть race: stop, пришедший до создания внутреннего solver handle, не должен потеряться; latched token + ограниченный повтор stop/короткий watchdog до подтверждённого выхода. Потоки watchdog bounded и закрываются в finally.

Не удерживать application monitor/lock на всё время `solver.solve(...)`, если stop/cancellation используют этот же lock: иначе отмена заблокируется до естественного завершения поиска. Регистрация/снятие handle — короткие критические секции; длительный solve выполняется без блокировки доступа к stop.

Permit возвращается только после фактического завершения native/Java работы. Не освобождать slot, пока отменённый solver продолжает занимать CPU/RAM. Отмена даже с accepted incumbent остаётся `cancelled`, не скрытым `completed`. При общей потере lease остановить solve и запретить запись результата.

Перед production закрыть текущие дефекты: утечка permit при исключении `claimNext`; heartbeat ownership loss только в логах; run/job completion отдельными неатомарными updates без owner/attempt fencing. Нужен transactional transition service и conditional SQL с проверкой affected rows. Моки не заменяют реальные DB tests rollback, stale worker и cancel/complete race.

Долгую read-only транзакцию `OfficialCalculationService.calculate` не держать вокруг CPU/native solve. Выделить реальную Spring transactional границу core snapshot и короткие window reads; self-invoked private annotation не работает как отдельная транзакция. До изменения доказать неизменность import и согласованность всех feature windows.

### 12.4. Native packaging и память

`infra/docker/backend.Dockerfile` использует Alpine и JRE runtime; `MaxRAMPercentage=75` не учитывает большой native heap. Проверить pinned OR-Tools в **реальном конечном образе**: Java 11, CPU arch, libc, non-root UID 10001, writable temp, запуск из packaged Spring Boot JAR. Maven unit test на Windows не доказывает этот gate. Если бинарный пакет не поддерживает libc образа, перейти на проверенный glibc-based Java 11 image отдельным change; не собирать новый toolchain на C: и не менять всю архитектуру.

Native loader извлекает ресурсы во временный каталог: [код Loader v9.15](https://raw.githubusercontent.com/google/or-tools/v9.15/ortools/java/com/google/ortools/Loader.java). До Maven/test/app startup задать `java.io.tmpdir`, TEMP/TMP и при необходимости JNA temp на E: для Windows; контейнерные temp/data должны физически размещаться в существующей Docker storage на E:. Ничего не скачивать при первом пользовательском расчёте: все зависимости входят в сборку.

На старте приложения выполнить capability test: load → маленькая задача с известным ответом → освобождение. Readiness native-engine требует его успеха. Наличие класса не означает готовность; `UnsatisfiedLinkError` не покрывается обычным `catch(Exception)` worker.

Установить и проверить cgroup/Compose лимиты, а не только описать их в документации. Совокупность heap, native solver, direct buffers, thread stacks и safety headroom должна помещаться в API budget. Ограничивать размер каталога/модели до solve. Native memory flag не считать надёжным hard limit без доказанного поведения. Проверять process RSS/cgroup peak, repeated runs и аварийное завершение JVM с последующим lease recovery.

Не повышать concurrency до 50: 50 пользовательских сессий — это responsive API + очередь, а не 50 одновременных native solves. Начальная production capacity 1 job, затем 2 только после load/memory/lease gates; scheduler budget учитывает solver workers × running jobs.

Параллельно разрешены независимые catalog, pure-evaluator и native-adapter задачи после фиксации DTO/contracts. Модель и conflicts должны согласовать одну identity/units схему до интеграции. Git mutations сериализовать; ownership файлов явно распределить. Не интегрировать чужие незавершённые изменения одним общим commit.

Каждое завершение gate обновляет `docs/implementation/progress.md` и roadmap доказательствами, не плановыми обещаниями. При новой кодовой версии явно обновить algorithm version по принятой схеме, tests и manifest. Тесты нельзя массово переписывать под новый результат до разбора причин различий.

## 14. Приёмочные тесты: конкретные контрпримеры

Новые названия тестов ниже — задания на создание; существующие suites перечислены отдельно. Каждый no-good проверяется на маленьком полном переборе независимым oracle, а не тем же CP-SAT adapter.

### Модель и конфликты

- `NetworkConstraintModelOracleTest`: случайные малые каталоги, 2–6 demands, разные roots; exhaustive enumeration сравнивает feasible set, optimum внутри каталога и canonical DU/economics.
- `ConflictCutSoundnessTest`: ни один cut не исключает допустимое назначение в своем proof scope; false literals, conditional DU, root policy и изменения каталога включены.
- `JointPortChoiceTest`: A+B конфликтуют, A+C допустимы; A сохраняется. A–B–C conflict graph без A–C не превращается в clique.
- `NetworkConnectivityTest`: detached cycle, leaf без root, два родителя, useless spur, несколько roots, zero-flow demand, два demands в одной точке (один с нулевым flow), bookkeeping не обходит физический ввод.
- `SharedAssetAccountingTest`: общий ствол оплачивается один раз, flow суммируется; частичное overlap, обратная ориентация, ложное совпадение разных уровней, два исходящих луча existing root стоят как два присоединения.
- `CanonicalDiameterFeedbackTest`: topology требует иной DU, сохраняется topology и фиксируется правильный DU; смена длины/descendants отменяет прежнюю implication.
- `UnknownIsNotInfeasibleTest`: timeout, bounded-router fail, budget truncation, incomplete catalog и техническая ошибка не порождают proof cut/no_route.
- `CatalogExpansionProofScopeTest`: после добавления нового junction/alternative прежний full-assignment no-good не запрещает новый допустимый вариант.
- `ObjectiveBoundSoundnessTest`: lower bound никогда не выше exact cost на exhaustive cases; отдельные rounding, special-depth, chamber и shared cases; surrogate optimum не становится exact optimum. Поздний candidate меняет balanced anchor — старый proof/gap не наследуется.
- `CoverageProofScopeTest`: полного решения нет, частичное допустимо; scope полного подключения не исключает частичную сеть, пустой лес не публикуется как готовый результат.

### Геометрия и evaluator

- `FrozenNetworkEvaluatorTest`: вход и topology/XY не изменились; `finish(A)→B` трактуется как новый candidate; mutation после оценки не меняет AcceptedSolution.
- `DirectedPathCertificateTest`: путь допустим только в одном направлении; DU общего ствола не отсекает маленькую узкую ветвь; изменение context делает сертификат неприменимым.
- `PhysicalChainReassemblyTest`: техническое дробление не меняет sizing, depth station и цену; split внутри road special не разрешает неправильный путь.
- `ChamberConfigurationModelTest`: фактические лучи с existing network, совпадение стороны, 5-е примыкание, оба конца camera→camera, degree2 technical continuation, камера рядом с существующей.
- `ConnectedDepthAdmissionTest`: локально возможные профили несовместимы в общем узле; network solver обнаруживает это; нельзя сохранить valid по отдельным edges.

Существующие опорные suites сохранить: `CorridorDirectionalAdmissionTest`, `CorridorLinkDirectionTest`, `CorridorTrunkAdmissionTest`, `CorridorTerminalRoadContinuationTest`, `CorridorIndividualAnchorTest`, `CorridorCompressionAdmissionTest`, `CorridorPortCompatibilityTest`, `CorridorJunctionAssignmentTest`, `CheckedCorridorAssemblyTest`, `ChamberApproachDiameterGenerationTest`, `OfficialNetworkSizingOracleTest`, `DepthTechnicalSplitContractTest`, `DepthGraphClosureOracleTest`, `DepthIndependentAdmissionTest`, `SavedDepthExportParityTest`, Saved*-assessment suites.

### Интеграция, ресурсы и совместимость

- `CpSatRuntimeSmokeTest`: actual pinned native, Java11, packaged image/non-root/temp, known optimum, repeated load/solve и asynchronous stop.
- `NativeCancellationRaceTest`: до регистрации, между регистрацией и native handle, во время solve, evaluator и перед persistence; slot не освобождается раньше завершения.
- `JobAttemptFencingIntegrationTest`: реальная DB, lease transfer, stale result, rollback между run/job updates, cancel/complete, executor rejection, repeat claim errors, смерть JVM и повторная попытка.
- `ExecutionVersionCompatibilityTest`: queued run старой версии не выполняется под новой подписью; legacy completed result читается; один STABLE и legacy alias сохранены.
- `NextGenerationOfficialApiTest`: import→run(depth=true)→result→export, 17/17, все variants проходят schema/Saved*-допуск; повторный export после рестарта.
- `NativeMemoryBudgetTest`: многократные runs, модель у лимита, отказ по budget без OOM, отсутствие роста RSS после установившегося прогрева; учёт Java+native.

Сохранить `RoutingAlgorithmRegistryTest`, `OfficialRunParametersTest`, `OfficialJsonSchemaContractTest`, controller/export tests, frontend tests. Native dependency нельзя прятать за skipped tests на production target.

### Corpus и защита от подгонки

Официальный fixture плюс отдельный official-like набор, подготовленный до настройки алгоритма и не используемый для выбора heuristics. Набор сценариев: 1, 17, 34 и 65+ demands; разные количества roots; плотные и редкие obstacles; узкие проходы; дороги/социальные запреты; concave ОКС; невозможная глубина; конфликтные камеры; отсутствие пути; большие пространственные окна.

Синтетические variants строить геометрически осмысленно: перенос/поворот всех метрических объектов вместе, перестановка входного порядка и IDs, изменение одного препятствия, разбиение одной физической линии. Для поворота/переноса из-за округления сравнивать обязательные свойства и допуски, не обещать побайтовую эквивалентность проекции. ID permutation не должна менять инженерную допустимость и не должна активировать специальный путь для знакомого ID.

Размер 3 ГБ input / 500 МБ output, машина 16 ГБ и 50 users отражены в репозиторном R9. Проверять reader/writer и end-to-end отдельно, не объявлять весь R9 закрытым по одному stream test. У `OfficialTopologyScaleTest` сейчас defaults depth=false при ожидании profiles; сначала исправить intended parameters, не удалять assertions.

## 15. Замеры и воспроизводимость

Считать отдельно: queue, input/windows/decode, catalog/assets/configurations/conflicts, model construction, native search, canonical sizing, frozen geometry/depth/economics, refinement, final validation, persistence/export. Для вложенных стадий хранить inclusive/exclusive time, не суммировать перекрывающиеся времена.

Counters: nodes, directed options, physical assets, variables/constraints, conflicts по типу, попытки solve, accepted/rejected/unknown, cuts и их reuse, expansions/truncations, evaluator calls, legacy-generator time, SQL queries/rows, cache hit/eviction, peak Java heap/native RSS, CPU/GC. Метрики должны объяснять ускорение, а не только показывать общее число секунд.

Manifest: commit+dirty diff, input SHA, rules/catalog hash, execution descriptor, JDK/image digest, OR-Tools/JNA/protobuf versions, seed/workers/deadline, CPU/RAM/cgroup flags, depth parameters, starts/ends и test commands. Bundle/strict export/quality report сохраняются отдельно для каждого запуска.

Baseline и candidate — замороженные сборки в отдельных каталогах на E:. Во время длинного расчёта нельзя менять его `target`, dataset, contracts или classpath. Не запускать оба тяжёлых benchmark одновременно. Профиль JFR снимать отдельно от сравнительных timing runs. До нового worktree сначала проверить существующие прикреплённые worktrees и использовать управление worktrees приложения; не создавать лишние checkout и не переписывать историю.

Официальный файл: `datasets/official/lct-2026.geojson`, 633 402 байта, SHA-256 `cffb7133419d93fe364a53015a7d3ead289f671cbfaf6f4befe87f2a21914130`. Не модифицировать его ради успешного benchmark.

## 16. Rollout, rollback и комплект для конкурса

### Stable promotion

Разработка может временно держать два planner, но production adapter один. Переключение производится только после N00–N11; новый engine становится обычным `stable`. Offline shadow comparison не должен оставаться обязательным двойным расчётом пользовательского запроса.

Fallback не означает «после нового таймаута запустить старые 73 минуты». Разрешён только ограниченный тем же deadline механизм, который честно отражён в version/diagnostics и участвует в latency gate. Надёжный rollback — предыдущий проверенный release image с корректной политикой queued versions; миграции metadata должны быть additive/backward-readable. Не делать destructive rollback БД.

Это ТЗ на реализацию не даёт само по себе разрешения на действие в production/VPS. Подготовить release и runbook, проверить на изолированном стенде; фактический deploy выполнять только по разрешённому пользователем workflow и `docs/operations/VPS_DEPLOYMENT.md`. При отсутствии разрешения отметить «release готов, production deployment не выполнен», не утверждать, что VPS обновлён.

### Что должно работать в конкурсной демонстрации

1. Чистый запуск поставки по документированным командам.
2. Импорт официального и второго, ранее не подогнанного набора.
3. Обычный запуск depth-on без скрытых параметров, prepared answer и ручных правок.
4. Понятный прогресс, отзывчивый интерфейс и действующая отмена.
5. Результат на карте: подключения, общие ветви, камеры, ДУ, длины, стоимость и глубина.
6. Объяснение конкретного выбранного обхода/отклонённой комбинации через rule ID и геометрию, без выдуманного «мнения эксперта».
7. Различающиеся допустимые варианты, если они найдены; честное объяснение частичного результата.
8. Strict export, повторный экспорт сохранённого результата после рестарта.
9. Таблица старый/новый: время, coverage, стоимость, длина, повороты, нарушения, memory — с одинаковым стендом и хешами.
10. Повторяемость другим человеком из переданного release-комплекта.

Конкурсные формулировки только по доказанным данным: «совместно выбирает сеть и инженерные конфигурации», «исключает доказанные несовместимые сочетания», «проверяет результат независимо». Не писать «наш новый математический алгоритм доказанно лучше всех», «гарантированный глобальный оптимум», «ускорение в 50 раз» по чужой статье или фиктивные консультации.

### Обязательные deliverables реализации

- Рабочий Java/native движок в normal stable pipeline, UI/result/export совместимы.
- Pin dependencies + runtime/image/license manifest; нет сетевой зависимости solver во время расчёта.
- Unit/property/oracle/integration/native/load/scale tests и явные CI gates.
- Reproducible benchmark harness, frozen baseline/new bundles, quality/cut-soundness reports.
- Руководство запуска, ограничения модели, определения статусов, cancellation/recovery/rollback runbook.
- Короткий конкурсный evidence report с только фактически подтверждёнными числами.

Большие результаты — на E: в ignored artifacts, в Git — код, tests, небольшие fixtures и компактные manifests/reports. Не коммитить secrets, dumps, native build caches и гигабайтные datasets.

## 17. Жёсткие запреты и финальный чек-лист

Не завершать задачу, если получилось лишь подключить OR-Tools, решить маленький пример, заменить один port-selector или показать быстрый master без инженерного допуска. Не получать скорость отключением depth, отбрасыванием demands/obstacles, увеличением tolerances, урезанием обязательных проверок или выдачей старого ответа.

Не объявлять solver ошибочным/неподходящим после одного случая без профиля; но и не продолжать бесконечно усложнять модель без измеримого прогресса. На каждом этапе фиксировать долю catalog generation, native search и admission. Если узкое место сместилось в построение геометрии, оптимизировать его exact reuse/подготовкой, а не скрывать за быстрым solver-only benchmark.

Финальная приёмка:

- [ ] Новый engine обслуживает один stable adapter; legacy alias/сохранённые результаты совместимы.
- [ ] Все обязательные нормы source102 и актуального ТЗ выполняются без ослабления.
- [ ] Полная сеть, не только порты: roots, shared branches, chambers, DU, connected depth, exact economics.
- [ ] Ни одного unsound cut на exhaustive corpus; UNKNOWN не выдаётся за невозможность.
- [ ] Каталог/admission/version scopes проверены; proof claims честны.
- [ ] Официальный depth-on: 17/17, качество не хуже, полный latency gate и ≥10× paired improvement.
- [ ] Второй неизвестный набор и граничные случаи работают без ручной настройки координат.
- [ ] Native runtime загружается из final image; память/отмена/lease/restart/crash проверены.
- [ ] End-to-end API→PostGIS→result→strict export, frontend и compatibility gates зелёные.
- [ ] Масштаб/50 users/IO gates выполнены либо явно перечислены как незакрытые — без ложного «всё готово».
- [ ] Release и rollback воспроизводимы; production deployment заявлен только если действительно выполнен с разрешением.
- [ ] Конкурсный комплект содержит проверяемые артефакты, а не обещания будущего прототипа.

**Итоговая установка:** построить новый основной движок с совместным выбором сети и доказанными конфликтами, используя существующую инженерную базу. Исследовательские риски закрываются этапами и тестами, а не отменяют требование готовой поставки. Главный результат — быстрое, допустимое и объяснимое решение на реальных данных.
