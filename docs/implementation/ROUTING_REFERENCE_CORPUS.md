# Корпус эталонных трассировок

**Статус:** рабочий процесс улучшения алгоритма, не официальный источник требований
**Обновлено:** 23 сентября 2026 года

## Зачем он нужен

Экспертные и удачные ручные решения дают алгоритму полезные примеры общей топологии, размещения
камер и геометрии ветвлений. Они хранятся отдельно от официального входа и не заменяют ТЗ. Это
защищает проект сразу от двух ошибок: потерять ценный инженерный пример или принять одну ручную
линию за единственно допустимый ответ.

Приоритет проверки всегда такой:

1. официальный контракт и ограничения организатора;
2. подключение ОКС, корректность дерева, расходов, ДУ и стоимости;
3. инженерная регулярность и диагностическое сходство с экспертными примерами;
4. длина, стоимость и время расчёта относительно принятого checkpoint.

## Что является блокирующей проверкой

Для reference-case блокируются только проверяемые инварианты: целостность fixture, покрытие
заявленных потребителей, связность, отсутствие циклов, ветвление в явных камерах и предельная
степень узла. Точное совпадение координат, количества поворотов или полной длины с ручной схемой
не блокирует результат алгоритма.

Новый алгоритмический кандидат принимается только после независимой официальной валидации. Затем
его сравнивают с текущим checkpoint по покрытию, score/стоимости, длине, числу камер, инженерным
предупреждениям и runtime. Улучшение одной характеристики не скрывает регрессию другой: такой
вариант можно оставить отдельной стратегией, но нельзя молча объявить новым основным результатом.

## Первый экспертный пример

`datasets/reference/professional-routing-01.geojson` извлечён из переданного `1.geojson`. Исходник
содержал старую округлённую подложку, поэтому она исключена. Зафиксированы только 26 линий и 11
маркеров ветвления. На текущем официальном входе пример образует:

- одно дерево из 29 узлов и 28 логических участков;
- 17 листьев — по одному на каждую точку подключения;
- корень в существующей камере 106 с двумя новыми лучами;
- четыре камеры степени 4 и семь камер степени 3;
- расходы корневых ветвей 96,90 и 391,82 т/ч при общем расходе 488,72 т/ч;
- длину ручных осевых линий 1913,859 м в EPSG:32637.

Две нарисованные линии проходят через внутренний маркер камеры. Проверка обязана разделить их на
логические участки — это отдельный полезный regression-case для общей сети.

## Цикл добавления примера

1. Оригинал остаётся вне репозитория; фиксируются источник, право хранения и SHA-256.
2. Из смешанного GeoJSON удаляется старая подложка и редакторские стили.
3. Создаётся отдельный manifest с привязкой к версии официального входа и допусками.
4. Автоматическая проверка воспроизводит топологию и заявленные числовые свойства.
5. Для результата алгоритма снимаются официальные метрики и неблокирующее геометрическое сравнение.
6. Наблюдение превращается сначала в общий тест или эвристику без координат конкретного датасета.
7. Изменение алгоритма проходит focused tests, полный Java 11 gate и живой расчёт согласно roadmap.

## Команды

Проверить текущий корпус:

```bash
pnpm benchmark:reference
```

Сравнить официальный экспорт алгоритма с примером:

```bash
pnpm benchmark:reference -- output/result.geojson
```

Извлечь ручной слой из нового смешанного файла:

```bash
node scripts/curate-routing-reference.mjs \
  /path/to/source.geojson \
  datasets/reference/<reference-id>.geojson \
  <reference-id>
```

Координаты, ID и расположение объектов reference-case нельзя переносить в production planner.
Обобщаем только инженерный принцип и подтверждаем его на официальных и синтетических тестах.
