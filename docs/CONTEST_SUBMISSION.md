# HeatRoute: конкурсное описание решения

## Проблема

При предварительном проектировании инженер вручную решает несколько связанных задач: где
присоединить каждый ОКС, как обойти ограничения, где объединить ветви, какие камеры поставить и
какой ДУ потребуется после сложения расходов. Локально короткий маршрут может оказаться дорогим
или сделать всю сеть недопустимой. Поэтому последовательная прокладка «по одному зданию» не даёт
хорошего общего решения.

Цена ошибки возникает не только в лишних метрах. Неверная точка присоединения меняет топологию,
расход общего участка, ДУ, число камер и стоимость. Чем позже это обнаружено, тем больше
вариантов приходится пересобирать вручную.

## Решение

HeatRoute получает городской GeoJSON и за один запуск строит предварительную схему подключения
всех перспективных объектов. Система:

1. проверяет исходные данные;
2. создаёт физически допустимые трассы с учётом препятствий;
3. объединяет совпадающие участки в общие assets;
4. синтезирует топологию сети через CP-SAT;
5. суммирует расходы и назначает ДУ;
6. проверяет камеры, пересечения, непрерывные длины и стоимость;
7. показывает результат на карте и выгружает строгий GeoJSON.

Результат предназначен для быстрого сравнения предпроектных решений. Он не заменяет рабочую
документацию и инженерную ответственность, но переносит трудоёмкий перебор вариантов и первичную
проверку в воспроизводимый цифровой процесс.

## Уникальность

HeatRoute оптимизирует не 17 независимых путей, а одну физическую сеть. Если несколько объектов
используют общий ствол, он существует в модели один раз, несёт суммарный расход, получает один
итоговый ДУ и один раз входит в стоимость.

Архитектура HeatRoute разделяет три разных класса сложности:

- JTS/PostGIS отвечают за геометрию и препятствия;
- OR-Tools CP-SAT выбирает совместимую топологию;
- `FrozenNetworkEvaluator` выполняет точный инженерный допуск готовой сети.

Если evaluator находит локальный конфликт, алгоритм адресно расширяет каталог и повторяет синтез.
Такой цикл не требует полного перебора непрерывной плоскости, а найденный вариант всё равно
проходит отдельную финальную проверку.

## Почему результату можно доверять

- расчётные расстояния выполняются в EPSG:32637;
- вход, параметры и версия алгоритма фиксируются в immutable run;
- production API не имеет скрытого fallback на старый планировщик;
- итог проходит отдельные validation, engineering и sizing проверки;
- выгрузка проверяется JSON Schema и межобъектным Java-валидатором;
- точная версия расчётного ядра видна в поле `algorithm_version`;
- ограничения алгоритма указаны явно: bounded-поиск не выдаётся за доказанный глобальный оптимум.

## Измеренный результат

На публичном VPS контрольный run от 29.09.2026 показал:

| Показатель | Значение |
|---|---:|
| Версия расчётного ядра | 6 |
| Подключение | 17 из 17 ОКС |
| Время run | 15,381 с повторный; 19,137 с cold |
| Новая сеть | 2 170,113 м |
| Стоимость | 300 092 048,85 ₽ |
| Validation / engineering / sizing issues | 0 / 0 / 0 |

Время относится к конкретному конкурсному набору и конкретному VPS. Для скрытого городского набора
оно будет зависеть от числа объектов, плотности ограничений и количества расширений каталога.

## Польза для Москвы

- быстрее получить исходную схему для инженерного обсуждения;
- сравнивать варианты по одной воспроизводимой методике;
- видеть причины недопуска до передачи решения на следующий этап;
- уменьшить число повторных ручных пересборок из-за топологии, ДУ и препятствий;
- передавать результат между системами без ручной перерисовки;
- хранить историю расчётов и понимать, на каких данных получен каждый вариант.

Количественное сокращение трудозатрат следует подтверждать замером с профильными инженерами. В
презентации нельзя подменять такой замер выдуманной цитатой или оценкой.

## Внедрение

Первый контур внедрения: предпроектный анализ подключения группы ОКС. Инженер загружает GeoJSON,
получает проверенную схему, изучает её на карте и выгружает результат для согласования.

Дальнейшие интеграции:

- городские геоинформационные системы и мастер-данные;
- данные градостроителей и дорожных служб;
- слои метрополитена, железных дорог и трамвайной инфраструктуры;
- владельцы газовых, электрических и других линейных коммуникаций;
- системы технических условий, смет и согласований;
- BIM/GIS-контур проектных организаций.

## Развитие

1. Калибровка каталогов и эвристик на новых районах Москвы.
2. Подключение актуальных городских ограничений по API.
3. Несколько сценариев развития территории и поэтапное строительство.
4. Продольный профиль и инженерная проверка по подтверждённым высотным данным.
5. Учет сроков перекрытий, разрешений, рисков и стоимости владения.
6. Объяснимое сравнение вариантов: почему выбран ствол, камера или присоединение.
7. Экспорт в форматы и системы, используемые городом и проектировщиками.
