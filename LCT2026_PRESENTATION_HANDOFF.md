# Бриф финальной презентации HeatRoute для ЛЦТ-2026

## Позиционирование

HeatRoute - система предпроектного синтеза тепловой сети для группы объектов. Она не заменяет
проектировщика и не выпускает рабочую документацию. Её задача - быстро получить проверяемую основу
для инженерного обсуждения: топологию, трассы, камеры, расходы, ДУ и стоимость.

Главная фраза:

> **Не 17 кратчайших линий, а одна инженерно проверенная сеть для 17 объектов.**

## Рекомендуемая структура: 12 слайдов

### 1. Титульный

**HeatRoute**

**Автоматическое построение предварительной схемы теплоснабжения**

Команда Dragons, ЛЦТ-2026, трек №2.

Визуал: один чистый скриншот итоговой сети, без мелкого текста.

### 2. Проблема инженера

**Одно подключение меняет всю сеть**

- где присоединиться;
- как обойти городские ограничения;
- когда объединить ветви;
- где поставить камеры;
- какой ДУ нужен после сложения расходов;
- как пересчитать стоимость после изменения трассы.

Финальная строка:

> Локально короткий маршрут может сделать общую сеть дороже или недопустимой.

### 3. Почему существующих подходов недостаточно

**GIS показывает данные. Кратчайший путь строит линию. Инженеру нужна сеть.**

Три колонки:

| Подход | Что умеет | Чего не хватает |
|---|---|---|
| Ручная трассировка | инженерный контекст | скорость и воспроизводимость |
| Кратчайший путь | быстро соединяет две точки | общие стволы, расходы, ДУ, камеры |
| HeatRoute | синтезирует всю сеть | инженер принимает финальное решение |

### 4. Решение

**Один GeoJSON → проверенная сеть → строгий GeoJSON**

Короткий конвейер:

```text
Данные → допустимые трассы → общая топология → расходы и ДУ → проверка → стоимость
```

Слева исходные слои, по центру схема, справа карта результата.

### 6. Главная уникальность

**Оптимизируем физическую сеть, а не набор линий**

Показать два маленьких рисунка:

- слева: независимые линии, общий коридор посчитан несколько раз;
- справа: один общий asset, суммарный расход, один ДУ и одна стоимость.

Фраза:

> Совпадающий участок существует в модели один раз и оплачивается один раз.

### 7. Архитектура алгоритма

**Геометрия + CP-SAT + точный инженерный допуск**

```text
RoutingProblemSnapshot
        ↓
obstacle-aware каталог
        ↓
PhysicalAssetCompiler
        ↓
CP-SAT topology synthesis
        ↓
FrozenNetworkEvaluator
        ↓
валидный GeoJSON
```

Не перегружать названиями классов: рядом с каждым блоком дать одну русскую подпись.

### 8. Как алгоритм исправляет ошибки

**Не пересчитываем пространство вслепую**

```text
CP-SAT выбрал сеть
        ↓
точный evaluator нашёл локальный конфликт
        ↓
ConflictStore фиксирует несовместимую комбинацию
        ↓
каталог расширяется только в проблемной области
        ↺
```

Ключевой тезис:

> Оптимизатор предлагает. Инженерный evaluator допускает.

### 9. Инженерная проверка

**Каждый опубликованный вариант проходит повторный контроль**

Четыре блока:

- геометрия: препятствия и пересечения;
- топология: связность, upstream, камеры;
- гидравлическая модель задачи: агрегированный расход и ДУ;
- экономика: физические участки и сумма компонентов.

Внизу: JSON Schema + `OfficialOutputContractValidator`.

### 10. Проверяемость и готовность

**Это работающий сервис, а не макет**

- immutable run;
- SHA-256 входа;
- `algorithm_version`;
- Swagger/OpenAPI;
- строгая JSON Schema;
- durable jobs в PostgreSQL;
- Docker Compose и публичный стенд.

QR-коды: приложение и Swagger.

### 11. Ценность и внедрение

**От предпроектного перебора к единому цифровому процессу**

Для инженера:

- готовая основа варианта;
- раннее обнаружение конфликтов;
- меньше ручных пересборок;
- карта и машиночитаемая выдача.

Для города:

- единые правила сравнения;
- воспроизводимость;
- пакетная оценка территорий;
- интеграция с городскими GIS.

Интеграции: дороги, градостроительство, метро, железная дорога, газ, электрические сети, BIM/GIS.

### 12. Финал

**HeatRoute превращает городской GeoJSON в проверяемую схему теплоснабжения**

Три строки:

- единая сеть вместо независимых маршрутов;

- не больше 35-45 слов основного текста;
