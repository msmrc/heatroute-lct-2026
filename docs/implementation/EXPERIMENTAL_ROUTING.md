# Изолированные эксперименты с маршрутизацией

## Зачем нужен отдельный контур

Основной алгоритм должен оставаться воспроизводимым во время быстрых исследований. Поэтому новая
идея сначала реализуется как отдельный профиль запуска, получает собственную версию и сравнивается
с основным алгоритмом на одном и том же импорте. Эксперимент не считается улучшением только потому,
что визуально похож на экспертную разметку: он обязан пройти официальный валидатор, расчёт диаметров,
экономику и экспорт.

## Текущие профили

| API-профиль | Версия | Назначение |
|---|---|---|
| `stable` | `global-tree-46` | Основной воспроизводимый baseline; используется по умолчанию |
| `expert_experimental` | `expert-tree-1` | Изолированный поиск инженерной геометрии с расширенными бюджетами |

Если `algorithm_profile` отсутствует в запросе или в старой сохранённой записи, backend выбирает
`stable`. Версия фиксируется при создании run, а профиль остаётся в неизменяемых параметрах run.
Это позволяет worker после перезапуска выполнить именно выбранный алгоритм.

В интерфейсе есть отдельные действия «Рассчитать варианты» и «Экспериментальный алгоритм». Для
текущего импорта браузер хранит отдельные указатели на последний основной и экспериментальный run,
поэтому между результатами можно переключаться, не перезаписывая другой контур. Сами run и их
результаты хранятся в PostgreSQL; `localStorage` содержит только UI-указатели.

## Граница изоляции

- `StableRoutingAlgorithm` делегирует стабильному `OfficialRoutePlanner` с неизменными бюджетами.
- `ExpertExperimentalRoutingAlgorithm` — отдельный Spring-компонент и отдельная точка для развития.
- `RoutePlannerTuning` хранит именованные бюджеты двух профилей.
- `RoutingAlgorithmRegistry` требует ровно одну реализацию каждого объявленного профиля и не даёт
  приложению стартовать с неполной или дублирующей конфигурацией.
- Официальные валидаторы, ограничения, sizing, экономика, depth и экспорт намеренно общие. Обходить
  их в эксперименте запрещено.

Первый эксперимент не содержит координат, ID или специальных правил для эталонного файла. Он лишь
расширяет общий инженерный поиск: допустимую добавочную длину выхода из ОКС, число глобальных
repair-попыток, число egress-кандидатов, размер локальной группы, число перестроений и радиус зоны.
Основные значения остались равны значениям `global-tree-46`.

## Как добавлять следующую идею

1. Не менять `RoutePlannerTuning.stable()` и `StableRoutingAlgorithm` в исследовательском коммите.
2. Менять экспериментальную реализацию или её tuning; если нужна другая архитектура, создать новый
   класс за интерфейсом `RoutingAlgorithm`, не добавлять условные ветки по профилю в stable-код.
3. При любом изменении поведения поднять экспериментальную версию (`expert-tree-N`).
4. Добавить сфокусированный тест на новую гипотезу и регрессионный тест границы профилей.
5. Запустить `pnpm benchmark:reference`: экспертный corpus — диагностический ориентир, а не контракт.
6. Прогнать Java 11 tests, web tests/lint/typecheck и live Compose smoke с реальным import → run →
   export. Для обеих кнопок проверить, что run содержит ожидаемые profile и version.
7. Зафиксировать результат ниже. Не заменять baseline, пока эксперимент не сравнен на официальном
   наборе и явно не одобрен командой.

## Условия продвижения в основной контур

Эксперимент можно сделать новым baseline только отдельным решением после проверки:

- все официальные ограничения и выходной контракт проходят без послаблений;
- ни один обязательный ОКС не потерян;
- геометрия и гидравлическая арифметика независимо проверены;
- результат детерминирован и воспроизводится после рестарта worker;
- качество подтверждено официальным набором и advisory reference benchmark;
- время и память укладываются в согласованный профиль;
- версия stable повышена, документация и regression evidence обновлены.

До этого момента надпись «Экспериментальный» должна оставаться видимой в UI и provenance; такой run
нельзя выдавать за принятый основной результат.
