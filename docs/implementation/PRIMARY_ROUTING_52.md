# Primary routing 52 — ранний контроль поворота и отсечение несвязного поиска

**Дата:** 24.09.2026. **Статус:** локальный интегрированный gate PASS; цель по качеству/скорости
ещё не достигнута. Live API остаётся `global-tree-49`; этот документ не закрывает R-этапы.
База — [source51](PRIMARY_ROUTING_51.md), рабочее дерево поверх `6171362`.

## Изменения разделены по смыслу

### Исправление поиска: обязательный угол до выбора пути

Ограничение изменения направления ≤90° из §2.1 организаторского приложения теперь проверяется
в каждом переходе направленного A*, а не только после построения сети. Прежний поиск мог
выбрать более дешёвый недопустимый поворот и потерять существующий допустимый обход.
Два синтетических regression-теста сначала воспроизвели это поведение.

Проверка использует тот же зависящий от длины допуск миллиметрового округления, что и финальный
валидатор; верхняя граница 0,1° не является безусловным разрешением превышения. Узлы один раз
переводятся в целые миллиметры, чтобы разность больших UTM-ординат не теряла точность в горячем
цикле. Добавлен счётчик `angle_pruned` — он считает отвергнутые переходы, не уникальные маршруты.
Запрет поворота — конкурсное требование, не новое ограничение «только 45/90» из СП.

### Оптимизации без намеренного изменения допустимых решений

- Для углов 0–90° достаточно скалярного произведения. Заведомо слишком большой угол
  отсекается консервативной оценкой через L1-нормы; тригонометрия нужна лишь около границы 90°.
  L1-норма не меньше евклидовой, поэтому такой ранний отказ не сужает исходный допуск.
- Перед поиском по парам «предыдущий/текущий узел» проверяется связность обычного графа
  видимости двусторонним обходом. Раскрывается меньшая очередь. Если один компонент исчерпан
  без встречи, направленного допустимого пути тоже быть не может. Если компоненты встретились,
  полный поиск с ограничением углов всё равно обязателен.
- Используется та же точная проверка препятствий. Результаты проверки рёбер принадлежат
  одному вызову поиска; готовые маршруты между запусками не переиспользуются.

Изолированный конец раньше приводил к 761 проверке видимости; малая изолированная компонента
из двух узлов — к 1168. Новые regression-тесты ограничивают эти случаи соответственно 39 и 98
проверками. Это счётчики конкретных синтетических случаев, не оценка сложности любого графа.

## Камеры: подтверждённый пропуск кандидата

Аудит `.tooling/primary51-chamber-audit.md` обнаружил, что при объединении камер подход к зданию
пересчитывается с нуля и может потерять уже допустимый нормальный ввод. На проверенном случае
неизменённый двухповоротный подход существует, а генератор новых подходов возвращает пустой набор.
Восстановленный кандидат проходит полный finish, но пока проигрывает preferred по score.
Простое расширение количества проверяемых пар камер также не дало улучшения.

Отдельная доработка `CorridorRetainedTerminalApproaches`: сохранять перепроверенный demand-side
префикс и перестраивать ограниченный хвост у переносимой камеры. До 38 хвостов, два места
среза, до восьми итоговых путей; свежие альтернативы сохраняются. 18 новых focused-тестов плюс
реальный merge-test: 19/19 PASS в изолированных Java11-классах
(`.tooling/retained-terminal-final.log`), красная регрессия в `retained-terminal-red.log`.
Проверены обратная согласованная ориентация, поворот/перенос осей, пересечения и препятствия
в префиксе/хвосте, отсутствие бесплатного исключения своего ОКС, отмена и границы перебора.
Подключение в `buildMergedChamberDraft` проверено также в скомпилированном planner.
Интегрированный Java fast gate: 613 total / 610 выполнено / 3 scale skipped, PASS
(`.tooling/primary52-integrated-fast.log`). Отдельный полный corridor gate: 1/1 PASS за 104,88 с.
Лучший по score допустимый кандидат `corridor-refined-1` — 1898,684 м, 13 узловых камер,
277670360,94 ₽, score 13,470822106, без engineering issues. Предыдущий corridor checkpoint51:
лучший `corridor-12` — 1901,581 м, 14 камер, 280954359,27 ₽, score 13,571465060.
Это подтверждённое улучшение в компонентном gate; последующий основной pipeline также выбрал
его, что отдельно зафиксировано ниже. Результаты компонента — `.tooling/primary52-integrated-corridor.json`.

## Открыто

- Исправить сохранение допустимых углов после normalize/snap. Отдельный синтетический аудит
  `.tooling/primary52-normalize-audit.log` подтвердил: допустимая полилиния
  `(0,0)→(10,0)→(10,10)→(0,10)→(-1,0)` при разрешённом shortcut первого звена до `(10,10)`
  получает 135° на следующем повороте. Это модель графа видимости, не воспроизведение
  конкретного препятствия из supplied-датасета. Нужны regression и проверка соседних углов
  при shortcut/snap; финальный валидатор остаётся обязательным. Изменение не включено
  в performance-only A/B, иначе нельзя было бы проверять сохранение поведения.
- Preferred всё ещё имеет две дополнительные камеры и три дополнительных поворота против
  разметки Евгения; быстродействие всего расчёта и работа на других геометриях требуют измерений.
- После исправления normalize/snap рассмотреть включение уже завершённого shortest в seeds
  refinement (сейчас лишь corridor-portfolio). Ограничивать бесполезные проверки хвостов
  доказуемыми геометрическими отказами, не сокращением допустимых решений ради времени.
