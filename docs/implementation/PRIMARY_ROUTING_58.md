# Source58: альтернативы финализации ввода без потери допустимых сетей

Дата:24.09.2026. Тип работы — исправление поведения, не рефакторинг и не новое правило СП.
Предыдущий шаг57 дал проверяемый прогресс по ресурсам, но не улучшил итоговую геометрию.
Цель по форме, камерам и скорости остаётся открытой. Git/VPS не обновлялись.

## Подтверждённая причина

`ensureMandatoryEgress` выбирал проверяемый выход из ОКС по направлению от потребителя
к удалённой камере. Независимый `OfficialRouteValidator` проверяет другое: направление
фактического последнего звена. Оба выхода могут быть допустимы, но не совпадать.
Из-за этого финализатор мог заменить уже допустимую коридорную геометрию диагональю.

В ограниченном составном probe первый вызов `ensureMandatoryEgress` поменял ровно одно
ребро при неизменном ДУ100. Его prefix прошёл `lineAllowed`; проверка ввода относительно
камеры — false, относительно фактической соседней точки — true. Черновик1913,710 м /
18 поворотов /8 нерегулярных пар после этого стал1898,828 м /16 /11. Это не выигрыш
регулярности: согласованные четыре подхода к новой позиции камеры распались.
Trace: `.tooling/compound58-probe/trace.log`.

Новая альтернатива проверяет уже построенное последнее звено. Проверка всего префикса на
финальном ДУ остаётся обязательной. Дополнительно проверяется исключённый из префикса
последний отрезок: исключение относится только к своему `oks` с данным ID, не к другим
запретам или принятым веткам. При настоящем нарушении используется прежний восстановительный
поиск. Geometry/sizing/depth/economics/export не ослаблены. Координаты/ID набора не зашиты.

### Почему нельзя просто включить сохранение везде

Первый свежий all-1758 прошёл три dataset/export-теста, но **не прошёл сравнительную проверку
качества**: shortest1888,465 м /14 камер /279584017,06 ₽ вместо57 с1887,222 м /13 /
276460904,63 ₽. Balanced остался точно равен57, cheapest немного ухудшился. Смена конечной
геометрии изменила отбор промежуточных топологий; исчезло объединение двух соседних камер.
Эта версия не запускалась в пользовательском API. `primary58-initial-*` — evidence отклонённого
варианта, не текущей сборки. Planner294,988 с, corridor96,103 с; это не принятый выигрыш скорости.

Независимый разбор уточнил механизм: объединение камер311/312 **не пропало из генератора** —
все77 сообщений его первого расширения совпадают. В finished `corridor-refined-1` совпали
nodes/connections/инцидентность/расходы/ДУ, но ветка к demand9 выросла43,216→55,327 м.
Вся объединённая сеть стала1910,795 м вместо1898,684 м и проиграла неслитой1899,927 м.
Последующий перенос камеры в обоих случаях снял одинаковые11,462 м, т.е. причину удалось
локализовать **до** него. Это не основание увеличивать бюджет поиска мест камеры.
Отчёт: `.tooling/egress58-regression/README.md`; сравнение артефактов0,16 с, без нового Java plan.

Текущее решение явно разделяет `TerminalApproachPolicy.TOWARD_UPSTREAM` и `PRESERVE_VALID`.
Основной поиск/объединения сохраняют прежний способ доводки. Только после ограниченного отбора
черновиков **согласованного переноса камеры** выполняются обе альтернативы и общий полный допуск.
Действующая сеть остаётся кандидатом; замена разрешена по прежним строгим условиям отсутствия
ухудшения длины, цены, поворотов/узлов и с полной включённой глубиной. Полный plan не запускается
дважды, исходный датасет/готовый результат не переиспользуется между запусками. Цена — до двух
finish на уже выбранный локальный черновик; фактическое итоговое время надо измерить заново.
